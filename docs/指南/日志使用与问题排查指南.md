# 日志使用与问题排查指南

> 最后更新：2026-07-31  
> 适用范围：Web 请求、LangGraph 父图、Planner、Advisor、Seeker、Evaluator  
> [返回文档索引](../文档索引.md)

## 一、日志能解决什么问题

本项目的结构化日志用于回答以下问题：

1. 一次请求经过了哪些节点？
2. Planner 为什么路由到 Advisor 或 Seeker？
3. `topic_status` 在哪个节点发生了变化？
4. 同一个 Topic 的多轮澄清是否属于同一任务？
5. Advisor 是否真正调用了 `submit_query_plan` 并生成 `locked` 方案？
6. 请求失败时，完整异常堆栈和对应的 `error_id` 是什么？
7. Evaluator、Intent Classifier 等附加能力是否发生了非阻断降级？

日志不是 Graph State 的替代品：

- Graph State 保存当前业务事实和 checkpoint。
- 日志保存执行过程、路由依据、耗时和异常证据。

## 二、日志文件位置与保留策略

当前结构化日志文件：

```text
agentTest/logs/langgraph_app.jsonl
```

每一行都是一个独立 JSON 对象，称为 JSON Lines 或 JSONL。

日志使用 `TimedRotatingFileHandler` 按天滚动：

```text
langgraph_app.jsonl
langgraph_app.jsonl.2026-07-31
langgraph_app.jsonl.2026-08-01
```

默认保留最近 14 天，服务重启不会清空历史日志。

旧文件 `agentTest/logs/langgraph_app.log` 是结构化改造前的文本日志，不再作为当前排查依据，可以保留用于历史对比。

修改日志代码后必须重启 Web 服务，旧进程不会自动加载新代码。

## 三、四个身份字段

每条请求链路主要通过以下字段关联：

| 字段 | 含义 | 生命周期 |
|---|---|---|
| `conversation_id` | 前端左侧的完整对话 | 一个对话期间不变 |
| `topic_id` | 对话中的一次独立问数任务 | 多轮澄清和最终执行期间不变 |
| `request_id` | 一次 HTTP 请求或一次图调用 | 用户每发送一次消息都会变化 |
| `graph_thread_id` | LangGraph checkpoint 隔离键 | 当前为 `conversation_id:topic_id` |

排查单次执行优先使用 `request_id`；排查多轮澄清优先使用 `topic_id`。

## 四、公共日志字段

| 字段 | 说明 |
|---|---|
| `timestamp` | 带时区的 ISO 8601 时间 |
| `level` | `INFO/WARNING/ERROR` |
| `event` | 稳定的事件名称 |
| `node` | 当前节点或路由器名称 |
| `duration_ms` 或 `ms` | 执行耗时，单位毫秒 |
| `topic_status` | 当前 Topic 生命周期状态 |
| `route` 或 `decision` | Planner/Router 的最终路由 |
| `error_id` | 返回给用户的错误编号 |
| `error_code` | 稳定错误类别 |
| `error_type` | Python 异常类型 |
| `error_message` | 服务端异常摘要，不返回前端 |
| `stack_trace` | 完整异常堆栈，仅保存在服务端日志 |

不要依赖日志字段出现顺序，应该按 JSON 字段名读取。

## 五、事件类型

### 5.1 请求事件

| 事件 | 含义 |
|---|---|
| `request.started` | Web 已接收并开始处理请求 |
| `request.completed` | 请求正常完成，包含最终路由、状态和总耗时 |
| `request.failed` | 核心请求失败，包含 `error_id` 和完整堆栈 |
| `request.user_input` | CLI 模式记录的用户输入摘要 |

正常请求应该至少形成：

```text
request.started
→ node.started/node.completed
→ route.decided
→ state.changed
→ request.completed
```

失败请求应该形成：

```text
request.started
→ node.failed
→ state.changed(current=failed)
→ request.failed(error_id=...)
```

### 5.2 节点事件

| 事件 | 含义 |
|---|---|
| `node.started` | 节点开始执行 |
| `node.completed` | 节点正常完成 |
| `node.failed` | 核心节点失败，异常会继续向请求边界传播 |
| `node.degraded` | 附加能力失败但主流程继续，例如 Evaluator 入库失败 |
| `node.event` | 节点过程信息，例如工具调用和示例检索 |
| `node.detail` | 补充分析信息，例如有效需求和候选字段 |

当前 `node.detail` 主要由 Planner 的兼容接口产生，可能没有 `node` 字段。排查时使用相同 `request_id` 和相邻时间定位所属 Planner 执行。

### 5.3 路由与状态事件

| 事件 | 含义 |
|---|---|
| `route.decided` | Planner Router 或 SQL Router 选择了后续分支 |
| `state.changed` | 关键 State 字段发生真实变化 |

`topic_status` 的典型转换：

```text
new
→ clarifying
→ confirmed
→ generating_sql
→ validating_sql
→ executing
→ completed
```

异常时可能从任意非终态进入 `failed`。

## 六、PowerShell 常用命令

以下命令均在项目根目录执行。

### 6.1 查看最后 20 行原始日志

```powershell
Get-Content agentTest/logs/langgraph_app.jsonl -Tail 20
```

### 6.2 把 JSON 日志转换为对象

```powershell
$logs = Get-Content agentTest/logs/langgraph_app.jsonl |
    ForEach-Object { $_ | ConvertFrom-Json }
```

后续示例默认已经执行该命令。

### 6.3 查看最近的请求

```powershell
$logs |
    Where-Object { $_.event -eq "request.started" } |
    Select-Object -Last 10 timestamp,request_id,topic_id,input_length
```

### 6.4 根据 request_id 还原单次请求

```powershell
$requestId = "替换为真实request_id"

$logs |
    Where-Object { $_.request_id -eq $requestId } |
    Select-Object timestamp,level,event,node,route,decision,topic_status,previous,current,ms
```

建议按以下顺序阅读：

1. `request.started`
2. Planner 的 `node.completed`
3. `planner_router` 的 `route.decided`
4. Advisor 或 Seeker 的节点日志
5. `state.changed`
6. `request.completed/request.failed`

### 6.5 根据 topic_id 查看多轮澄清

```powershell
$topicId = "替换为真实topic_id"

$logs |
    Where-Object { $_.topic_id -eq $topicId } |
    Select-Object timestamp,request_id,event,node,topic_status,previous,current,answer_summary
```

同一个 `topic_id` 下出现多个不同 `request_id` 是正常现象，表示用户在同一个问数任务中进行了多轮补充、选择或确认。

### 6.6 根据 error_id 定位完整异常

```powershell
$errorId = "用户提供的错误编号"

$logs |
    Where-Object { $_.error_id -eq $errorId } |
    Select-Object timestamp,error_code,error_type,error_message,stack_trace |
    Format-List
```

客服或业务用户只需要提供 `error_id`，不要要求用户复制内部异常文本。

### 6.7 查看所有 Topic 状态变化

```powershell
$logs |
    Where-Object { $_.event -eq "state.changed" } |
    Select-Object timestamp,request_id,node,field,previous,current
```

### 6.8 查看 Planner 和 SQL 路由

```powershell
$logs |
    Where-Object { $_.event -eq "route.decided" } |
    Select-Object timestamp,request_id,node,decision,completeness,plan_status,topic_status
```

### 6.9 查看非阻断降级

```powershell
$logs |
    Where-Object { $_.event -eq "node.degraded" } |
    Select-Object timestamp,request_id,node,error_code,error_type,stage
```

出现 `node.degraded` 不代表查询一定失败。例如 Evaluator 入库失败时，用户仍可能已经获得正确答案。

### 6.10 查看最慢节点

```powershell
$logs |
    Where-Object {
        $_.event -eq "node.completed" -and
        $null -ne $_.ms
    } |
    Sort-Object ms -Descending |
    Select-Object -First 20 timestamp,request_id,node,ms
```

## 七、典型问题排查

### 7.1 用户已经确认，为什么系统仍然追问

按同一 `topic_id` 依次检查：

1. Advisor 的 `node.completed` 是否为 `locked=True`。
2. 是否出现 `locked_plan:` 的 `node.event`。
3. Planner 日志中 `accept_locked_plan` 是否为 `True`。
4. Planner Router 是否为 `decision=seeker`。
5. `plan_status` 是否为 `confirmed`。

如果 Advisor 文本声称方案完整，但日志为 `locked=False`，说明只是 LLM 文本表达，程序并没有形成可确认方案。

如果 Planner 输出 `completeness=full`，而 Advisor 日志显示 `completeness=none`，应检查 Planner→Advisor 的 State Schema 是否声明了交接字段。

### 7.2 请求失败但前端只显示错误编号

这是预期行为。使用错误编号执行：

```powershell
$logs |
    Where-Object { $_.error_id -eq "错误编号" } |
    Format-List
```

重点查看：

- 最后一个 `node.started`
- 是否有对应的 `node.failed`
- `error_type`
- `error_message`
- `stack_trace`
- checkpoint 是否记录 `topic_status=failed`

### 7.3 Advisor 为什么没有提交方案

检查 Advisor 事件：

```powershell
$logs |
    Where-Object {
        $_.node -eq "advisor_agent" -and
        $_.request_id -eq "目标request_id"
    } |
    Select-Object timestamp,event,message,locked,answer_summary
```

常见结果：

- `模式=clarify`：本轮只允许检索和追问。
- `模式=plan`：本轮允许调用 `submit_query_plan`。
- `本轮工具调用: [无]`：模型没有调用任何工具。
- `locked=False`：没有形成程序认可的 locked 方案。
- `locked=True`：方案已锁定，下一轮可以由 Planner 处理最终确认。

### 7.4 SQL 为什么被重新生成

检查：

```powershell
$logs |
    Where-Object {
        $_.request_id -eq "目标request_id" -and
        $_.node -in @("validate_sql", "sql_router", "prepare_sql_fix", "generate_sql")
    } |
    Select-Object timestamp,event,node,valid,retry,decision,error
```

典型链路：

```text
validate_sql(valid=False)
→ sql_router(decision=fix)
→ prepare_sql_fix
→ generate_sql(retry=1)
```

## 八、日志使用原则

### 8.1 不记录完整敏感数据

- 不打印 API Key、数据库密码和 Token。
- 不打印完整查询结果。
- SQL、用户问题和模型输出需要限制长度。
- State 中只保存安全错误编号，不保存完整异常堆栈。

### 8.2 不把日志当业务判断依据

业务路由必须由 Graph State、QueryPlan 和领域校验决定。日志只能用于观测和诊断，不能通过“日志里出现某个字符串”驱动业务流程。

### 8.3 不仅看 LLM 文本

排查方案确认问题时，应优先查看：

```text
locked
plan_status
route.decided
topic_status
```

LLM 回复中出现“已确认”“方案完整”等文字，不代表程序状态真的已经变化。

## 九、当前边界

- 当前日志文件适用于单进程或单实例本地部署。
- 多进程 Gunicorn 或多实例部署时，不建议多个进程共同滚动同一个本地文件；应输出 JSON 到标准输出，再交给集中式日志系统采集。
- 当前尚未接入 Prometheus、Grafana、OpenTelemetry 或 ELK。
- 当前日志查询主要使用 PowerShell，后续可以增加只读 Debug 接口或日志查询脚本。
- `MemorySaver` 和内存 Session 重启后会丢失，日志只能还原执行过程，不能替代持久化 checkpoint。

## 十、面试表达

项目最初只有按节点打印的文本日志，并发请求无法串联。我使用 `ContextVar` 自动注入 Conversation、Topic、Request 和 Graph Thread 四个身份字段，把日志改为 JSON Lines 和按天滚动，并定义请求、节点、路由、状态变化、失败和降级事件。核心异常在统一请求边界生成 `error_id` 和完整堆栈，前端只展示安全提示；Evaluator 等非核心能力使用 `node.degraded`，不会影响已经成功的查询结果。实际排查时可以通过一个 `request_id` 还原完整节点链路，也可以通过 `topic_id` 还原多轮澄清过程。
