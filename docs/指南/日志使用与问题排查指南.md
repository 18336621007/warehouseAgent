# 日志使用与问题排查指南

> 最后更新：2026-08-04
> 适用范围：Web 请求、LangGraph 父图、Planner、Advisor、Seeker、Evaluator  
> [返回文档索引](../文档索引.md)

## 一、日志能解决什么问题

本项目的结构化日志用于回答以下问题：

1. 一次请求经过了哪些节点？
2. Planner 为什么路由到 Advisor 或 Seeker？
3. `topic_status` 在哪个节点发生了变化？
4. 同一个 Topic 的多轮澄清是否属于同一任务？
5. Advisor 是否真正调用了 `submit_query_plan` 并生成 `locked` 方案？
6. 请求失败时，完整异常堆栈和对应的 `error_id` 是什么？
7. Evaluator、Intent Classifier 等附加能力是否发生了非阻断降级？

日志不是 Graph State 的替代品：

- Graph State 保存当前业务事实和 checkpoint。
- 日志保存执行过程、路由依据、耗时和异常证据。

## 二、日志文件位置与保留策略

当前结构化日志文件：

```text
agentTest/logs/langgraph_app.jsonl
```

每一行都是一个独立 JSON 对象，称为 JSON Lines 或 JSONL。

日志使用 `TimedRotatingFileHandler` 按天滚动：

```text
langgraph_app.jsonl
langgraph_app.jsonl.2026-07-31
langgraph_app.jsonl.2026-08-01
```

默认保留最近 14 天，服务重启不会清空历史日志。

旧文件 `agentTest/logs/langgraph_app.log` 是结构化改造前的文本日志，不再作为当前排查依据，可以保留用于历史对比。

修改日志代码后必须重启 Web 服务，旧进程不会自动加载新代码。

## 三、四个身份字段

每条请求链路主要通过以下字段关联：

| 字段 | 含义 | 生命周期 |
|---|---|---|
| `conversation_id` | 前端左侧的完整对话 | 一个对话期间不变 |
| `topic_id` | 对话中的一次独立问数任务 | 多轮澄清和最终执行期间不变 |
| `request_id` | 一次 HTTP 请求或一次图调用 | 用户每发送一次消息都会变化 |
| `graph_thread_id` | LangGraph checkpoint 隔离键 | 当前为 `conversation_id:topic_id` |

排查单次执行优先使用 `request_id`；排查多轮澄清优先使用 `topic_id`。

## 四、公共日志字段

| 字段 | 说明 |
|---|---|
| `timestamp` | 带时区的 ISO 8601 时间 |
| `level` | `INFO/WARNING/ERROR` |
| `event` | 稳定的事件名称 |
| `node` | 当前节点或路由器名称 |
| `duration_ms` 或 `ms` | 执行耗时，单位毫秒 |
| `topic_status` | 当前 Topic 生命周期状态 |
| `route` 或 `decision` | Planner/Router 的最终路由 |
| `error_id` | 返回给用户的错误编号 |
| `error_code` | 稳定错误类别 |
| `error_type` | Python 异常类型 |
| `error_message` | 服务端异常摘要，不返回前端 |
| `stack_trace` | 完整异常堆栈，仅保存在服务端日志 |
| `seq` | 请求内事件序号，trace 渲染排序依据 |
| `trace_id` | 链路追踪 ID，通常等于 `request_id` |
| `span_id` | 当前事件所属 span（请求或节点） |
| `parent_span_id` | 父 span，用于还原树形调用链 |

不要依赖日志字段出现顺序，应该按 JSON 字段名读取。

## 五、事件类型

### 5.1 请求事件

| 事件 | 含义 |
|---|---|
| `request.started` | Web 已接收并开始处理请求 |
| `request.completed` | 请求正常完成，包含最终路由、状态和总耗时 |
| `request.failed` | 核心请求失败，包含 `error_id` 和完整堆栈 |
| `request.user_input` | CLI 模式记录的用户输入摘要 |

正常请求应该至少形成：

```text
request.started
→ node.started/node.completed
→ route.decided
→ state.changed
→ request.completed
```

失败请求应该形成：

```text
request.started
→ node.failed
→ state.changed(current=failed)
→ request.failed(error_id=...)
```

### 5.2 节点事件

| 事件 | 含义 |
|---|---|
| `node.started` | 节点开始执行 |
| `node.completed` | 节点正常完成 |
| `node.failed` | 核心节点失败，异常会继续向请求边界传播 |
| `node.degraded` | 附加能力失败但主流程继续，例如 Evaluator 入库失败 |
| `node.event` | 节点过程信息，例如歧义拦截与重试提示 |
| `node.detail` | 补充分析信息，例如有效需求和候选字段，已携带 `node` 归属 |
| `tools.called` | Advisor 本轮实际调用的工具列表 |
| `example.retrieved` | 历史示例检索结果，含 `hit_count/top_sim/top_question` |
| `plan.locked` | 最终锁定方案，含 `table/measures/dimensions/order_by` |
| `advisor.mode` | Advisor 本轮运行模式与 Planner 模糊度 |

`node.detail` 已由 Planner 传入 `node="planner"`，trace 渲染时会自动归属到对应节点 span 下。

### 5.3 路由与状态事件

| 事件 | 含义 |
|---|---|
| `route.decided` | Planner Router 或 SQL Router 选择了后续分支 |
| `state.changed` | 关键 State 字段发生真实变化 |

`topic_status` 的典型转换：

```text
new
→ clarifying
→ confirmed
→ generating_sql
→ validating_sql
→ executing
→ completed
```

异常时可能从任意非终态进入 `failed`。

## 六、常用查询命令（Python）

以下命令均在项目根目录执行，推荐优先使用 `trace_view` 工具（见第十二节），按请求渲染树形调用链，无需手工过滤 JSON。

### 6.1 查看最后 20 行原始日志

```bash
python agentTest/scripts/trace_view.py tail --lines 20
```

### 6.2 查看最近的请求

```bash
python agentTest/scripts/trace_view.py list
```

### 6.3 根据 request_id 还原单次请求

```bash
python agentTest/scripts/trace_view.py show <request_id前缀>
```

建议按以下顺序阅读：

1. `request.started`
2. Planner 的 `node.completed`
3. `planner_router` 的 `route.decided`
4. Advisor 或 Seeker 的节点日志
5. `state.changed`
6. `request.completed/request.failed`

### 6.4 根据 topic_id 查看多轮澄清

```bash
python agentTest/scripts/trace_view.py filter --topic <topic_id>
```

同一个 `topic_id` 下出现多个不同 `request_id` 是正常现象，表示用户在同一个问数任务中进行了多轮补充、选择或确认。

### 6.5 根据 error_id 定位完整异常

```bash
python agentTest/scripts/trace_view.py filter --error <error_id> --full
```

客服或业务用户只需要提供 `error_id`，不要要求用户复制内部异常文本。

### 6.6 查看所有 Topic 状态变化

```bash
python agentTest/scripts/trace_view.py filter --event state.changed
```

### 6.7 查看 Planner 和 SQL 路由

```bash
python agentTest/scripts/trace_view.py filter --event route.decided
```

### 6.8 查看非阻断降级

```bash
python agentTest/scripts/trace_view.py filter --event node.degraded
```

出现 `node.degraded` 不代表查询一定失败。例如 Evaluator 入库失败时，用户仍可能已经获得正确答案。

### 6.9 查看最慢节点

```bash
python agentTest/scripts/trace_view.py nodeslow --top 20
```

## 七、典型问题排查

### 7.1 用户已经确认，为什么系统仍然追问

按同一 `topic_id` 依次检查：

1. 是否出现 `metric_ambiguity.detected` 和 `metric_resolution.user_required`，确认首轮候选已生成。
2. 下一轮是否出现 `metric_resolution.completed`，并检查 `field/source` 是否为用户选择。
3. Advisor 的 `node.completed` 是否为 `locked=True`。
4. 是否出现 `plan.locked`。
5. Planner 日志中 `accept_locked_plan` 是否为 `True`。
6. Planner Router 是否为 `decision=seeker`。
7. `plan_status` 是否为 `confirmed`。

如果用户已经回复“第二个”，但后续仍出现同一 `metric_resolution.user_required`，应检查 `AnalysisSpec.pending_clarifications` 是否在首轮写入、planner 日志“用户选择校验: 命中 ...”是否出现（模型 `user_selection` + 程序 `validate_user_selection` 白名单校验）、是否生成 `explicit_user` resolved 记录，以及 Advisor 是否使用更新后的 AnalysisSpec。

如果 Advisor 文本声称方案完整，但日志为 `locked=False`，说明只是 LLM 文本表达，程序并没有形成可确认方案。

### 7.2 请求失败但前端只显示错误编号

这是预期行为。使用错误编号执行：

```bash
python agentTest/scripts/trace_view.py filter --error "错误编号" --full
```

重点查看：

- 最后一个 `node.started`
- 是否有对应的 `node.failed`
- `error_type`
- `error_message`
- `stack_trace`
- checkpoint 是否记录 `topic_status=failed`

### 7.3 Advisor 为什么没有提交方案

检查 Advisor 事件：

```bash
python agentTest/scripts/trace_view.py filter --node advisor_agent --request <request_id前缀>
```

常见结果：

- `advisor.mode=adaptive`：Advisor 根据当前元数据和门禁状态决定继续追问或提交方案。
- `advisor.mode=plan`：需求已经完整，应在核验字段后提交方案。
- `本轮工具调用: [无]`：模型没有调用任何工具。
- `locked=False`：没有形成程序认可的 locked 方案。
- `locked=True`：方案已锁定，下一轮可以由 Planner 处理最终确认。

### 7.4 SQL 为什么被重新生成

检查：

```bash
# 渲染完整链路，检查 SQL 生成与修复过程
python agentTest/scripts/trace_view.py show <request_id前缀>

# 只看 SQL 校验结果
python agentTest/scripts/trace_view.py filter --request <request_id前缀> --node validate_sql
```

典型链路：

```text
validate_sql(valid=False)
→ sql_router(decision=fix)
→ prepare_sql_fix
→ generate_sql(retry=1)
```

## 八、日志使用原则

### 8.1 不记录完整敏感数据

- 不打印 API Key、数据库密码和 Token。
- 不打印完整查询结果。
- SQL、用户问题和模型输出需要限制长度。
- State 中只保存安全错误编号，不保存完整异常堆栈。

### 8.2 不把日志当业务判断依据

业务路由必须由 Graph State、QueryPlan 和领域校验决定。日志只能用于观测和诊断，不能通过“日志里出现某个字符串”驱动业务流程。

### 8.3 不仅看 LLM 文本

排查方案确认问题时，应优先查看：

```text
locked
plan_status
route.decided
topic_status
```

LLM 回复中出现“已确认”“方案完整”等文字，不代表程序状态真的已经变化。

## 九、当前边界

- 当前日志文件适用于单进程或单实例本地部署。
- 多进程 Gunicorn 或多实例部署时，不建议多个进程共同滚动同一个本地文件；应输出 JSON 到标准输出，再交给集中式日志系统采集。
- 当前尚未接入 Prometheus、Grafana、OpenTelemetry 或 ELK。
- 当前日志查询使用 `trace_view` 只读脚本，后续可以增加只读 Debug 接口。
- `MemorySaver` 和内存 Session 重启后会丢失，日志只能还原执行过程，不能替代持久化 checkpoint。

## 十、面试表达

项目最初只有按节点打印的文本日志，并发请求无法串联。我使用 `ContextVar` 自动注入 Conversation、Topic、Request 和 Graph Thread 四个身份字段，把日志改为 JSON Lines 和按天滚动，并定义请求、节点、路由、状态变化、失败和降级事件。核心异常在统一请求边界生成 `error_id` 和完整堆栈，前端只展示安全提示；Evaluator 等非核心能力使用 `node.degraded`，不会影响已经成功的查询结果。实际排查时可以通过一个 `request_id` 还原完整节点链路，也可以通过 `topic_id` 还原多轮澄清过程。

## 十一、多表过滤排查案例

### 11.1 典型现象

日志中的 SQL 使用了正确复合 Join 键，但只包含事实表：

```sql
WHERE fact.pt_dt = yesterday_expression
```

维表没有 `dim.pt_dt`，导致维表历史快照重复参与 Join，聚合结果膨胀。

### 11.2 排查顺序

1. 查 Advisor `locked_plan` 日志，确认 `table_plans` 是否覆盖所有表。
2. 查 `retrieve_schema` 的覆盖分析，确认字段来源和参与表。
3. 查 `generate_sql` 的最终 SQL，逐表搜索必选过滤字段。
4. 查是否出现 `逐表过滤自动修复` 事件。
5. 查 `validate_sql` 是否因缺少全局必选过滤而进入 fix 分支。
6. 对比 Hive 执行耗时和结果行，确认修复后不存在历史分区放大。

### 11.3 当前关键日志

- `plan.locked` 事件的 `table_plans` 字段
- `覆盖分析: 单表=False, 涉及表=..., 字段来源=...`
- `Join 路径已规划: edges=..., grain=...`
- `逐表过滤自动修复: 表 ... 缺少全局必选过滤条件 ...`
- `validate_sql` 的 `sql_error`

### 11.4 判断标准

当 `REQUIRED_FILTER_FIELDS_FOR_ALL_TABLES=["pt_dt"]` 时，每张表必须在 ON 或 WHERE 中拥有独立 `alias.pt_dt` 常量/函数过滤。`fact.pt_dt = dim.pt_dt` 不满足要求，因为它不能保证 Hive 对两张表分别进行分区裁剪。

## 十二、trace_view 树形查看工具

`agentTest/scripts/trace_view.py` 读取 `langgraph_app.jsonl`，按 `request_id` 还原一次请求的树形调用链，无需手工过滤 JSON。

### 常用命令

```bash
# 列出最近 20 个请求（耗时、结果、节点数）
python agentTest/scripts/trace_view.py list

# 渲染单个请求的树形 trace（支持 request_id 前缀）
python agentTest/scripts/trace_view.py show <request_id前缀>

# 查看完整字段，不截断长文本
python agentTest/scripts/trace_view.py show <request_id前缀> --full

# 按请求总耗时排行，快速定位慢请求
python agentTest/scripts/trace_view.py slow --top 10

# 按事件/节点/关键词过滤
python agentTest/scripts/trace_view.py filter --event plan.locked
python agentTest/scripts/trace_view.py filter --node advisor_agent --keyword new_order

# 读取指定日期的滚动日志
python agentTest/scripts/trace_view.py show <request_id前缀> --date 2026-08-05
```

### 树形输出示例

```text
==== trace 4fd4e5d9…  2026-08-05T15:49:51  [14.8s]  result=query
└─ request [14800.0ms] result_type=query
   ├─ planner [5466.0ms] route=advisor completeness=partial
   │  ├─ example.retrieved hit_count=2 top_sim=0.80
   │  └─ node.detail message=有效需求: ...
   ├─ route.decided decision=advisor
   └─ advisor_agent [8868.0ms] locked=True retries=0
      ├─ advisor.mode mode=adaptive completeness=partial
      ├─ tools.called tools=["search_columns", "submit_query_plan"]
      ├─ metric_ambiguity.detected mention=新增订单 candidate_count=4
      └─ plan.locked table=ads_trip.xxx measures=["new_order"] dimensions=[...]
```

### 归属规则

- 节点事件由 `span_id/parent_span_id` 构成父子层级，`request` 为根。
- `node.detail` 等 leaf 事件即使写在节点结束后，也会按 `node` 字段自动归属到同名节点 span 下。
- 旧格式日志（无 span 字段）仍可查看，事件会平铺展示。
## 十三、指标循环确认与连续问答排查

### 13.1 当前指标确认事件链

正常的多候选确认应看到：

```text
metric_ambiguity.detected
  ↓
metric_resolution.user_required
  ↓ 用户回复编号/字段名/中文含义
metric_resolution.completed(source=explicit_user)
  ↓
plan.locked
```

排查重点：

- 第一轮 `metric_resolution.user_required` 必须包含固定 `clarification_options`。
- 用户选择后的 `metric_resolution.completed.field` 必须与上一轮 option 对应。
- Advisor 的 `node.end.answer_summary` 应是最终展示文本，不能再用 LLM 原始草稿判断实际回复。
- 如果 resolved 后 LLM 漏传 `concept_resolutions`，仍应通过 previous resolution 放行。
- 候选重新排序后，已确认字段仍应保持 resolved。

### 13.2 典型循环确认判断

| 现象 | 可能原因 | 检查位置 |
|---|---|---|
| 首轮展示了候选，下一轮无法识别“第二个” | 候选只生成文本，没有写入 pending，或模型 `user_selection` 未命中/校验失败 | `analysis_spec.pending_clarifications` + planner 日志“用户选择校验” |
| Planner 已还原字段，Advisor 仍追问 | Planner 重建 AnalysisSpec 时保留了旧 ambiguous | `metric_resolutions.status/source` |
| LLM 未传解析参数后再次追问 | 门禁只依赖 `concept_resolutions` | previous resolutions 是否参与 Validator |
| 已确认字段因重新检索消失 | resolved 只校验本轮 candidates | 上轮 resolution.candidates 是否纳入合法字段 |
| 日志显示“好，开始查询”但用户看到候选 | 记录了 LLM 草稿而非 final_answer | `node.end.answer_summary` 写入时机 |

### 13.4 延迟编号排查方式

用户隔数轮回复“第二个”时，应按同一 `topic_id` 检查：

1. 最早的 `metric_resolution.user_required` 对应 pending 是否仍为 open（`pending_clarifications.status`）。
2. 中间解释或条件修改是否错误关闭 pending。
3. 本轮是否只有一个 open pending。
4. `metric_resolution.completed` 是否引用原始 `clarification_id`，而不是重新生成的候选。
5. 如果有多个 pending，是否安全追问而不是猜测（当前一次只澄清一个问题）。
6. 新 Topic 是否完全看不到旧 Topic 的 clarification 和 result snapshot。
