# 日志使用与问题排查指南

> 最后更新：2026-10-08
> 适用范围：Web 请求、飞书机器人、LangGraph 父图、Planner 单 Agent 工具循环  
> [返回文档索引](../文档索引.md)

> **架构说明**：当前是单 Agent 架构——父图只有 `capture_user_message` 与 `planner` 两个节点，查数由 Planner 在 ReAct 循环内调用 `execute_query` 工具完成，执行链在工具内部同步执行。
> 因此日志里**不会**出现 Advisor / Seeker / Evaluator 的节点事件：口径澄清由 Planner 直接输出文案，执行在工具内部完成，用户评分在 Web 层落库。
> **LLM token 统计**：`llm.response` 的 `tokens` 含 `cache_hit/cache_miss`；`request.completed` 的 `summary.llm_tokens` 为请求级汇总。
> **skill 渐进式披露**：每轮只披露技能 name+description 索引，由 LLM 自主调 `read_skill` 读取正文。

> **2026-09-16 变更**：
> - **多数据源执行审计**：`execute_sql` 节点的 `node.completed` 新增 `engine` 字段（trino/doris/hive），可查看每次查询实际命中的引擎；引擎降级过程有 `node.event`（尝试引擎 X 执行查询）可查。
> - **Trino 404 自动重试日志**：Trino 多 coordinator 非粘滞路由偶发 404，数据源层自动重试（最多 2 次、间隔 0.5s）并直接写 `trino.retry` / `trino.retry_success` 事件，用于统计 404 触发频率与恢复情况（见 5.6 / 6.14）。

## 一、日志能解决什么问题

本项目的结构化日志用于回答以下问题：

1. 一次请求经过了哪些节点？
2. Planner 为什么路由到 execute（执行链）或 respond（输出文本）？
3. `topic_status` 在哪个节点发生了变化？
4. 同一个 Topic 的多轮澄清是否属于同一任务？
5. Planner 是否调用了 `execute_query`，并拿到真实数据结果？
6. 请求失败时，完整异常堆栈和对应的 `error_id` 是什么？
7. Evaluator、Intent Classifier 等附加能力是否发生了非阻断降级？

日志不是 Graph State 的替代品：

- Graph State 保存当前业务事实和 checkpoint。
- 日志保存执行过程、路由依据、耗时和异常证据。

## 二、日志文件位置与保留策略

当前结构化日志文件：

```text
agentTest/logs/langgraph_app.jsonl
```

每一行都是一个独立 JSON 对象，称为 JSON Lines 或 JSONL。

日志使用 `TimedRotatingFileHandler` 按天滚动：

```text
langgraph_app.jsonl
langgraph_app.jsonl.2026-07-31
langgraph_app.jsonl.2026-08-01
```

默认保留最近 14 天，服务重启不会清空历史日志。

旧文件 `agentTest/logs/langgraph_app.log` 是结构化改造前的文本日志，不再作为当前排查依据，可以保留用于历史对比。

修改日志代码后必须重启 Web 服务，旧进程不会自动加载新代码。

## 三、四个身份字段

每条请求链路主要通过以下字段关联：

| 字段                | 含义                       | 生命周期                           |
| ----------------- | ------------------------ | ------------------------------ |
| `conversation_id` | 前端左侧的完整对话                | 一个对话期间不变                       |
| `topic_id`        | 对话级固定标识（去 Topic 化）         | 整个对话期间不变                        |
| `request_id`      | 一次 HTTP 请求或一次图调用         | 用户每发送一次消息都会变化                  |
| `graph_thread_id` | LangGraph checkpoint 隔离键 | 当前为 `conversation_id`（整对话共享）  |

排查单次执行优先使用 `request_id`；排查跨问数多轮对话按 `conversation_id`（或 `graph_thread_id`）过滤。

## 四、公共日志字段

| 字段                   | 说明                        |
| -------------------- | ------------------------- |
| `timestamp`          | 带时区的 ISO 8601 时间          |
| `level`              | `INFO/WARNING/ERROR`      |
| `event`              | 稳定的事件名称                   |
| `node`               | 当前节点或路由器名称                |
| `duration_ms` 或 `ms` | 执行耗时，单位毫秒                 |
| `topic_status`       | 当轮请求推进阶段（去 Topic 化后仅作阶段标识） |
| `route` 或 `decision` | Planner/Router 的最终路由      |
| `error_id`           | 返回给用户的错误编号                |
| `error_code`         | 稳定错误类别                    |
| `error_type`         | Python 异常类型               |
| `error_message`      | 服务端异常摘要，不返回前端             |
| `stack_trace`        | 完整异常堆栈，仅保存在服务端日志          |
| `seq`                | 请求内事件序号，trace 渲染排序依据      |
| `trace_id`           | 链路追踪 ID，通常等于 `request_id` |
| `span_id`            | 当前事件所属 span（请求或节点）        |
| `parent_span_id`     | 父 span，用于还原树形调用链          |

不要依赖日志字段出现顺序，应该按 JSON 字段名读取。

## 五、事件类型

### 5.1 请求事件

| 事件                   | 含义                         |
| -------------------- | -------------------------- |
| `request.started`    | Web 已接收并开始处理请求             |
| `request.completed`  | 请求正常完成，包含最终路由、状态和总耗时；`summary.llm_tokens` 为该请求 LLM token 汇总（输入/输出/缓存命中/未命中） |
| `request.failed`     | 核心请求失败，包含 `error_id` 和完整堆栈 |
| `request.user_input` | CLI 模式记录的用户输入摘要            |

正常请求应该至少形成：

```text
request.started
→ node.started/node.completed
→ tools.called
→ state.changed
→ request.completed
```

失败请求应该形成：

```text
request.started
→ node.failed
→ state.changed(current=failed)
→ request.failed(error_id=...)
```

### 5.2 节点事件

| 事件                  | 含义                                            |
| ------------------- | --------------------------------------------- |
| `node.started`      | 节点开始执行                                        |
| `node.completed`    | 节点正常完成                                        |
| `node.failed`       | 核心节点失败，异常会继续向请求边界传播                           |
| `node.degraded`     | 附加能力失败但主流程继续，例如 Evaluator 入库失败                |
| `node.event`        | 节点过程信息，例如歧义拦截与重试提示                            |
| `node.detail`       | 补充分析信息，例如有效需求和候选字段，已携带 `node` 归属              |
| `tools.called`      | Planner / 执行链本轮实际调用的工具列表                |
| `skill.matched`     | skill 渐进式披露：本次披露了哪些技能（`mode=progressive_disclosure`） |
| `example.retrieved` | 历史示例检索结果，含 `hit_count/top_sim/top_question`   |

`node.detail` 已由 Planner 传入 `node="planner"`，trace 渲染时会自动归属到对应节点 span 下。

### 5.3 状态事件

| 事件              | 含义                     |
| --------------- | ---------------------- |
| `state.changed` | 关键 State 字段发生真实变化      |

`topic_status` 的典型转换：

```text
new
→ clarifying
→ confirmed
→ generating_sql
→ validating_sql
→ executing
→ completed
```

异常时可能从任意非终态进入 `failed`。

### 5.4 LLM 调用事件

| 事件             | 含义                                                       |
| -------------- | -------------------------------------------------------- |
| `llm.call`     | 一次 LLM 调用开始，含 `model/call_id/prompt`                     |
| `llm.response` | 对应调用返回，含 `output/ms/tokens`，与 `llm.call` 通过 `call_id` 配对 |
| `llm.error`    | 对应调用失败，含 `error_message/ms`                              |

`prompt` 字段默认不截断（`LOG_LLM_MAX_LENGTH=0`），记录除系统提示词外的全部消息（human/ai/tool），ReAct 每步的工具调用与工具结果都会体现在输入中。

`llm.response` 的 `tokens` 字段包含每次调用的 token 明细：

| 字段 | 含义 |
|---|---|
| `prompt_tokens` | 本次调用的输入 token 数 |
| `completion_tokens` | 本次调用的输出 token 数 |
| `total_tokens` | 输入 + 输出 |
| `cache_hit` | 缓存命中 token 数（`prompt_tokens_details.cached_tokens`，前缀缓存命中） |
| `cache_miss` | 缓存未命中 token 数（输入 − 命中） |

请求级汇总见 `request.completed` 的 `summary.llm_tokens`（同请求内所有 LLM 调用累加），前端消息气泡同步展示为「输入总token | 输出总token | 缓存命中 | 缓存未命中」。

### 5.5 指标与检索事件

语义层命中与 RAG 召回**不单独打事件**，通过「工具调用 + 模型输入输出」判断一次请求实际走了哪条路径：

| 观察点 | 说明 |
|---|---|
| `tools.called` | Planner 本轮调用了哪些工具。出现 `grep_semantic` / `read_metric` → 走了语义层；出现 `search_tables` / `search_columns` → 触发 RAG 兜底；出现 `execute_query` → 已实际执行 SQL |
| `llm.call` 的 `prompt` | Planner 实际看到的上下文：对话历史、工具返回的候选指标与口径 |
| `llm.response` 的 `output` | Planner 的决策结果：选了哪个指标、SQL 怎么写、怎么回答 |
| `skill.matched` | 本次披露了哪些技能 |
| `node.completed`（planner） | 本轮 `route` 与耗时 |

判断规则：

- 只有 `grep_semantic` / `read_metric`，没有 `search_*` → 语义层路径；
- 出现 `search_*` → 触发了 RAG 兜底（`ENABLE_RAG=false` 时这些工具返回空结果）；
- 出现 `execute_query` → 已真正查库，引擎与行数在 `llm.response` 的工具结果与落盘元数据里。

### 5.6 数据源执行与重试事件

多数据源（Trino / Doris / Hive）的执行信息挂在 `execute_sql` 节点上；Trino 偶发 404 的自动重试由数据源层直接写日志：

| 事件                  | 含义                                                         | 关键字段                                          |
| ------------------- | ---------------------------------------------------------- | --------------------------------------------- |
| `node.completed`    | `execute_sql` 节点正常完成，`engine` 标明本次实际命中的查询引擎        | `node_name=execute_sql`、`engine=trino/doris/hive`、`rows/ms` |
| `node.event`        | `execute_sql` 尝试每个候选引擎时各打一条，内容为 `尝试引擎 X 执行查询`    | `message`                                      |
| `trino.retry`       | Trino 偶发 404（多 coordinator 非粘滞路由）自动重试前记录          | `attempt/retry_count/elapsed_ms/error/sql`      |
| `trino.retry_success` | Trino 404 重试后成功恢复                                       | `attempt/retry_count/elapsed_ms/sql`            |

`trino.retry` / `trino.retry_success` 由 `TrinoDataSource` 用标准 logging 直接写入同一 jsonl，**不带 `request_id`**，用于全局统计 404 触发频率与恢复情况；要关联到具体请求，请用 `execute_sql` 节点的 `node.completed(engine=...)`。

## 六、常用查询命令（Python）

以下命令均在项目根目录执行，推荐优先使用 `trace_view` 工具（见第十二节），按请求渲染树形调用链，无需手工过滤 JSON。

### 6.1 查看最后 20 行原始日志

```bash
python agentTest/scripts/trace_view.py tail --lines 20
```

### 6.2 查看最近的请求

```bash
python agentTest/scripts/trace_view.py list
```

### 6.3 根据 request_id 还原单次请求

```bash
python agentTest/scripts/trace_view.py show <request_id前缀>
```

输出整体架构如下：**每一行末尾的 `category=...`** 是事件类型，用来快速过滤：`lifecycle`（阶段/状态）、`llm`（模型调用）、`search`（检索）、`metric`（指标歧义）、`plan`（方案）、`state`（状态）。

```yaml
==== trace <请求ID>  <时间>  [总耗时]  result=结果类型 ====
├─ request [总耗时] ...        ← 树的根：整个请求
│  ├─ planner [耗时] ...       ← 一级节点：Planner 阶段
│  │  ├─ llm.call ...          ← 二级：Planner 里的 LLM 调用
│  │  ├─ tools.called ...      ← 二级：Planner 调用的工具
│  │  └─ ...
│  └─ tools.called ...         ← 一级节点：Planner 调用的工具（execute_query / grep_semantic 等）
│     ├─ tools.called ...      ← 二级：调用了哪些工具
│     └─ ...
state.snapshot ...             ← 树外：结束时的状态快照
```

### 6.4 根据 conversation_id 查看多轮澄清

```bash
python agentTest/scripts/trace_view.py filter --conversation <conversation_id>
```

同一个 `conversation_id` 下出现多个不同 `request_id` 是正常现象，表示用户在同一对话中进行了多轮补充、选择、确认或新问数（去 Topic 化后共享同一 Checkpoint）。

### 6.5 根据 error_id 定位完整异常

```bash
python agentTest/scripts/trace_view.py filter --error <error_id> --full
```

客服或业务用户只需要提供 `error_id`，不要要求用户复制内部异常文本。

### 6.6 查看所有 Topic 状态变化

```bash
python agentTest/scripts/trace_view.py filter --event state.changed
```

### 6.7 查看 Planner 和 SQL 路由

```bash
python agentTest/scripts/trace_view.py filter --event tools.called
```

### 6.8 查看非阻断降级

```bash
python agentTest/scripts/trace_view.py filter --event node.degraded
```

出现 `node.degraded` 不代表查询一定失败。例如 Evaluator 入库失败时，用户仍可能已经获得正确答案。

### 6.9 查看最慢节点

```bash
python agentTest/scripts/trace_view.py nodeslow --top 20
```

### 6.10 查看 LLM 输入与输出

```bash
python agentTest/scripts/trace_view.py prompt <request_id前缀> [--caller planner] [--full]
```

展示规则：

- 按时间戳顺序用 `call_id` 配对 `llm.call` 与 `llm.response`，呈现「调用→输出→调用→输出」，输入和输出不会分开聚在末尾。
- 同一调用方连续调用时，首次显示完整输入；后续输入与上次完全相同则显示「与上次调用相同，省略」；是上次输入的扩展（如 ReAct 追加工具调用/工具结果）则只显示新增部分。
- `--caller` 只显示指定调用方（如 planner / generate_sql）；`--full` 不截断长文本。
- 旧日志（无 `call_id`）自动降级为按顺序平铺展示。

### 6.11 查看请求级摘要

```bash
python agentTest/scripts/trace_view.py summary <request_id前缀>
```

输出输入原文、结果类型、总耗时、节点数、LLM 调用数、事件分布与节点分布，快速判断一次请求的整体走向。

`summary` 会额外打印一行请求级 token 汇总：

```text
Token: 输入总token 35396 | 输出总token 2733 | 缓存命中 17408 | 缓存未命中 17988
```

查看每次 LLM 调用的 token 明细（含缓存命中/未命中）：

```bash
python agentTest/scripts/trace_view.py filter --event llm.response --request <request_id前缀> --full
```

### 6.12 查看语义层命中与 RAG 召回

排查一次查询"走了语义层还是召回、命中什么"，看工具调用与模型输入输出：

```bash
# Planner 本轮调用了哪些工具（grep_semantic / read_metric / search_* / execute_query）
python agentTest/scripts/trace_view.py filter --event tools.called --request <request_id前缀> --full

# Planner 的输入与输出（能看到命中的指标名、口径与最终 SQL）
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner
```

确认 Planner 输入到底注入了什么（语义层候选 / 维度枚举值）：

```bash
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner --full
```

### 6.13 查看 0 行自愈链路（探查看不出数据→修正重跑）

查询执行 0 行时，系统会回 Planner 并注入【上次执行 0 行反馈】。用 trace_view 还原整条自愈链路：

```bash
python agentTest/scripts/trace_view.py show <request_id前缀>
```

判断标准：

```text
execute_sql(0 行)
→ persist_result(empty_self_heal)      # 0 行自愈标记，落盘后回 Planner
→ planner(收到【上次执行 0 行反馈】)
   ├─ tools.called=["probe_values"]     # Planner 探查实际存储值（正确路径）
   │    → 修正 filters 后 route=execute 重跑
   └─ route=respond + final_answer      # 确认确属无数据，直接告知用户
```

- 若 0 行反馈后 planner 直接 `route=respond` 且询问用户"实际存储值是什么"，说明把「事实问题」当成了「口径问题」，
  属路由偏差（事实问题查库可解，应 probe_values 探查或 route=respond 告知）。
- planner 维度软失败可查 `state.snapshot` 中 `planner_entities.unresolved_dimensions`：
  未命中语义层实体的维度词会在此记录，供区分「故意跳过」还是「语义层缺实体」。

### 6.14 查看查询引擎与 Trino 404 重试

本次查询实际走了哪个引擎，看 `execute_sql` 节点的 `node.completed` 的 `engine` 字段：

```bash
# 单次请求：树形 trace 中 execute_sql 节点行带 engine=...
python agentTest/scripts/trace_view.py show <request_id前缀>

# 只看 execute_sql 的完成事件
python agentTest/scripts/trace_view.py filter --event node.completed --keyword execute_sql --request <request_id前缀> --full
```

实际引擎取值：`trino`（默认首选）/ `doris`（data_project 专属）/ `hive`（Trino 失败后的兜底）。若同一请求内出现多条 `node.event`（尝试引擎 X 执行查询），表示发生了引擎降级。

Trino 偶发 404（多 coordinator 负载均衡非粘滞路由：POST 建查询成功但 GET 状态被路由到其他节点）由数据源自动重试（最多 2 次、间隔 0.5s），重试日志直接落在 jsonl：

```bash
# 统计 404 触发频率（全局，不区分请求）
python agentTest/scripts/trace_view.py filter --event trino.retry --limit 50 --full

# 统计重试后恢复成功的次数
python agentTest/scripts/trace_view.py filter --event trino.retry_success --limit 50 --full
```

`trino.retry` 字段含义：`attempt`（第几次尝试）、`retry_count`（累计重试次数）、`elapsed_ms`（从查询开始到重试的耗时）、`error`（404 错误）、`sql`（截断前 200 字符）。连续 3 次仍 404 时抛错并降级 Hive（走 `node.failed` + 汇总错误）。

## 七、典型问题排查

### 7.1 用户已经确认，为什么系统仍然追问

按同一 `topic_id` 依次检查：

1. 本轮 `llm.response` 的 `output` 是否为澄清文案，以及澄清里给出的候选是否与上一轮一致。
2. 下一轮 `llm.call` 的 `prompt` 是否包含上一轮问答（历史缺失会导致重复追问）。
3. 下一轮 `tools.called` 是否出现过 `execute_query`：出现说明已真正查库。
4. 若一直只有 `grep_semantic` 没有 `execute_query`，说明口径仍未确认，属预期澄清行为。

如果用户已经回复了选项编号，但系统仍在重复追问同一件事，优先检查 Planner 本轮是否读到了完整对话历史，再检查候选口径是否在两轮之间发生了变化。

### 7.2 请求失败但前端只显示错误编号

这是预期行为。使用错误编号执行：

```bash
python agentTest/scripts/trace_view.py filter --error "错误编号" --full
```

重点查看：

- 最后一个 `node.started`
- 是否有对应的 `node.failed`
- `error_type`
- `error_message`
- `stack_trace`
- checkpoint 是否记录 `topic_status=failed`

### 7.3 Planner 为什么没有形成可执行方案

方案由 Planner 在工具循环内构建。检查 Planner 的工具调用与最终输出：

```bash
python agentTest/scripts/trace_view.py show <request_id前缀>
python agentTest/scripts/trace_view.py filter --event tools.called --request <request_id前缀>
```

常见结果：

- 输出澄清文案：Planner 认为需求不完整或口径有歧义，直接向用户提问（预期行为）。
- 调用了 `grep_semantic` 但没有 `execute_query`：语义层未命中或口径未确认，Planner 选择先澄清。
- 调用了 `execute_query`：已实际执行 SQL，结果落盘后由 Planner 撰写回答。
- `execute_query` 返回校验错误：Planner 应改写 SQL 重试；若直接答复用户，需检查工具返回信息是否被正确读取。

### 7.4 SQL 为什么被重新生成

检查：

```bash
# 渲染完整链路，检查 SQL 生成与修正过程
python agentTest/scripts/trace_view.py show <request_id前缀>

# 看 Planner 拿到的工具返回（含校验失败原因）
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner
```

典型链路：

```text
llm.response → 生成 SQL → execute_query 校验失败（返回具体原因）
→ 结果回填上下文 → Planner 改写 SQL → execute_query 重试
```

### 7.5 查询 0 行后为什么要询问用户（事实 vs 口径）

现象：SQL 执行成功但 0 行，系统没有探查，反而向用户确认"实际存储值是什么"。

排查顺序：

1. `trace_view show <request_id前缀>`：确认首轮 filters 是否与用户表述一致（如用户说"徐州大区"但 filters 写成 `region_name='徐州'`）。
2. 确认 0 行反馈后 Planner 的 route：
   - 正确：planner 调 `probe_values` 修正 filters 后 `route=execute` 重跑，或 `route=respond` 直接告知；
   - 偏差：planner 直接 `route=respond` 向用户询问过滤值（把「事实问题」当「口径问题」）。
3. 判断标准：过滤值与实际存储值不匹配属「事实问题」（查库可解），不应问用户；多候选口径选择才属「口径问题」，才应由 Planner 澄清。

关键日志：

```bash
# 0 行反馈注入（planner llm.call 的 prompt 含【上次执行 0 行反馈】）
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner --full

# 探查已执行
python agentTest/scripts/trace_view.py filter --event tools.called --request <request_id前缀>
```

### 7.6 子口径型指标（dimensional_measures）查询失败

现象：多指标查询中某一段报"语义层方案构建失败"，其余段正常；或单查子口径型指标（如"激活换电柜数"）反复失败。

排查顺序：

1. `trace_view show <request_id前缀>`：确认该段返回的 SQL 与报错信息。
2. 查看该次查询脚本元数据（`query_results/<日期>/<conversation_id>/<request_id>_p1_script.json`），核对失败 step 的 SQL 与过滤条件。
3. 若 `read_metric` 返回的子口径与 SQL 里写死的物理字段不一致，即为本问题。

关键日志：

```bash
python agentTest/scripts/trace_view.py show <request_id前缀>
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner
```

修复/约定：

- `execute_query` 的 `dimension` 参数应传与用户问法一致的**中文子口径名**（如"激活电柜"），不是物理字段名；
- `search_semantic` 返回的可选子口径只列中文名，模型拿不准时先 `search_columns` 确认口径名再执行；
- 正常结果示例：`SELECT SUM(active_cabinet_num) ... WHERE pt_dt='20260917'`（激活电柜数 = 25,964 台）。

## 八、日志使用原则

### 8.1 不记录完整敏感数据

- 不打印 API Key、数据库密码和 Token。
- 不打印完整查询结果。
- SQL、用户问题和模型输出需要限制长度。
- State 中只保存安全错误编号，不保存完整异常堆栈。

### 8.2 不把日志当业务判断依据

业务路由必须由 Graph State、QueryPlan 和领域校验决定。日志只能用于观测和诊断，不能通过“日志里出现某个字符串”驱动业务流程。

### 8.3 不仅看 LLM 文本

排查方案确认问题时，应优先查看：

```text
node.completed(planner).route
topic_status
tools.called
```

LLM 回复中出现“已确认”“方案完整”等文字，不代表程序状态真的已经变化。

## 九、当前边界

- 当前日志文件适用于单进程或单实例本地部署。
- 多进程 Gunicorn 或多实例部署时，不建议多个进程共同滚动同一个本地文件；应输出 JSON 到标准输出，再交给集中式日志系统采集。
- 当前尚未接入 Prometheus、Grafana、OpenTelemetry 或 ELK。
- 当前日志查询使用 `trace_view` 只读脚本，后续可以增加只读 Debug 接口。
- `MemorySaver` 和内存 Session 重启后会丢失，日志只能还原执行过程，不能替代持久化 checkpoint。

## 十、设计小结

日志最初只有按节点打印的文本，并发请求无法串联。现在使用 `ContextVar` 自动注入 Conversation、Topic、Request 和 Graph Thread 四个身份字段，日志统一为 JSON Lines 并按天滚动，同时定义请求、节点、路由、状态变化、失败和降级事件。核心异常在统一请求边界生成 `error_id` 和完整堆栈，前端只展示安全提示；Evaluator 等非核心能力标记为 `node.degraded`，不影响已经成功的查询结果。排查时通过一个 `request_id` 即可还原完整节点链路，通过 `topic_id` 可还原多轮澄清过程。

## 十一、多表过滤排查案例

### 11.1 典型现象

日志中的 SQL 使用了正确复合 Join 键，但只包含事实表：

```sql
WHERE fact.pt_dt = yesterday_expression
```

维表没有 `dim.pt_dt`，导致维表历史快照重复参与 Join，聚合结果膨胀。

### 11.2 排查顺序

1. 从落盘脚本元数据（`query_results/.../<request_id>_p1_script.json`）取出实际执行的 SQL。
2. 逐表检查是否都带了自己的 `pt_dt` 条件；只有事实表带、维表没带，就是这个问题。
3. 检查 Join 键是否用了语义层声明的复合键（如 `pt_platform + company_id`）。
4. 对比结果行数与单表预期，确认是否存在历史分区放大。

### 11.3 当前关键日志

- `tools.called`：确认 Planner 调用了 `execute_query` 及其它工具
- `llm.response` 的 `output`：SQL 生成本身的依据
- 落盘脚本元数据中的 `sql` / `engine` / `row_count`
- 执行期安全校验失败时的工具返回文本（`SQL 未通过安全校验：...`）

> 说明：主链路执行期校验的是"整条 SQL 是否含分区过滤"，逐表校验能力目前未接入主链路，因此多表场景需要人工复核每张表的过滤条件。

### 11.4 判断标准

当 `REQUIRED_FILTER_FIELDS_FOR_ALL_TABLES=["pt_dt"]` 时，每张表必须在 ON 或 WHERE 中拥有独立 `alias.pt_dt` 常量/函数过滤。`fact.pt_dt = dim.pt_dt` 不满足要求，因为它不能保证 Hive 对两张表分别进行分区裁剪。

## 十二、trace_view 树形查看工具

`agentTest/scripts/trace_view.py` 读取 `langgraph_app.jsonl`，按 `request_id` 还原一次请求的树形调用链，无需手工过滤 JSON。

### 常用命令

```bash
# 列出最近 20 个请求（耗时、结果、节点数）
python agentTest/scripts/trace_view.py list

# 渲染单个请求的树形 trace（支持 request_id 前缀）
python agentTest/scripts/trace_view.py show <request_id前缀>

# 查看完整字段，不截断长文本
python agentTest/scripts/trace_view.py show <request_id前缀> --full

# 按请求总耗时排行，快速定位慢请求
python agentTest/scripts/trace_view.py slow --top 10

# 查看指定请求的 LLM 输入与输出（调用→输出交错配对展示）
python agentTest/scripts/trace_view.py prompt <request_id前缀>
# 只看某个调用方的 LLM 调用
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner
# 查看完整输入输出，不截断
python agentTest/scripts/trace_view.py prompt <request_id前缀> --full

# 按事件/节点/关键词过滤
python agentTest/scripts/trace_view.py filter --event tools.called
python agentTest/scripts/trace_view.py filter --node planner --keyword new_order

# 读取指定日期的滚动日志
python agentTest/scripts/trace_view.py show <request_id前缀> --date 2026-08-05
```

### prompt 展示规则

- 按时间戳顺序用 `call_id` 把 `llm.call` 与 `llm.response` 配对，展示为「调用→输出→调用→输出」，输入和输出不会分开聚在末尾。
- 同一调用方连续调用时，首次显示完整输入；后续输入与上次完全相同则显示「与上次调用相同，省略」；是上次输入的扩展（如 ReAct 追加工具调用/工具结果）则只显示新增部分。
- 旧日志（无 `call_id`）自动降级为按顺序平铺展示。

### 树形输出示例

```text
==== trace 4fd4e5d9…  2026-08-05T15:49:51  [14.8s]  result=query
└─ request [14800.0ms] result_type=query
   └─ planner [5466.0ms] route=respond
      ├─ node.detail message=有效需求: ...
      ├─ tools.called tools=["grep_semantic", "read_metric", "execute_query"]
      └─ llm.response 工具结果：engine=trino row_count=20 → 结果落盘 → 撰写回答
```

### 归属规则

- 节点事件由 `span_id/parent_span_id` 构成父子层级，`request` 为根。
- `node.detail` 等 leaf 事件即使写在节点结束后，也会按 `node` 字段自动归属到同名节点 span 下。
- 旧格式日志（无 span 字段）仍可查看，事件会平铺展示。
  
  ## 十三、指标循环确认与连续问答排查

### 13.1 当前指标确认事件链

正常的多候选确认应看到：

```text
llm.response: 输出澄清文案（列出候选口径）
  ↓ 用户回复编号/字段名/中文含义
llm.call(prompt): 历史里带上上轮候选与本轮选择
  ↓
tools.called: grep_semantic → read_metric → execute_query
```

排查重点：

- 第一轮澄清文案里必须包含固定编号的候选口径。
- 用户选择后，Planner 本轮 `llm.call` 的 prompt 必须包含上一轮候选与本轮选择。
- 最终展示文本以 `respond_text` 为准，不要用中间草稿判断实际回复。
- 如果 resolved 后 LLM 漏传 `concept_resolutions`，仍应通过 previous resolution 放行。
- 候选重新排序后，已确认字段仍应保持 resolved。

### 13.2 典型循环确认判断

| 现象                        | 可能原因                                               | 检查位置                                                        |
| ------------------------- | -------------------------------------------------- | ----------------------------------------------------------- |
| 首轮展示了候选，下一轮无法识别“第二个”      | 候选只生成文本，没有写入 pending，或模型 `user_selection` 未命中/校验失败 | `analysis_spec.pending_clarifications` + planner 日志“用户选择校验” |
| Planner 已还原字段，仍反复追问           | Planner 重建 AnalysisSpec 时保留了旧 ambiguous            | `metric_resolutions.status/source`                          |
| LLM 未传解析参数后再次追问           | 门禁只依赖 `concept_resolutions`                        | previous resolutions 是否参与 Validator                         |
| 已确认字段因重新检索消失              | resolved 只校验本轮 candidates                          | 上轮 resolution.candidates 是否纳入合法字段                           |
| 日志显示“好，开始查询”但用户看到候选       | 记录了 LLM 草稿而非 final_answer                          | `node.end.answer_summary` 写入时机                              |

### 13.4 延迟编号排查方式

用户隔数轮回复“第二个”时，应按同一 `topic_id` 检查：

1. 最早的 `metric_resolution.user_required` 对应 pending 是否仍为 open（`pending_clarifications.status`）。
2. 中间解释或条件修改是否错误关闭 pending。
3. 本轮是否只有一个 open pending。
4. `metric_resolution.completed` 是否引用原始 `clarification_id`，而不是重新生成的候选。
5. 如果有多个 pending，是否安全追问而不是猜测（当前一次只澄清一个问题）。
6. 新 Topic 是否完全看不到旧 Topic 的 clarification 和 result snapshot。

## 十四、语义层命中与 RAG 兜底日志排查

系统是"语义层优先、RAG 兜底"：Planner 先用 `grep_semantic` 检索语义层指标，命中后用 `read_metric` 读完整口径，再自行生成 SQL 交给 `execute_query` 执行；只有语义层未覆盖时才走 BM25 + 向量的双路召回。

**没有专门的"命中事件"**，判断路径靠三类信息组合。

### 14.1 判断走了哪条路径

| 观察点 | 结论 |
| --- | --- |
| `tools.called` 含 `grep_semantic` / `read_metric`，不含 `search_*` | 语义层路径 |
| `tools.called` 含 `search_tables` / `search_columns` | 触发了 RAG 兜底 |
| `tools.called` 含 `execute_query` | 已真正查库 |
| 只有 `grep_semantic`，没有 `execute_query` | 口径未确认，Planner 选择先澄清 |

> `ENABLE_RAG=false` 时 `search_*` 即使被调用也返回空结果，日志里会看到工具被调用但没有候选返回。

### 14.2 看模型到底看到了什么

`tools.called` 只能说明"调用了什么工具"，命中的具体指标与口径要看模型输入输出：

```bash
# Planner 的输入与输出（调用→输出交错配对）
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner

# 不截断长文本
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner --full
```

- `llm.call.prompt` 里的工具返回段落，就是 `grep_semantic` / `read_metric` 给出的候选与口径；
- `llm.response.output` 是 Planner 的判断结果：选了哪个指标、SQL 怎么写、是否澄清。

### 14.3 一次真实请求的排查示例（"昨天A类新增订单是多少"）

```bash
# ① 看调用了哪些工具
python agentTest/scripts/trace_view.py filter --event tools.called --request <request_id前缀>
#    出现 grep_semantic(["新增","订单"]) → read_metric(...) → 说明走了语义层

# ② 看 Planner 的输入输出
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner
#    llm.call.prompt    里能看到候选指标「新增订单数」及其口径、来源表、维度
#    llm.response.output 里能看到：是继续澄清（多口径）还是直接生成 SQL

# ③ 看是否真正执行
python agentTest/scripts/trace_view.py filter --event tools.called --request <request_id前缀>
#    出现 execute_query → 已执行；未出现 → Planner 选择先向用户澄清
```

如果 Planner 判断"推广渠道A的新增订单"与"A类代理商"存在多种口径，它会直接输出澄清文案，此时不会出现 `execute_query`——这是预期行为。

### 14.4 一句话排查技巧

```bash
python agentTest/scripts/trace_view.py filter --event tools.called --request <request_id前缀>
python agentTest/scripts/trace_view.py prompt <request_id前缀> --caller planner
```

第一条看"做了什么"，第二条看"为什么这么做"。
