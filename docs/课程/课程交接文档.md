## 一、项目目标

基于 SQL-MARS 的 Planner → Advisor/Seeker 思路，建设可上线的智能数仓问数系统。当前开发策略调整为功能优先：先在现有单表链路上实现安全的多表 Join 和分析性查询，再进行上下文、持久化、并发与部署优化。

当前能力：

- 自然语言问题 → 元数据识别 → 多轮澄清 → 方案确认 → 精确 Schema 加载 → SQL 生成与执行。
- Planner / Advisor / Seeker / Evaluator 多智能体协作。
- 库、表、字段三层 FAISS + 高质量示例长期记忆。
- Conversation / Topic / Request 三层业务身份、Graph Thread 执行身份与 Topic checkpoint 隔离。
- JSON Lines 结构化日志、请求链路追踪、状态变化记录和安全 `error_id` 异常边界。
- Web 前端和 CLI 共用 Graph State 业务状态。

## 二、当前多智能体链路

```text
CaptureMessage
  ↓
Planner：表/字段检索 + LLM 需求还原 + 完整度判断
  ├─ partial/none → Advisor clarification_agent（无提交工具）
  ├─ full 且未锁定 → Advisor plan_agent
  └─ 用户接受完整 locked 方案 → confirm_query_plan → Seeker

Advisor clarification_agent：库/表/字段检索 → 解释歧义并追问
Advisor plan_agent：核对字段 → submit_query_plan
  ↓
lock_query_plan → QueryPlan(status=locked)
  ↓ 下一轮交给 Planner 判断确认或修改

Seeker：QueryPlanSchemaResolver
  ↓ 精确校验 database.table、单表约束和字段存在性
schema_context → GenerateSQL → ValidateSQL → ExecuteSQL → FinalAnswer → Evaluator
```

职责边界：

- Advisor 的 `partial/none` 澄清模式不绑定 `submit_query_plan`，无法形成 `locked` 方案。
- Advisor 只有在 `full` 方案模式中才能形成 `locked` 方案，且不能授权执行。
- Planner 负责将合法 `locked` 方案升级为 `confirmed`。
- Seeker 只接受 `status=confirmed`，不通过向量检索重新选表选字段。
- QueryPlan 已为多表保留 `tables`，但当前 `lock_query_plan()` 和 Resolver 仍明确限制为单表；下一阶段将拆分用户 QueryPlan 与系统 ExecutionPlan。

## 四、关键约定

### 4.1 上课与改码

1. 默认先讲设计、文件和代码，用户明确授权后才直接修改代码。
2. 不安排自动化测试课程，优先使用代码检查、日志和手动场景验证。
3. 不为临时兜底给 `HiveMetadataProvider` 增加 confirmed_plan 特例。
4. 不通过关键词硬编码判断确认或修改，由模型理解语义，程序负责契约校验。
5. 用户修改局部口径时优先基于原方案调整；方案根本错误时允许重新规划。

### 4.2 代码规范

- 使用中文注释。
- 修改代码不删除已有空行和注释，新代码添加简要注释。
- 避免无意义换行。
- Prompt 放在 `langgraph_app/prompts/`。
- 配置放在 `config/`。
- 禁止重新引入 `advisor_messages` 或 Web/Graph 双写 Topic 状态。

### 4.3 当前 Planner 配置

```python
MAX_HIGH_SIMILARITY_COUNT = 3
HIGH_SIMILARITY_THRESHOLD = 0.65
TABLE_SEARCH_K = 5
COLUMN_SEARCH_K = 7
EXAMPLE_SIMILARITY_THRESHOLD = 0.7
```

`HIGH_SIMILARITY_THRESHOLD` 和 `MAX_HIGH_SIMILARITY_COUNT` 保留为候选分布观测基线，用于日志、阈值校准和异常告警，不应直接覆盖 LLM 已结合上下文得出的 `completeness`。当前代码中的候选数量硬路由分支尚待删除，文档中的目标设计不能误写成已完成实现。

## 五、当前边界与技术债

- 已完成人工配置的表关系元数据和 SemanticMetadataProvider，JoinPlanner 可直接查询。；`tables` 尚未真正参与执行，下一阶段将通过 ExecutionPlan、关系元数据和 Join Planner 激活多表能力。
- `filters` 仍为字符串，Resolver 需要加载确认表完整物理 Schema。
- 跨库同名表暂时直接拒绝，等待统一元数据 Provider 支持完整库表标识。
- `SeekerState.schema_documents/schema_candidate_ids` 已退出活动链路但尚未删除。
- PlannerState、AdvisorState、SeekerState 仍重复声明继承来的 `confirmed_plan`，checkpoint 中仍是同一键。
- `AdvisorState` 当前未显式声明 `planner_entities/planner_reason`，父图进入 Advisor 子图时可能被 State Schema 过滤；待新增独立 `PlannerHandoffState` 契约。
- Advisor 方案模式若未调用 `submit_query_plan`，当前仍可能直接展示 LLM 文本；待增加协议校验和有限内部重试，只有获得真实 `locked_plan` 后才展示待确认方案。
- Planner 中“高相似候选数量强制 `full → partial`”的代码分支待删除，候选数仅保留在结构化日志和调优指标中。
- `MemorySaver` 仅适合单进程短期记忆，服务重启恢复尚未完成。
- GenerateSQL fallback 仍有单表、聚合和日期表达假设，需要在上线前继续收紧。
