## 一、课程目标与优先级

### 1.1 新的优先级

1. 修复 Planner → Advisor 的跨子图状态契约，保证当前方案确认链路稳定。
2. 在兼容现有单表查询的前提下，让系统自动判断单表是否足够，必要时生成多表执行方案。
3. 建立可维护的表关系元数据和确定性 Join Planner，禁止 LLM 自由猜测关联键。
4. 支持聚合、分组、趋势、排名、同比和环比等分析性查询。
5. 扩展更多库表和业务指标，形成可以演示的完整业务场景。
6. 功能闭环完成后，再优化上下文长度、记忆持久化、并发幂等、监控和部署。

### 1.2 功能优先不等于临时拼接

本阶段允许暂缓性能和工程优化，但不能采用未来必然推翻的临时架构：

- 不在 `HiveMetadataProvider` 中写某张表或某个方案的特例。
- 不让业务用户选择物理 Join 条件、关联键或 SQL 写法。
- 不让 LLM 在没有关系元数据时自由生成 Join。
- 不把物理 Join 细节继续塞进用户确认的业务方案中。
- 不为了多表查询重新启用 Seeker 向量检索选表。
- 单表查询必须作为多表执行模型中的零 Join 特例继续兼容。

### 1.3 暂缓的优化内容

以下内容不是取消，而是移动到多表和分析功能完成之后：

- Topic 历史消息摘要和上下文裁剪。
- 持久化 Checkpointer 与服务重启恢复。
- 对话历史恢复接口。
- 并发、幂等和请求去重增强。
- Prometheus、Grafana、OpenTelemetry 等外部可观测平台。
- 大规模元数据性能优化和自动化阈值调优。

当前结构化日志和 `error_id` 异常定位继续保留，作为功能开发阶段的主要 Debug 手段。

### 1.4 上课方式

- 默认先讲设计、改动文件和完整代码，用户明确要求后再直接修改业务代码。
- 后续课程不单独建设自动化测试体系，使用代码检查、结构化日志和手动验收场景验证。
- 每节开发课程在 `docs/课程复盘/` 新建独立复盘文档，记录问题、根因、方案取舍和面试表达。
- 每完成一课，同步更新本规划、课程交接文档和相关架构文档。

## 三、目标功能架构

### 3.1 双层查询计划

多表阶段不继续让一个 QueryPlan 同时承担业务确认和物理执行职责，而是拆成两层：

```text
用户问题
  ↓
Planner / Advisor
  ↓
QueryPlan：用户可理解的业务查询方案
  ↓ 用户确认
confirmed_plan
  ↓
TableCoverageAnalyzer
  ↓
JoinPlanner
  ↓
ExecutionPlan：系统内部物理执行方案
  ↓
Schema Resolver → SQL 生成 → SQL 校验 → 执行
```

**QueryPlan 负责业务语义**：

- 查询指标。
- 分析维度。
- 时间范围和时间粒度。
- 业务过滤条件。
- 分析类型，例如明细、聚合、趋势、排名或对比。
- 用户确认状态。

**ExecutionPlan 负责物理执行**：

- `single_table` 或 `multi_table` 模式。
- 主表、参与表和稳定表标识。
- 字段到物理表字段的映射。
- Join 边、关联键、Join 类型和基数。
- 目标数据粒度和必要的预聚合步骤。
- 关系元数据版本和生成原因。

业务用户只确认 QueryPlan，不确认 ExecutionPlan 中的物理 Join 细节。

### 3.2 单表与多表自动选择

系统遵循以下顺序：

1. 检查是否存在一张表能够覆盖全部指标、维度、时间字段和过滤字段。
2. 单表可完整覆盖时，优先生成 `single_table` ExecutionPlan。
3. 单表无法覆盖时，从已配置的关系元数据中寻找安全 Join 路径。
4. 多条路径都安全时，按覆盖完整度、路径长度、粒度匹配和关系优先级选择。
5. 路径会产生业务语义差异时，向用户澄清业务口径，而不是让用户选择关联键。
6. 无安全路径、存在无法消除的多对多膨胀或字段类型不兼容时，明确拒绝执行。

### 3.3 最小可用语义层

当前不先建设完整企业语义层，但多表和分析查询至少需要以下可维护元数据：

- 表的业务实体和数据粒度。
- 主键、业务键和时间字段。
- 表关系、关联键、关系方向和基数。
- 指标的默认聚合方式，例如 `sum/count/count_distinct/avg`。
- 指标允许使用的数据源和必要过滤条件。
- 维度字段的业务名称、同义词和来源表。

这些信息通过独立 Provider 或存储层提供，不在 Prompt、Planner 或 Hive Provider 中写死。

## 五、第6课：Planner → Advisor 契约修复

### 5.1 本课目标

- 新增独立 `PlannerHandoffState`，显式传递 `planner_reason/planner_entities`。
- 删除候选数量对 `completeness` 和路由的强制覆盖，只保留日志统计。
- Advisor 方案模式只有获得真实 `locked_plan` 后才能向用户展示完整方案。
- 未调用 `submit_query_plan` 时执行有限内部重试或返回可解释错误，不能伪装成方案已锁定。

### 5.2 为什么必须先做

多表阶段会增加候选表、字段覆盖结果和执行模式判断。如果 Planner 与 Advisor 的交接字段仍可能丢失，后续 Join 选择会更难定位，也会出现用户确认后重复追问。

### 5.3 验收标准

- 用户选择一个候选口径后，不因原始 Top-K 数量再次被追问同一问题。
- Advisor 收到的 `completeness`、有效问题和 Planner 原因与父图日志一致。
- 用户确认前必须存在 `status=locked` 的真实 QueryPlan。

---

## 六、第7课：QueryPlan V2 与 ExecutionPlan

### 6.1 本课目标

- 保留 `confirmed_plan` 作为用户确认的业务契约。
- 新增系统内部 `ExecutionPlan`，避免用户方案包含 Join 键等物理细节。
- 将单表执行定义为 `joins=[]` 的合法 ExecutionPlan。
- 为后续分析查询增加结构化 `analysis_spec` 入口，但本课不实现复杂 SQL。

### 6.2 建议结构

```python
class ExecutionPlan(TypedDict, total=False):
    mode: Literal["single_table", "multi_table"]
    primary_table: str
    tables: list[str]
    joins: list[dict]
    field_sources: dict[str, str]
    target_grain: list[str]
    metadata_version: str
```

实际编码时应继续细化 Join 和字段映射类型，不长期保留无约束的 `list[dict]`。

### 6.3 关键取舍

- QueryPlan 描述“用户要什么”。
- ExecutionPlan 描述“系统如何查”。
- ExecutionPlan 由程序根据确认方案和关系元数据生成，不由用户确认。
- 关系元数据版本变化后，可以重新派生 ExecutionPlan，避免长期保存过期 Join 路径。

## 七、第8课：表关系与粒度元数据

### 7.1 本课目标

建立独立的关系元数据模型，至少包含：

- 左表、右表完整标识。
- 左右关联字段。
- 允许的 Join 类型。
- `one_to_one/one_to_many/many_to_one/many_to_many` 基数。
- 两张表的数据粒度和业务实体。
- 关系是否启用、优先级和版本。
- 可选的固定关系过滤条件。

### 7.2 设计要求

- 关系元数据不能从字段同名自动推断后直接执行。
- LLM 可以帮助离线生成候选关系，但必须经过人工审核后进入活动关系目录。
- Runtime 只读取已启用的关系。
- 关系存储通过独立 Provider 访问，不给 `HiveMetadataProvider` 增加 QueryPlan 特例。

### 7.3 验收标准

- 能查询指定表的所有可用关系。
- 能区分同名字段但业务含义不同的错误关系。
- 能通过稳定 `database.table` 标识跨库定位表。
- 关系元数据缺失时系统明确说明，不让 LLM 猜 Join。

## 八、第9课：表覆盖分析与 Join Planner

### 8.1 TableCoverageAnalyzer

输入 QueryPlan 中的指标、维度、时间和过滤需求，输出：

- 每张候选表能够覆盖的字段集合。
- 单表是否能完整覆盖。
- 尚未覆盖的业务槽位。
- 需要参与多表规划的表集合候选。

### 8.2 Join Planner

Join Planner 只在已审核关系图上规划：

- 优先单表。
- 多表时选择覆盖完整且路径最短的方案。
- 校验 Join 边方向、字段类型和基数。
- 对一对多关系检查最终查询粒度。
- 对多对多关系默认拒绝，除非存在明确桥表和预聚合策略。
- 输出结构化 ExecutionPlan，而不是 SQL 文本。

### 8.3 验收标准

- 同一问题能稳定判断单表是否足够。
- 多次执行相同输入得到相同 Join 路径。
- 无关系、错误关系和危险多对多场景不会进入 SQL 生成。
- Join 决策原因写入结构化日志，便于面试演示和 Debug。

## 九、第10课：多表 Schema Resolver

### 9.1 本课目标

将当前单表 `QueryPlanSchemaResolver` 扩展为按 ExecutionPlan 工作：

- 精确加载所有参与表的 Schema。
- 校验每个字段属于指定表。
- 校验关联键存在且数据类型兼容。
- 校验 ExecutionPlan 中的表和 Join 边都来自活动关系元数据。
- 为每张表分配稳定别名，生成结构化 Schema Context。

### 9.2 关键边界

- Resolver 不做向量检索，也不重新选择表。
- Resolver 不修补 Join Planner 缺失的关系。
- confirmed_plan 或 ExecutionPlan 非法时直接拒绝执行。
- Schema Context 必须保留表、字段和关联边界，不能把多表字段平铺后丢失来源。

## 十、第11课：多表 SQL 生成、校验与执行

### 10.1 SQL 生成

- Prompt 同时接收 QueryPlan、ExecutionPlan 和精确多表 Schema。
- Join 顺序、表集合、关联键和 Join 类型由 ExecutionPlan 固定。
- LLM 只负责生成符合执行计划的 SQL 表达，不允许新增表或替换关联键。
- SQL 重试时继续保留原 ExecutionPlan，不能因报错重新自由规划 Join。

### 10.2 SQL 校验

在现有语法和资源校验基础上增加：

- SQL 使用的表集合必须与 ExecutionPlan 一致。
- 每条 Join 条件必须对应已批准的 Join 边。
- 字段必须来自已加载 Schema。
- 禁止无条件 Join 和意外笛卡尔积。
- 检查一对多 Join 后的指标重复计算风险。
- 检查 `GROUP BY` 与目标粒度是否一致。

建议引入 SQL AST 解析完成结构校验，不使用字符串包含判断承担长期安全职责。

### 10.3 验收标准

- 跑通至少一个真实两表查询。
- 单表查询仍沿用同一执行链路。
- 模型擅自增加表、修改 Join 键或遗漏 Join 条件时被校验层拒绝。
- 无法安全执行时返回明确原因，而不是无限重试。

## 十一、第12课：分析查询意图与 AnalysisSpec

### 11.1 本课目标

把分析需求从自然语言提取为结构化规格，而不是只保存字段列表：

```text
analysis_type: detail / aggregate / trend / ranking / comparison
metrics: 指标及聚合方式
dimensions: 分析维度
time_grain: day / week / month / quarter / year
order_by: 排序指标和方向
limit: TopN 数量
comparison: 同比、环比或基期
```

### 11.2 Planner 与 Advisor 职责

- Planner 判断缺少的是指标、维度、时间、排序还是对比口径。
- Advisor 只对业务歧义追问，例如“新增订单按创建还是支付口径”。
- 用户不需要说明 `GROUP BY`、窗口函数或子查询。
- 用户确认后将 AnalysisSpec 固化到 QueryPlan，后续执行层不得改变业务含义。

## 十二、第13课：基础分析性查询

### 12.1 第一批支持范围

- `count/sum/avg/count_distinct` 聚合。
- 按一个或多个维度分组。
- 按日、周、月汇总趋势。
- 排序、TopN 和 BottomN。
- 明细查询与聚合查询自动区分。

### 12.2 验收场景

- “昨天各城市新增订单数”。
- “最近 30 天每天订单金额趋势”。
- “本月订单量最高的前 10 个渠道”。
- “查询指定订单的明细信息”。
- 指标和维度来自不同表时，能够复用多表 ExecutionPlan。

---

## 十三、第14课：高级分析性查询

### 13.1 第二批支持范围

- 同比、环比和基期比较。
- 占比、转化率和人均等派生指标。
- 去重指标和 Join 后去重策略。
- 窗口累计、移动平均和排名。
- 多阶段聚合，例如事实表先聚合后关联维表。

### 13.2 安全要求

- 派生指标公式来自配置或明确的业务表达，不允许模型猜测公式。
- 比较查询必须明确当前期、对比期和时间粒度。
- 一对多 Join 上的聚合必须先确认粒度或执行预聚合。
- 结果中说明指标口径、时间范围和分组维度。

---

## 十四、第15课：更多库表与轻量业务语义

### 14.1 本课目标

- 扩展更多事实表、维度表和汇总表。
- 配置业务指标、同义词、默认聚合和固定过滤条件。
- 配置表粒度、关系和常用 Join 路径。
- 当汇总表能够直接覆盖问题时优先使用汇总表，避免不必要 Join。
- 建立元数据版本，确保 ExecutionPlan 可追溯。

### 14.2 与完整语义层的关系

本课建设的是多表与分析查询所需的最小语义能力。完整语义层可以在功能稳定后继续扩展：

- 指标继承与复用。
- 数据权限。
- 时间语义和日历表。
- 多数据源编译。
- 成本优化和物化视图选择。

## 十五、第16课：功能验收与演示闭环

### 15.1 必须通过的场景

1. 单表明细查询。
2. 单表聚合和时间趋势。
3. 两表事实表与维表 Join。
4. 指标和维度分布在不同表的查询。
5. 自动判断单表足够，不产生多余 Join。
6. 缺少关系元数据时安全拒绝。
7. 多对多膨胀风险时安全拒绝或使用明确桥表方案。
8. TopN、同比或环比分析。
9. 用户修改一个口径时尽量保留原 QueryPlan 其他部分。
10. 日志能够还原 QueryPlan、ExecutionPlan、Join 决策和 SQL 校验结果。

### 15.2 功能阶段完成标准

- 业务用户不需要理解物理表、字段和 Join 条件。
- 单表、多表和分析查询共享统一执行架构。
- Join 关系可配置，不依赖 Prompt 写死。
- SQL 生成不能突破 ExecutionPlan。
- 失败场景有明确、可解释的拒绝原因。

达到以上标准后，再进入优化课程。

## 十六、功能完成后的优化课程

### 第17课：上下文裁剪与 Topic 摘要

- 限制传给 LLM 的历史消息数量。
- 保留原始问题、QueryPlan、AnalysisSpec、最近轮次和关键工具结果。
- ExecutionPlan、Schema Context 和查询结果避免长期重复写入消息历史。

### 第18课：Checkpointer 与历史恢复

- 将 `MemorySaver` 替换为持久化 Checkpointer。
- 服务重启后恢复 Topic、confirmed_plan 和必要消息。
- ExecutionPlan 根据元数据版本决定恢复或重新派生。

### 第19课：并发、幂等与失败恢复

- 使用 `request_id` 防止重复追加消息和重复执行 SQL。
- 限制同一 Topic 并发修改 QueryPlan。
- 区分安全重试、重新规划和新 Topic。

### 第20课：部署、监控与性能优化

- 健康检查、配置环境变量化和进程部署。
- 统计单表命中率、多表规划率、Join 拒绝率和 SQL 首次成功率。
- 优化元数据检索、关系图查询、Prompt 长度和 SQL 执行成本。
- 根据需要接入 Prometheus、Grafana 或 OpenTelemetry。

### 第21课：简历与面试材料

- 系统架构图和双层计划数据流。
- 多表 Join 安全设计和分析查询 IR。
- 真实问题、根因、方案取舍和量化指标。
- 演示脚本、项目描述和常见面试追问。
