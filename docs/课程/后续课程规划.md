## 一、课程目标与优先级

### 1.1 新的优先级

1. 修复 Planner → Advisor 的跨子图状态契约，保证当前方案确认链路稳定。
2. 在兼容现有单表查询的前提下，让系统自动判断单表是否足够，必要时生成多表执行方案。
3. 建立可维护的表关系元数据和关系优先 Join Planner，通过开关控制是否允许 LLM 推测缺失关系。
4. 建立连续问答能力，让用户可以基于上一轮查询结果继续追问，并支持跨数轮恢复未完成的候选选择。
4.5 元数据规模化接入：白名单配置化、schema 指纹增量采集、字段/枚举/向量变更同步，支撑数仓全量表接入与废弃表治理。
5. 先建立指标、维度、实体和业务术语组成的最小可用语义层。
6. 基于标准语义文档实现 BM25、向量检索、混合召回、重排和检索评估。
7. 支持聚合、分组、趋势、排名、同比和环比等分析性查询。
8. 扩展更多库表和业务指标，形成可以演示的完整业务场景。
9. 功能闭环完成后，再优化上下文长度、记忆持久化、并发幂等、监控和部署。

### 1.2 功能优先不等于临时拼接

本阶段允许暂缓性能和工程优化，但不能采用未来必然推翻的临时架构：

- 不在 `HiveMetadataProvider` 中写某张表或某个方案的特例。
- 不让业务用户选择物理 Join 条件、关联键或 SQL 写法。
- 关系元数据优先；仅在 `ALLOW_AI_INFERRED_JOIN=True` 时允许 LLM 推测 Join，并继续接受复合键、白名单、逐表过滤和 SQL Guardrails 校验。
- 不把物理 Join 细节继续塞进用户确认的业务方案中。
- 不为了多表查询重新启用 Seeker 向量检索选表。
- 不直接对原始 Schema 结果做简单 BM25 与向量分数相加，混合检索必须基于标准语义对象和可解释融合策略。
- 不让检索结果绕过指标口径、字段来源、Join 路径、权限和逐表必选过滤等硬约束。
- 单表查询必须作为多表执行模型中的零 Join 特例继续兼容。

### 1.3 暂缓的优化内容

以下内容不是取消，而是移动到语义检索、分析查询和功能验收完成之后：

- Topic 历史消息摘要和上下文裁剪。
- 持久化 Checkpointer 与服务重启恢复。
- 对话历史恢复接口。
- 并发、幂等和请求去重增强。
- Prometheus、Grafana、OpenTelemetry 等外部可观测平台。
- 大规模元数据性能优化和自动化阈值调优。

当前结构化日志和 `error_id` 异常定位继续保留，作为功能开发阶段的主要 Debug 手段。

### 1.4 上课方式

- 默认先讲设计、改动文件和完整代码，用户明确要求后再直接修改业务代码。
- 后续课程不单独建设自动化测试体系，使用代码检查、结构化日志和手动验收场景验证。
- 每节开发课程在 `docs/课程复盘/` 新建独立复盘文档，记录问题、根因、方案取舍和面试表达。
- 每完成一课，同步更新本规划、课程交接文档和相关架构文档。

### 2.2 当前代码能力

- SQL 链路支持多表生成、复合 Join 校验、字段来源检查、失败重试和结果总结。

- LEFT JOIN 维表的分区过滤放入 `ON`，避免外连接因 `WHERE` 条件退化。
- 缺少维表必选过滤时，简单 SQL 可以根据 confirmed QueryPlan 确定性重建，复杂 SQL 进入 LLM 修复，执行前继续保留硬门禁。
- 库、表、字段三级 FAISS 向量检索和增量构建已经可用，但主要检索对象仍是物理 Schema。

## 三、目标功能架构

### 3.1 双层查询计划

多表阶段不继续让一个 QueryPlan 同时承担业务确认和物理执行职责，而是拆成两层：

```text
用户问题
  ↓
Planner 提取 AnalysisSpec
  ↓
语义检索、候选过滤与重排
  ↓
Advisor 澄清或锁定
  ↓
QueryPlan：用户可理解的业务查询方案
  ↓ 用户确认
confirmed_plan
  ↓
TableCoverageAnalyzer → JoinPlanner
  ↓
ExecutionPlan：系统内部物理执行方案
  ↓
Schema Resolver → SQL 生成 → SQL 校验 → 执行
```

**QueryPlan 负责业务语义**：

- 查询指标。
- 分析维度。
- 时间范围和时间粒度。
- 业务过滤条件。
- 分析类型，例如明细、聚合、趋势、排名或对比。
- 用户确认状态。

**ExecutionPlan 负责物理执行**：

- `single_table` 或 `multi_table` 模式。
- 主表、参与表和稳定表标识。
- 字段到物理表字段的映射。
- Join 边、关联键、Join 类型和基数。
- 目标数据粒度和必要的预聚合步骤。
- 关系元数据版本和生成原因。

业务用户只确认 QueryPlan，不确认 ExecutionPlan 中的物理 Join 细节。

### 3.2 单表与多表自动选择

系统遵循以下顺序：

1. 检查是否存在一张表能够覆盖全部指标、维度、时间字段和过滤字段。
2. 单表可完整覆盖时，优先生成 `single_table` ExecutionPlan。
3. 单表无法覆盖时，优先从已配置的关系元数据中寻找安全 Join 路径。
4. 多条路径都安全时，按覆盖完整度、路径长度、粒度匹配和关系优先级选择。
5. 人工关系缺失且 `ALLOW_AI_INFERRED_JOIN=True` 时，允许 LLM 根据 Schema 推测候选 Join，但必须继续通过复合键、白名单、字段类型、逐表过滤和 SQL Guardrails 校验。
6. 路径会产生业务语义差异时，向用户澄清业务口径，而不是让用户选择关联键。
7. 开关关闭且无安全路径，或存在无法消除的多对多膨胀、字段类型不兼容时，明确拒绝执行。

### 3.3 最小可用语义层

BM25 + RAG 混合检索不能只建立在原始表名、字段名和字段注释上，否则只能增强 Schema 搜索，无法稳定识别业务指标、固定口径和适用维度。因此在混合检索前先建设最小可用语义层，但不提前扩张成完整企业指标平台。

最小语义层包含以下四类对象：

- `Metric`：指标名称、别名、解释、计算表达式、默认聚合、固定过滤、默认时间字段和支持维度。
- `Dimension`：维度名称、别名、所属实体、物理来源和可用枚举。
- `Entity`：订单、经销商、渠道等业务实体，以及实体键和相关表。
- `BusinessTerm`：业务术语、简称、同义词、标准值和目标维度。

同时继续维护以下物理与关系元数据：

- 表的业务实体和数据粒度。
- 主键、业务键和时间字段。
- 表关系、关联键、关系方向和基数。
- 指标、维度到物理字段和表达式的确定性绑定。
- 指标固定过滤、用户业务过滤和系统逐表必选过滤的来源隔离。

这些信息通过独立 Provider 或存储层提供，不在 Prompt、Planner 或 Hive Provider 中写死。

### 3.4 语义检索与执行边界

语义层建立后，将每个指标、维度、实体、业务术语、表、字段和典型查询案例转换为独立检索文档，并携带 `document_type`、`semantic_id`、版本、数据域、关联表和启用状态等 metadata。

检索链路采用以下分层：

```text
用户问题
  ↓
查询理解与类型过滤
  ↓
BM25 召回 + 向量召回
  ↓
RRF 融合
  ↓
元数据硬过滤 + 规则/LLM 重排
  ↓
Planner 候选 → Advisor 澄清或锁定
  ↓
QueryPlan → ExecutionPlan → SQL
```

混合检索只负责提供候选，不负责自创指标、字段或 Join。最终执行仍必须经过字段来源锁定、关系路径校验、逐表过滤校验和 SQL Guardrails。

## 五、第6课：Planner → Advisor 契约修复

### 5.1 本课目标

- 新增独立 `PlannerHandoffState`，显式传递 `planner_reason/planner_entities`。
- 删除候选数量对 `completeness` 和路由的强制覆盖，只保留日志统计。
- Advisor 方案模式只有获得真实 `locked_plan` 后才能向用户展示完整方案。
- 未调用 `submit_query_plan` 时执行有限内部重试或返回可解释错误，不能伪装成方案已锁定。

### 5.2 为什么必须先做

多表阶段会增加候选表、字段覆盖结果和执行模式判断。如果 Planner 与 Advisor 的交接字段仍可能丢失，后续 Join 选择会更难定位，也会出现用户确认后重复追问。

### 5.3 验收标准

- 用户选择一个候选口径后，不因原始 Top-K 数量再次被追问同一问题。
- Advisor 收到的 `completeness`、有效问题和 Planner 原因与父图日志一致。
- 用户确认前必须存在 `status=locked` 的真实 QueryPlan。

## 六、第7课：QueryPlan V2 与 ExecutionPlan

### 6.1 本课目标

- 保留 `confirmed_plan` 作为用户确认的业务契约。
- 新增系统内部 `ExecutionPlan`，避免用户方案包含 Join 键等物理细节。
- 将单表执行定义为 `joins=[]` 的合法 ExecutionPlan。
- 为后续分析查询增加结构化 `analysis_spec` 入口，但本课不实现复杂 SQL。

### 6.2 建议结构

```python
class ExecutionPlan(TypedDict, total=False):
    mode: Literal["single_table", "multi_table"]
    primary_table: str
    tables: list[str]
    joins: list[dict]
    field_sources: dict[str, str]
    target_grain: list[str]
    metadata_version: str
```

实际编码时应继续细化 Join 和字段映射类型，不长期保留无约束的 `list[dict]`。

### 6.3 关键取舍

- QueryPlan 描述“用户要什么”。
- ExecutionPlan 描述“系统如何查”。
- ExecutionPlan 由程序根据确认方案、关系元数据或开关允许的 AI 推测关系生成，不由用户确认。
- 关系元数据版本变化后，可以重新派生 ExecutionPlan，避免长期保存过期 Join 路径。

---

## 七、第8课：表关系与粒度元数据

### 7.1 本课目标

建立独立的关系元数据模型，至少包含：

- 左表、右表完整标识。
- 左右关联字段。
- 允许的 Join 类型。
- `one_to_one/one_to_many/many_to_one/many_to_many` 基数。
- 两张表的数据粒度和业务实体。
- 关系是否启用、优先级和版本。
- 可选的固定关系过滤条件。

### 7.2 设计要求

- 关系元数据不能仅凭字段同名自动推断后直接执行，人工配置关系始终优先。
- `ALLOW_AI_INFERRED_JOIN=True` 时，LLM 可以在运行时生成候选关系，但候选必须通过复合键、字段类型、白名单、逐表过滤和 SQL Guardrails 校验。
- Runtime 优先读取已启用关系；只有开关打开且人工关系缺失时才进入 AI 推测分支。
- 关系存储通过独立 Provider 访问，不给 `HiveMetadataProvider` 增加 QueryPlan 特例。

### 7.3 验收标准

- 能查询指定表的所有可用关系。
- 能区分同名字段但业务含义不同的错误关系。
- 能通过稳定 `database.table` 标识跨库定位表。
- 关系元数据缺失且开关关闭时明确拒绝；开关打开时允许推测，但校验失败仍必须拒绝。

## 八、第9课：表覆盖分析与 Join Planner

### 8.1 TableCoverageAnalyzer

输入 QueryPlan 中的指标、维度、时间和过滤需求，输出：

- 每张候选表能够覆盖的字段集合。
- 单表是否能完整覆盖。
- 尚未覆盖的业务槽位。
- 需要参与多表规划的表集合候选。

### 8.2 Join Planner

Join Planner 优先在已审核关系图上规划，缺少关系时按开关决定是否进入 AI 推测分支：

- 优先单表。
- 开关打开且人工关系缺失时，LLM 输出候选表对、复合关联键、Join 类型和推测理由，再由确定性规则校验。
- 多表时选择覆盖完整且路径最短的方案。
- 校验 Join 边方向、字段类型和基数。
- 对一对多关系检查最终查询粒度。
- 对多对多关系默认拒绝，除非存在明确桥表和预聚合策略。
- 输出结构化 ExecutionPlan，而不是 SQL 文本。

### 8.3 验收标准

- 同一问题能稳定判断单表是否足够。
- 多次执行相同输入得到相同 Join 路径。
- 开关关闭时无关系场景不会进入 SQL 生成；错误关系和危险多对多场景始终拒绝。
- Join 决策原因写入结构化日志，便于面试演示和 Debug。

## 九、第10课：多表 Schema Resolver

### 9.1 本课目标

将当前单表 `QueryPlanSchemaResolver` 扩展为按 ExecutionPlan 工作：

- 精确加载所有参与表的 Schema。
- 校验每个字段属于指定表。
- 校验关联键存在且数据类型兼容。
- 校验 ExecutionPlan 中的 Join 边来自活动关系元数据，或来自已通过安全校验的 AI 推测结果。
- 为每张表分配稳定别名，生成结构化 Schema Context。

### 9.2 关键边界

- Resolver 不做向量检索，也不重新选择表。
- Resolver 不自行推测或修补 Join，只消费 JoinPlanner 已输出的结构化关系。
- confirmed_plan 或 ExecutionPlan 非法时直接拒绝执行。
- Schema Context 必须保留表、字段和关联边界，不能把多表字段平铺后丢失来源。

## 十、第11课：多表 SQL 生成、校验与执行

### 10.1 SQL 生成

- Prompt 同时接收 QueryPlan、ExecutionPlan 和精确多表 Schema。
- Join 顺序、表集合、关联键和 Join 类型由 ExecutionPlan 固定。
- LLM 只负责生成符合执行计划的 SQL 表达，不允许新增表或替换关联键。
- SQL 重试时继续保留原 ExecutionPlan，不能因报错重新自由规划 Join。

### 10.2 SQL 校验

在现有语法和资源校验基础上增加：

- SQL 使用的表集合必须与 ExecutionPlan 一致。
- 每条 Join 条件必须对应已批准的 Join 边。
- 字段必须来自已加载 Schema。
- 禁止无条件 Join 和意外笛卡尔积。
- 检查一对多 Join 后的指标重复计算风险。
- 检查 `GROUP BY` 与目标粒度是否一致。

建议引入 SQL AST 解析完成结构校验，不使用字符串包含判断承担长期安全职责。

### 10.3 验收标准

- 跑通至少一个真实两表查询。
- 单表查询仍沿用同一执行链路。
- 模型擅自增加表、修改 Join 键或遗漏 Join 条件时被校验层拒绝。
- 无法安全执行时返回明确原因，而不是无限重试。

## 十一、第12课：AnalysisSpec 与指标口径歧义门禁（已完成）

### 11.1 问题背景

真实日志中，用户询问“查询昨天新增订单最多的经销商的名称，状态，业务经理”。Planner 已将需求判定为 `partial`，候选字段中同时存在 `new_order`、`really_add_order`、`dealership_new_order` 等口径，但 Advisor 受到高相似历史案例影响，直接选择 `new_order` 并调用 `submit_query_plan`。

本次问题说明：Prompt 已要求“多口径必须追问”仍然不够，必须在 `submit_query_plan → lock_query_plan` 之间增加程序级业务口径门禁。

### 11.2 本课目标

本课同时完成 AnalysisSpec 和指标歧义闭环：

- 从自然语言提取指标、维度、时间、过滤、排序和分析类型。
- 显式保存用户提到的业务概念，而不是只保存物理字段。
- 为每个指标记录候选、解析状态和解析证据。
- 多个合理指标且没有用户选择或正式默认口径时，程序必须阻止方案锁定。
- 用户本轮解决歧义后，Advisor 必须在同一轮生成 `locked_plan`，不能重新引入重复确认。

建议的 AnalysisSpec：

```json
{
  "analysis_type": "ranking",
  "metric_mentions": ["新增订单"],
  "dimension_mentions": ["经销商名称", "状态", "业务经理"],
  "time_range": "昨天",
  "time_grain": "day",
  "filters": [],
  "order_by": [{"concept": "新增订单", "direction": "DESC"}],
  "limit": 1,
  "comparison": null,
  "metric_resolutions": [
    {
      "mention": "新增订单",
      "status": "ambiguous",
      "selected_field": null,
      "resolution_source": "",
      "candidates": [
        "new_order",
        "really_add_order",
        "pure_new_order",
        "dealership_new_order"
      ]
    }
  ]
}
```

### 11.3 可信解析来源

指标只有满足以下任一条件才算已经解决：

- `llm_submitted`：Advisor 提交 `concept_resolutions` 时，程序信任模型对用户回复的解读（字段必须落在真实候选或上轮已确认字段内）。
- `explicit_user`：上轮已确认的解析记录，用户在后续轮次未改选时保持有效。
- `semantic_default`：正式语义配置为该业务术语指定唯一默认指标。
- `unique_metadata`：元数据中只有一个合理候选。

以下信息只能用于候选排序，不能独立证明用户已经确认口径：

- 历史优秀案例及历史 SQL。
- 向量相似度最高的字段。
- ADS 表优先规则。
- LLM 根据常识自行选择的字段。

### 11.4 Planner 与 Advisor 职责

- Planner 提取 AnalysisSpec、`metric_mentions` 和初始候选冲突，不直接替用户选择物理指标。
- Advisor 使用元数据工具核验候选，并向用户解释业务差异。
- Advisor 可以在当前轮解决歧义；`concept_resolutions` 可作为模型提交证据，但 State 中已确认记录不能因模型漏传而失效。
- Planner 在 LLM 前使用 `MetricClarificationService` 解析 pending 编号、字段名和中文含义；Validator 继续校验字段必须来自真实候选或上轮已确认记录。
- QueryPlan 只接收已解决的指标；未解决候选保留在 AnalysisSpec 或 Advisor 临时状态中。

### 11.5 提交硬门禁

现有“已对所有目标表调用 `search_columns`”校验继续保留，并增加以下条件：

1. 每个 `metric_mentions` 都存在解析记录。
2. 每条解析记录只有一个 `selected_field`。
3. `selected_field` 必须存在于真实元数据候选中。
4. pending 命中的用户选择生成 `explicit_user` 记录；LLM 提交字段必须存在于真实候选或上轮已确认字段，且不能覆盖已确认选择。
5. 历史案例不能将 `ambiguous` 自动变为 `resolved`。
6. 任意指标仍为 `ambiguous` 时，阻止 `lock_query_plan` 并生成澄清选项。

不得采用 `planner_completeness == "partial"` 时一律禁止提交的简单方案。因为部分 `partial` 可以通过本轮工具核验变成唯一映射，仍应允许同轮锁定。

### 11.6 历史案例使用边界

在指标尚未解析前，Advisor 不应接收历史案例中的原始 SQL。可以展示历史问题或语义指标 ID，但必须明确：历史案例只参与召回和排序，不能替当前用户确认业务口径。

推荐顺序：

```text
AnalysisSpec
  ↓
指标候选与歧义门禁
  ↓
用户选择或正式默认口径
  ↓
检索同指标历史案例
  ↓
QueryPlan 锁定与后续 SQL 生成
```

### 11.7 验收标准

- “新增订单”存在多个合理指标时必须追问，不得调用 `lock_query_plan`。
- 高相似历史案例使用 `new_order` 时，仍不能绕过歧义门禁。
- 用户回答“全量新增订单”后，本轮直接锁定 `new_order`。
- 用户回答“净增订单”后，本轮直接锁定 `really_add_order`。
- 用户回答“B类新增订单”后，本轮直接锁定 `new_b_order`。
- 唯一指标候选不增加额外确认轮次。
- 多表 `field_sources`、复合 Join、逐表 `pt_dt` 和业务过滤隔离能力不得回归。
- 日志能够说明指标为何被判定为歧义、用户最终选择了什么以及方案为什么允许锁定。

## 十二、第13课：连续问答与延迟澄清恢复

### 12.1 本课目标

在不新增独立 Agent、不依赖硬编码业务规则的前提下，让同一 Topic 支持两类连续问答：

1. **结果追问**：用户可以引用上一轮查询结果，例如“第一名的业务经理是谁”“这些经销商里状态正常的有几个”“把刚才结果按城市汇总”。
2. **方案追问**：用户可以沿用上一轮 QueryPlan，只修改时间、过滤、维度、排序或指标，例如“换成近 7 天”“再加上城市”“按净增订单重算”。
3. **延迟选择**：Advisor 给出候选选项后，用户可以先询问口径解释或补充其他条件，隔数轮再回复“第二个”，系统仍能定位原候选并正确解析。
4. **冲突保护**：如果同时存在多个未完成澄清，单独回复“第二个”不能猜测，必须要求用户指出指标概念或澄清问题。

### 12.2 状态模型

本课不把完整结果和所有历史消息直接塞给 LLM，而是在 Topic State 增加结构化引用：

```python
class QueryResultSnapshot(TypedDict, total=False):
    result_id: str
    source_request_id: str
    confirmed_plan: dict
    columns: list[str]
    preview_rows: list[dict]
    row_count: int
    result_summary: str
    entity_keys: list[str]
    created_at: str

class PendingClarification(TypedDict, total=False):
    clarification_id: str
    clarification_type: str
    mention: str
    question: str
    options: list[dict]
    status: str
    created_request_id: str
    last_active_request_id: str
    resolved_value: dict

class FollowUpContext(TypedDict, total=False):
    mode: str
    referenced_result_id: str
    base_plan: dict
    changed_slots: list[str]
    resolved_question: str
```

State 已从单个 `pending_metric_clarification` 升级为：

- `pending_clarifications: list[PendingClarification]`（已落地）：候选创建时固化 `clarification_id` 与 options；用户未选择时复用同一 open pending，编号不随后续召回重排变化。
- `last_query_result: QueryResultSnapshot`（已落地）：`build_final_answer` 在查询成功/空结果后写入引用+预览+实体键，不把全量数据写入 checkpoint。
- `active_clarification_id` / `follow_up_context`（第二阶段）：多 pending 冲突消解与结果追问路由时再启用，`follow_up_mode` 已由 Planner 输出但暂不参与路由。

### 12.3 处理顺序

```text
Capture User Message
  ↓
Planner LLM 判断 user_selection（判断归模型）
  ├─ 结合【对话历史】+【待澄清候选】识别用户选择
  └─ 未选择（询问解释/闲聊/补充条件）→ 保持 pending
  ↓
程序 validate_user_selection（白名单校验，校验归程序）
  ├─ field 逐字命中 options 且 clarification_id 对齐 → explicit_user
  ├─ 候选外字段 / id 不匹配 → 拒绝，宁可不选也不猜测
  └─ 未选择 → pending 保留（同一概念）或清理（换话题）
  ↓
Planner → Advisor / Seeker
```

关键原则：

- 选择判断由 Planner LLM 完成，但必须只使用 State 中真实保存的 pending options；程序做白名单校验兜底。
- 中间轮次没有选择候选时，不得删除 pending；只有明确解决、用户取消、Topic 结束或配置化过期策略触发时才关闭。
- 不使用“最近一条 AI 消息”反推候选，也不写死“第几个=第几个候选”的硬规则，避免消息裁剪、模型改写或多轮插话造成编号漂移。
- 结果追问优先引用结构化结果快照和 QueryPlan，不简单拼接“上一问 + 当前问”。
- 用户说“第一名”“这些”“刚才的结果”时，必须有唯一可用结果引用；没有结果或结果已过期时应明确提示重新查询。
- 新 Topic 不能读取旧 Topic 的 pending 或结果快照，防止上下文串话。

### 12.4 延迟编号解析规则

通用解析只依赖候选状态，不写死具体指标，也不写死编号映射：

- 支持 `2`、`第二个`、`选第二项`、精确字段名和完整中文含义（由 Planner LLM 结合历史对话判断）。
- 用户先问“第二个和第一个有什么区别”，`selected` 必须为 false；Advisor 会基于候选的原始备注/别名/来源表生成口径区别说明（`build_clarification_explanation`），pending 保持 open，不重复展示“请选择”。
- 数轮后回复“第二个”时，如果只有一个 `open` pending，LLM 按该 pending 的固定 options 判断，程序白名单校验后解析。
- 如果存在多个 `open` pending，要求用户回复“新增订单选第二个”或指定 `clarification_id` 对应概念（第二阶段）。
- 候选重新检索、重排或消息摘要后，原编号仍以创建 pending 时的 options 为准。
- 是否过期、最多保留多少轮必须配置化，不能把固定轮数写死在业务代码中。

### 12.5 结果追问边界

第一阶段支持：

- 引用上一轮结果中的行、排名和实体，如“第一名”“最后一个”“这些经销商”。
- 沿用上一轮方案修改时间、过滤、排序、TopN 和展示维度。
- 对上一轮结果做轻量解释、筛选或再次聚合。
- 根据上一轮实体键发起补充查询，例如从经销商结果继续查询业务经理联系方式。

第一阶段不直接支持：

- 将任意多轮大结果全部写入 Prompt。
- 跨 Topic 自动引用结果。
- 没有实体键或字段来源时凭文本猜测结果行对应的物理记录。
- 结果快照已过期后静默复用旧数据。

### 12.6 预计改动范围

优先在现有架构上迭代：

- `state/topic_state.py`：增加结果快照、pending 列表和 follow-up 上下文。
- `state/analysis_spec.py`：将单个 pending 兼容升级为可审计澄清记录。
- `services/metric_clarification_service.py`：支持 pending 注册表、活动项选择和延迟编号解析。
- `nodes/planner_node.py`：在 LLM 解析前消费确定性选择，并接收结构化 follow-up context。
- `graphs/supervisor_graph.py` 或现有入口节点：增加连续问答分类，不新增独立 Agent。
- `nodes/build_final_answer_node.py`：查询成功后生成 `QueryResultSnapshot`。
- `tests/`：增加结果追问、延迟回复、多 pending 冲突和 Topic 隔离回归。

### 12.7 验收场景

1. 查询完成后问“第一名的业务经理联系方式是什么”，能够引用上一轮实体继续查询。
2. 查询完成后问“换成最近 7 天”，只修改时间范围，保留指标、维度和 Join 方案。
3. Advisor 给出指标选项后，用户连续询问两轮口径解释，再回复“第二个”，仍命中最初 option 2。
4. 候选在后台重新召回并改变排序后，延迟回复编号仍按原 options 解析。
5. 同时存在两个 pending 时回复“第二个”，系统不猜测并要求指出业务概念。
6. 用户明确说“新增订单选第二个”时，只解决对应 pending。
7. 新建 Topic 后回复“第二个”，不能读取旧 Topic 候选。
8. 上一轮结果不存在或已过期时，“第一名是谁”返回可解释提示，不编造结果。
9. 日志能够关联 `result_id / clarification_id / source_request_id`，还原连续问答链路。

### 12.8 评估指标

- 结果追问识别准确率。
- QueryPlan 槽位继承正确率。
- 延迟编号选择成功率。
- stale pending 误解析率，目标为 0。
- 多 pending 冲突时的安全拒绝率。
- 连续问答平均额外澄清轮次。
- 结果快照复用后的端到端执行正确率。

## 十二·五、第13.5课：元数据规模化接入与增量同步（任务书）

### 本课目标

在不手写 500 张表白名单的前提下，让系统安全接入数仓全量表，并保证元数据（字段、备注、枚举值）变化可自动同步：

1. 白名单配置化：库级白名单 + include/exclude 表 + 可选正则，废弃表治理。
2. schema 指纹增量采集：表级指纹粗筛、字段级 diff，只对新增/变更字段做采样与 LLM 增强。
3. 变更同步：字段增删改、枚举刷新、向量索引 upsert/delete，全链路可审计可重跑。

### 为什么必须先做

第14-21课（语义层、BM25、向量检索、评估）需要在 500 表真实规模上验证。如果仍靠 5 张表手写白名单，检索质量和评估结论无法外推；如果全量采集不做增量，增强成本与运行时长不可接受；如果没有变更同步，字段/备注/枚举变化会导致检索到过期元数据。

### 里程碑与验收

#### M1 白名单配置化与门禁改造

- 新增 `agentTest/config/metadata.yaml`（`metadata_scope` 配置块）：`databases`（库级白名单）、`include_tables`（空=库下全部；支持 `db.table` 精确指定某库下表，推荐使用）、`exclude_tables`（废弃/内部表）、`include_patterns`（可选正则，仅 include_tables 为空时生效）、`auto_retire_missing`（Hive 中已消失表是否自动治理）。
- 新增 `db/metadata_scope.py` 作为接入范围单一事实源，供元数据采集层与 SQL 门禁层共用；配置缺失或解析失败时回退默认 5 表白名单，安全边界不因配置错误失效。
- `include_tables` 裸表名仅在所有白名单库中唯一时生效（跨库同名必须写 `db.table`，避免不同库下同名表被全部加入）；`list_tables` 按表名出现次数做唯一性判定。
- `hive_guardrails.py` 改为从配置加载并新增 `is_table_allowed(table, db)`；`sql_ast_guardrails.check_table_whitelist` 支持 `allow_table_fn` 回调做 `db.table` 精确判定；`sql_safety_validator.py` 与 `sql_validate.py` 同步接入统一判定。
- `HiveMetadataProvider.list_tables` 增加可选 `with_comment` 参数批量补全表备注（默认关闭，避免表多时变慢；缓存命中时也会补查，并复用 `_table_schema_cache` 避免重复查询）；`describe_table` 额外执行 `describe formatted` 解析表备注，并通过缓存定位表所属库后做白名单校验。
- 验收：5 张表手写白名单可清空，库下全部表可被采集；跨库同名表需 `db.table` 精确配置；废弃表被排除且 SQL 门禁拒绝访问。

#### M2 schema 指纹增量采集（已完成）

- 新增 `metadata_sync_state` 表：`database_name/table_name/table_fingerprint/column_fingerprints/last_synced_at`（表结构建在 `mysql_store.init_metadata_tables`，幂等）。
- 新增 `metadata/schema_fingerprint.py`：字段指纹（名+类型+注释）与表指纹（字段指纹+表注释）的 sha1 计算，以及字段级 diff（新增/修改/删除）。
- `metadata_enricher._enrich_columns` 增加指纹前置过滤：指纹一致整表跳过；变化则字段级 diff，新增/修改字段重新采样 + LLM 增强，删除字段清理 `enriched_columns`。
- 修改字段强制重增强（不再被 `column_exists` 断点续跑跳过）；表级增强在表不存在、字段有变化或表注释变化时重跑（表备注写入 `enriched_tables.original_comment`）；`auto_retire_missing=True` 时清理 Hive 中已消失表的增强数据与指纹状态。
- 采样 SQL 已回滚硬编码 `pt_dt`（恢复 `SELECT DISTINCT ... WHERE col IS NOT NULL AND col != ''`）。
- 并发/限流本轮未做（保持串行，避免引入不稳定），全流程幂等，失败可重跑。
- 验收：二次运行无变化表全部跳过；新增/修改/删除字段只处理对应字段（mock 链路验证通过）。

#### M3 变更同步与向量索引 upsert（已完成）

- 新增 `metadata_change_log` 表：记录 `column_added/column_modified/column_removed/enum_refreshed/table_retired` 事件（审计 + 可回放），写入点覆盖 enricher diff 与枚举刷新。
- `SchemaVectorStore` 新增 `sync_documents()`：按唯一键 upsert/delete（新增追加、page_content 变化删除重写、MySQL 消失删除向量）；`load_or_build()` 复用同一逻辑。
- `refresh_enum_samples.py` 增加 `--refresh`：强制刷新指定表/字段，内容变化才写库 + 记录事件 + 同步 column 向量层。
- 新增 `scripts/sync_metadata.py`：采集（diff）+ 增强 + 向量同步一体，支持 `--force/--skip-vector/--dry-run`。
- `build_indexes.py` 抽出 `run_build_all()` 供 CLI 与 sync_metadata 复用，默认即增量同步（upsert/delete）。
- 验收：修改字段注释/枚举后运行同步，MySQL 与向量索引均更新；删除字段后向量中不再召回（FakeEmbeddings 验证新增/更新/删除/幂等/全删通过）。

### 涉及文件（M2/M3 实际落地）

- 新增：`agentTest/config/metadata.yaml`、`metadata/schema_fingerprint.py`、`scripts/sync_metadata.py`、`db/metadata_scope.py`（M1）。
- 修改：`db/hive_guardrails.py`、`db/sql_ast_guardrails.py`、`metadata/hive_meta_provider.py`、`metadata/metadata_enricher.py`、`metadata/mysql_store.py`、`langchain_app/vectorstores/schema_vector_store.py`、`langchain_app/app_builder.py`、`scripts/build_indexes.py`、`scripts/refresh_enum_samples.py`、`langgraph_app/services/sql_safety_validator.py`、`validate/sql_validate.py`。

### 评估指标

- 全量接入后检索准确率（对比 5 表基线）。
- 增量同步耗时：无变化表整表跳过率目标 100%，单次运行分钟级。
- 变更感知时效：字段/备注/枚举变化到索引生效的时间。
- 废弃表误召回率，目标为 0。

## 十三、第14课：最小语义层对象模型

### 13.1 本课目标

建立可执行、可检索的四类语义对象：

- `Metric`：指标名称、别名、说明、计算方式、默认聚合和默认时间字段。
- `Dimension`：维度名称、别名、所属实体、物理来源和枚举信息。
- `Entity`：订单、经销商、渠道等业务实体及其业务键。
- `BusinessTerm`：业务术语、简称、同义词、标准值和目标维度。

### 13.2 设计边界

- 复用现有 `SemanticMetadataProvider`，不在 Planner、Prompt 或 Hive Provider 中写死业务口径。
- 语义对象使用稳定 ID、版本、启用状态和负责人字段。
- 语义对象不保存 Topic、用户消息或临时查询状态。
- 物理 Schema、关系元数据和业务语义保持分层，但可以通过稳定 ID 相互引用。

### 13.3 验收标准

- 一个业务指标可以唯一定位到语义对象。
- 同义词、简称和中文业务名能够映射到同一对象。
- 禁用或版本过期的对象不会进入运行时候选。
- 新增语义对象不需要修改 Planner 核心代码。

---

## 十四、第15课：指标口径与物理绑定

### 14.1 本课目标

建立语义对象到物理数据的确定性映射：

- 指标到事实表、字段或计算表达式的绑定。
- 维度到来源表、来源字段和实体的绑定。
- 指标支持维度、默认时间字段和适用粒度。
- 指标固定过滤、用户业务过滤和系统逐表必选过滤的来源隔离。
- 语义对象到 `field_sources`、`table_plans` 和 ExecutionPlan 的转换规则。

### 14.2 关键约束

- 指标固定过滤不能被用户过滤覆盖。
- `pt_dt` 等必选过滤继续由 Guardrails 管理，不写入指标定义。
- 指标与维度不兼容时必须澄清或拒绝，不能由 LLM 临时拼接口径。
- 多表绑定必须复用关系元数据和 JoinPlanner，语义层不能直接生成未经审核的 Join。

### 14.3 验收标准

- 同一版本指标只有一个明确计算口径。
- 每个字段来源都能追溯到语义对象和物理元数据。
- 业务过滤允许各表不同，系统过滤对所有参与表分别生效。
- 语义绑定失败时返回具体缺失项，而不是退化为模型猜测。

## 十五、第16课：语义文档与索引单元

### 15.1 本课目标

将指标、维度、实体、业务术语、表、字段和典型查询案例转换为独立检索文档，不直接把完整 JSON 或整张 Schema 作为一个大文档写入索引。

每个文档至少携带：

```text
document_type
semantic_id
name
aliases
description
domain
tables
entities
version
enabled
content_hash
```

### 15.2 文档类型

- 指标文档：业务解释、公式、固定过滤、时间字段和支持维度。
- 维度文档：业务名称、别名、实体和物理来源。
- 表文档：业务用途、数据粒度、主键、时间字段和可连接实体。
- 字段文档：业务名称、物理名称、类型、枚举值和所属语义对象。
- 案例文档：典型问题、命中指标、维度、过滤和涉及表。

### 15.3 验收标准

- 每个文档具有唯一 ID 和明确类型。
- 相同对象内容未变化时不重复构建索引。
- 对象禁用或删除后，对应检索文档可以同步失效。
- 文档模板支持 BM25 与向量检索分别使用适合的内容字段。

## 十六、第17课：BM25 关键词检索

### 16.1 本课目标

建立独立的 BM25 召回链路，优先解决精确业务词、英文缩写、业务编码、表名和字段名检索。

### 16.2 课程内容

- 中文分词和业务词典。
- `company_id` 等标识符拆词。
- 名称、别名、说明和物理字段的字段权重。
- 按 `document_type`、数据域、版本和启用状态过滤。
- BM25 TopK、分数解释和调试日志。

### 16.3 验收标准

- 精确指标名和字段名稳定出现在 Top1。
- 英文缩写、编码和中文专有词能够正确召回。
- 指标、维度、表和字段可以分别检索。
- BM25 单路召回具有独立基线指标。

## 十七、第18课：向量语义检索升级

### 17.1 本课目标

将现有库、表、字段三级向量检索升级为语义对象召回，重点支持口语化表达、同义改写和不包含原始关键词的查询。

### 17.2 课程内容

- 指标、维度、字段使用不同文档模板生成 embedding。
- 复用现有 FAISS 增量构建和内容指纹能力。
- 增加 embedding 模型版本和索引版本。
- 按文档类型分别设置召回数量和相似度阈值。
- 保留物理 Schema 检索作为证据和兜底，不让其覆盖权威业务语义。

### 17.3 验收标准

- 口语化问题能够召回正确指标或维度。
- 同义改写场景下向量召回优于纯 BM25。
- 索引增量更新不会重复写入未变化文档。
- 向量低置信度时不强行返回唯一答案。

## 十八、第19课：BM25 + RAG 混合召回

### 18.1 本课目标

并行执行 BM25 与向量召回，第一版使用 Reciprocal Rank Fusion（RRF）按排名融合，不直接线性相加两种不同尺度的原始分数。

```text
BM25 TopK ─┐
            ├→ RRF 融合 → 去重 → 类型配额 → 候选语义对象
Vector TopK ─┘
```

### 18.2 关键策略

- 保留每条候选的召回来源、原始排名和融合分数。
- 同一 `semantic_id` 多路命中时合并证据。
- 不同文档类型设置候选配额，避免字段文档淹没指标文档。
- 根据 AnalysisSpec 先做数据域和对象类型过滤，再进行融合。

### 18.3 验收标准

- 精确词问题不低于 BM25 单路效果。
- 同义改写问题不低于向量单路效果。
- 混合问题的正确候选排名优于任意单路基线。
- 无关问题能够保持低置信度并进入澄清或拒绝。

## 十九、第20课：重排与 Planner 接入

### 19.1 本课目标

将混合召回候选转换为 Planner 可使用的可靠语义候选，并保持现有 Advisor 单轮锁定和最终一次确认协议。

### 19.2 处理顺序

```text
混合召回 TopK
  ↓
权限、版本、类型和数据域硬过滤
  ↓
指标维度兼容性、粒度和 Join 可达性过滤
  ↓
规则重排或 LLM Reranker
  ↓
Planner 候选
  ↓
Advisor 澄清或生成 locked_plan
```

### 19.3 LLM 边界

- 可以判断候选与用户问题的语义相关性。
- 可以解释口径差异并生成澄清问题。
- 不允许自创指标、字段、公式和未启用关系。
- 不允许绕过权限、逐表必选过滤和 SQL Guardrails。

### 19.4 验收标准

- 候选充分且无歧义时，当前轮直接生成真实 `locked_plan`。
- 候选存在业务歧义时，只询问业务口径，不让用户选择物理字段。
- 检索结果不能直接进入 Seeker，必须经过 Planner/Advisor 契约。
- 日志能够还原召回、融合、过滤、重排和最终锁定过程。

## 二十、第21课：检索评估与消融实验

### 20.1 本课目标

建立带标准答案的检索评估集，分别评估指标、维度、业务术语、表和字段召回，并证明混合检索相对单路检索的真实收益。

### 20.2 评估指标

- `Recall@K`、`MRR`、`NDCG@K`。
- 指标识别准确率和维度识别准确率。
- 表召回率和无答案拒绝率。
- 平均澄清轮次和重复确认率。
- 最终 QueryPlan 正确率、SQL 执行成功率和口径一致率。
- 检索、重排和完整问数链路的 P50/P95 耗时。

### 20.3 消融实验

至少比较以下组合：

1. 仅 BM25。
2. 仅向量检索。
3. BM25 + 向量 RRF。
4. 混合召回 + 规则重排。
5. 混合召回 + LLM Reranker。
6. 混合召回 + 语义层硬约束。

### 20.4 验收标准

- 评估集覆盖精确词、同义改写、混合表达、歧义和无答案问题。
- 每次调整分词、embedding、融合或重排策略后可以重复评估。
- 课程结论由指标支持，而不是只根据少量演示样例判断。

## 二十四、第25课：功能验收与演示闭环

### 24.1 必须通过的场景

1. 精确业务词通过 BM25 命中正确语义对象。
2. 口语化和同义改写通过向量检索命中正确对象。
3. 混合问题通过 RRF 和重排提升正确候选排名。

8. 自动判断单表足够，不产生多余 Join。

### 24.2 功能阶段完成标准

- 语义检索、单表、多表和分析查询共享统一业务契约。
- 混合检索相对 BM25 和向量单路具有可量化收益。
- Join 关系、指标口径和检索文档均可配置和追溯。
- SQL 生成不能突破 ExecutionPlan 和 Guardrails。
- 失败场景有明确、可解释的澄清或拒绝原因。

## 二十五、功能完成后的优化课程

### 第26课：上下文裁剪与 Topic 摘要

- 限制传给 LLM 的历史消息数量。
- 保留原始问题、QueryPlan、AnalysisSpec、最近轮次和关键工具结果。
- 检索候选、ExecutionPlan、Schema Context 和查询结果避免长期重复写入消息历史。

### 第27课：Checkpointer 与历史恢复

- 将 `MemorySaver` 替换为持久化 Checkpointer。
- 服务重启后恢复 Topic、confirmed_plan 和必要消息。
- ExecutionPlan 根据语义元数据和关系元数据版本决定恢复或重新派生。

### 第28课：并发、幂等与失败恢复

- 使用 `request_id` 防止重复追加消息和重复执行 SQL。
- 限制同一 Topic 并发修改 QueryPlan。
- 区分安全重试、重新规划和新 Topic。
- 防止并发索引构建覆盖稳定的 BM25 或向量索引版本。

### 第29课：部署、监控与性能优化

- 健康检查、配置环境变量化和进程部署。
- 统计 BM25、向量、混合召回和重排各阶段耗时与命中率。
- 统计单表命中率、多表规划率、Join 拒绝率和 SQL 首次成功率。
- 优化元数据检索、关系图查询、Prompt 长度和 SQL 执行成本。
- 根据需要接入 Prometheus、Grafana 或 OpenTelemetry。

### 第30课：简历与面试材料

- 系统架构图、语义检索链路和双层计划数据流。
- BM25 + RAG 混合检索、RRF、重排和消融实验指标。
- 多表 Join 安全设计和分析查询 IR。
- 真实问题、根因、方案取舍和量化指标。
- 演示脚本、项目描述和常见面试追问。
