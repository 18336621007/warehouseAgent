## 一、课程目标与约定

### 1.1 当前优先级

1. 建立正确、可维护的短期对话记忆。
2. 完成单表查询的方案确认、精确 Schema 加载、SQL 安全校验和异常处理闭环。
3. 让单表问数项目具备单机上线、服务重启恢复和线上故障定位能力。
4. 扩展更多库表时不需要频繁修改核心 Agent 代码。
5. 单表链路达到上线标准后，再建设语义层编译和企业级多表 Join。
6. 补齐工程文档和量化指标，形成可写入简历的完整项目。

### 1.2 暂不进入的内容

- 暂不建设完整语义层。
- 暂不开放多表 Join 查询执行，只预留计划契约并整理表关系元数据。
- 暂不接入新的业务数据源。
- 暂不为了完全复现论文而保留不适合当前项目的设计。
- 暂不安排自动化测试课程，优先通过代码检查、日志和手动场景验证理解功能。

### 1.3 上课方式

1. 每课先讲知识点、当前问题和设计原因。
2. 再明确需要修改的文件、位置和完整代码。
3. 默认由用户自己修改，除非用户明确说“帮我修改代码”。
4. 用户修改后再进行代码检查，不顺手修改无关代码。
5. 每课结束更新本文档的进度和遗留问题。
6. 每课在 `docs/课程复盘/` 下新建独立 Markdown，记录实际困难、根因、方案取舍、验证过程和面试表达。

### 1.4 DataAgent 能力借鉴原则

- 不迁移到 Spring AI Alibaba DataAgent，继续使用当前 Python + LangGraph 架构。
- 借鉴其知识约束、独立问题改写、可行性评估、表关系和 SQL 语义一致性设计，不照搬完整平台。
- 暂不建设重型语义层，先用可维护的轻量业务知识表解决指标口径、同义词和固定过滤条件。
- Planner 和 Advisor 负责语义检索与消歧；Seeker 只执行用户确认后的 `confirmed_plan`，不再自行语义选表选字段。
- 业务人员只确认指标、维度、时间和过滤口径，不要求理解物理表、字段、SQL 或 Join 条件。
- 未来多表阶段由模型识别业务概念，由表覆盖分析、语义层编译器和确定性 Join Planner 生成物理执行方案，禁止模型自由猜测 Join。
- 保留 Evaluator 自动沉淀高质量示例的反馈闭环，形成区别于纯人工知识维护的项目亮点。

## 二、已经完成的记忆系统基础

### 2.1 State 基础整理

- Planner、Advisor、Seeker 统一通过父图 `AgentState` 协作。
- 建立 `IdentityState → TopicState → BaseState → 各模块State` 的继承结构。
- 将问题字段拆分为：
  - `original_question`：当前 Topic 的原始问题。
  - `current_user_input`：用户本轮真实输入。

### 2.2 三层身份模型

- `conversation_id`：前端的一个完整对话。
- `topic_id`：对话中的一次独立查数任务。
- `request_id`：一次 HTTP 请求或一次图调用。
- 已确认一个 `conversation_id` 可以包含多个 Topic。
- 新 Topic 不继承上一个 Topic 的查数状态。

### 2.3 Checkpoint 隔离

- LangGraph 内部使用：

```python
graph_thread_id = f"{conversation_id}:{topic_id}"
```

- 同一 Topic 的 Advisor 多轮追问复用同一个 checkpoint。
- Seeker 完成后，下一次查数创建新的 `topic_id`。
- 产品 API 已统一使用 `conversation_id`，仅 LangGraph 配置保留框架要求的 `thread_id`。

完整设计见 [State 与记忆系统架构](../架构/State与记忆系统架构.md)。

## 四、第1课：Graph State 成为唯一记忆源

### 4.1 改造前问题

当前 Topic 记忆同时存在于两处：

- Flask `sessions` 保存 `original_question`、`advisor_turns`、`advisor_last_answer`。
- LangGraph checkpoint 也保存 State。

两套状态可能不一致。例如 Web 状态已经重置，但 checkpoint 仍保留旧值；或者 checkpoint 更新成功，Web 层更新失败。

### 4.2 本课目标

- Flask 只负责保存当前 `topic_id`、前端展示消息和会话标题。
- `original_question`、`advisor_turns`、`advisor_last_answer` 全部由 Graph State 管理。
- Web 每轮只传入身份字段和 `current_user_input`。
- Planner 初始化原始问题，Advisor 更新澄清轮次和上一轮回复。

### 4.3 计划修改文件

- `agentTest/langgraph_app/state/base_state.py`
- `agentTest/langgraph_app/state/planner_state.py`
- `agentTest/langgraph_app/state/seeker_state.py`
- `agentTest/langgraph_app/nodes/planner_node.py`
- `agentTest/langgraph_app/graphs/advisor_graph.py`
- `web/server.py`
- `agentTest/langgraph_app/demo.py`

### 4.4 验收标准

- `web/server.py` 不再向图传入 `original_question`、`advisor_turns`、`advisor_last_answer`。
- Web `sessions` 不再保存上述三个业务状态字段。
- Advisor 连续追问时，`advisor_turns` 由 checkpoint 自动累积。
- 用户输入“1”“第二个”等短回答时，Planner 仍能理解上一轮 Advisor 给出的选项。
- 新 Topic 使用新 checkpoint，不继承旧 Topic 的状态。

本课已完成，Graph State 已成为 Topic 业务状态的唯一来源。

## 五、第2课：统一消息记忆模型

### 5.1 改造前问题

系统同时存在：

- `messages`
- `advisor_messages`
- `advisor_last_answer`
- Web `session["messages"]`

它们用途有重叠，后续容易出现消息重复、顺序错误和字段无法删除的问题。

### 5.2 本课目标

- `messages` 作为当前 Topic 的标准对话记忆。
- 使用 LangGraph `add_messages` reducer 增量追加消息。
- Planner 从 `messages` 中获取上一轮 Advisor 回复。
- Advisor 从 `messages` 中构造本轮上下文。
- Web 展示消息与 Graph 业务消息职责分离，不把工具消息直接暴露给前端。

### 5.3 验收标准

- 已删除 State 字段 `advisor_last_answer`。
- 已删除 `advisor_messages`，统一使用 `messages`。
- 每个节点只返回本轮新增消息，不重复返回完整历史。
- ToolMessage、AIMessage、HumanMessage 的顺序正确。

本课已完成，用户、Advisor、工具和 Seeker 消息已统一进入 Topic 消息记忆。

## 六、第3课：confirmed_plan 契约与精确执行（已完成）

### 6.1 完成后的方案链路

```text
Planner 使用表级、字段级 FAISS 识别需求和候选
    ↓
partial/none → Advisor clarification_agent，只检索并追问
    ↓ 用户补充后 Planner 重新判断
full → Advisor plan_agent 核对库、表、字段
    ↓
Advisor 调用 submit_query_plan
    ↓
lock_query_plan() 标准化并写入 status=locked
    ↓
Advisor 展示完整方案，等待用户确认或修改
    ↓
Planner 判断用户是否接受完整 locked 方案
    ↓
confirm_query_plan() 校验并写入 status=confirmed
    ↓
QueryPlanSchemaResolver 精确校验库表字段并加载物理 Schema
    ↓
Seeker 生成、校验和执行 SQL
```

### 6.2 已完成改造

- 新增 `QueryPlan` 契约，统一 `table/tables/measures/dimensions/fields/time/filters/status`。
- 使用 `locked → confirmed` 区分“方案已形成”和“用户已授权执行”。
- Advisor 改用 `submit_query_plan`，由 `lock_query_plan()` 派生 `tables/fields/status/locked_at`。
- Advisor 按 `completeness` 拆分为 `clarification_agent` 和 `plan_agent`；`partial/none` 模式不绑定提交工具。
- Advisor 图级代码已经尝试读取 `planner_reason`，但 `AdvisorState` 尚未声明该字段，跨子图传递仍待通过 `PlannerHandoffState` 修复。
- Planner 通过模型理解用户确认或修改，不使用确认关键词硬编码；程序校验失败时仍返回 Advisor。
- Planner 当前代码仍保留候选数量硬路由；设计已确认删除其路由作用，只保留候选统计，安全性继续由完整度判断、Advisor 工具门禁、QueryPlan 校验和用户确认保证。
- 新增 `QueryPlanSchemaResolver`，只接受 `status=confirmed` 的单表方案。
- Resolver 精确校验 `database.table`、跨库同名表、物理表身份和字段存在性。
- Seeker 已移除对 `enriched_faiss_index`、通用 `runtime["retriever"]` 和旧 enrich 节点的依赖。
- 当前 `retrieve_schema` 节点只负责调用 Resolver 并写入 `schema_context`。

### 6.3 当前实现边界

- 当前上线版本只支持单表，`tables` 为未来多表 Join 保留契约空间。
- `filters` 仍为字符串，因此 Resolver 加载确认表完整物理 Schema，而不是只裁剪 `fields`。
- `HiveMetadataProvider.describe_table()` 当前使用裸表名；存在跨库同名表时 Resolver 选择拒绝执行，而不是临时增加 Provider 特例。
- GenerateSQL 的 fallback 仍有单表和聚合假设，后续上线前需要继续收紧异常处理和可解释失败。
- `SeekerState.schema_documents/schema_candidate_ids` 与子 State 重复声明的 `confirmed_plan` 仍残留在类型定义中，但已不属于活动链路，后续可做一次低风险清理。

### 6.4 实际修改文件

- `langgraph_app/state/query_plan.py`
- `langgraph_app/services/query_plan_service.py`
- `langgraph_app/services/query_plan_schema_resolver.py`
- `langgraph_app/tools/submit_query_plan.py`
- `langgraph_app/graphs/advisor_graph.py`
- `langgraph_app/nodes/planner_node.py`
- `langgraph_app/nodes/retrieve_schema_node.py`
- `langgraph_app/graphs/seeker_graph.py`
- `langgraph_app/runtime/graph_runtime.py`
- `langchain_app/app_builder.py`
- `langchain_app/tools/tool_factory.py`

### 6.5 验收结论

- 没有完整且最终确认的 `confirmed_plan` 时无法进入 Seeker。
- Seeker 不再根据原始问题重新召回表和字段。
- 物理 Schema 加载能追溯到唯一确认表，并校验确认字段存在。
- 非法方案、缺失元数据和跨库同名表会明确失败，不会被静默兜底掩盖。
- `partial/none` 请求的 Advisor 工具调用中不会出现 `submit_query_plan`，日志应显示 `模式=clarify` 和 `locked=False`。
- 单表执行主链路已具备继续建设 Topic 状态机和上线可观测性的基础。

## 七、第4课：Topic 生命周期状态机

### 7.1 本课目标

正式使用 `topic_status` 管理 Topic：

```text
new → clarifying → confirmed → generating_sql
    → validating_sql → executing → completed
                              └→ failed
```

### 7.2 关键收益

- 前端可以显示“正在澄清”“正在生成 SQL”等真实状态。
- 服务端不再仅依赖 `_new_topic` 这样的临时布尔标记。
- 失败后可以判断应该重试当前 Topic，还是创建新 Topic。
- 为后续恢复未完成任务和排查线上问题建立基础。

## 八、第5课：状态可观测性与全链路日志（已完成）

### 8.1 本课目标

- 建立统一日志上下文，让每条日志自动包含 `conversation_id/topic_id/request_id/graph_thread_id`。
- 增加请求开始、请求结束、节点执行、路由决策、关键 State 变化和异常六类日志。
- 记录 `topic_status`、`route`、`confirmed_plan` 有效性和重试次数等关键状态变化。
- 异常日志保留错误类型、错误编号和完整堆栈，前端只展示安全的错误提示。
- 补齐 `capture_user_message`、Schema 上下文增强等当前缺少日志的关键节点。

### 8.2 日志字段规范

```text
timestamp / level / event
conversation_id / topic_id / request_id / graph_thread_id
node / route / topic_status / duration_ms / retry_count
status / error_type / error_id
```

- 不直接打印完整 Graph State、完整查询结果和密钥。
- SQL、用户问题和业务字段根据部署环境决定是否截断或脱敏。
- 本地日志不再在服务启动时清空，改为按日期或文件大小滚动保留。
- 当前阶段先完成结构化文件日志和状态查看工具，不急于引入 Prometheus、Grafana 等外部平台。

### 8.3 实现结果

- 日志文件统一为 `agentTest/logs/langgraph_app.jsonl`，每行一个 JSON 对象。
- 使用 `ContextVar` 在 Web/CLI 请求入口绑定四个身份字段，业务节点无需重复传参。
- 已覆盖 `request/node/route/state/error/degraded` 等事件，并记录节点耗时和关键状态摘要。
- 使用按天滚动策略保留 14 天日志，不再在 Runtime 启动时清空历史日志。
- 请求级异常生成 `error_id`，完整异常和堆栈仅写服务端日志，前端只展示安全提示。
- 日志查看、PowerShell 查询命令和典型问题排查见 [日志使用与问题排查指南](../指南/日志使用与问题排查指南.md)。

### 8.4 验收标准

- 可以通过任意一个 `request_id` 找到该请求经过的全部节点、路由和最终状态。
- 可以通过 `conversation_id + topic_id` 还原同一 Topic 的多轮状态变化。
- 并发请求的日志不会互相混淆。
- 节点异常能够定位到具体代码堆栈，且不会只剩一条 `str(error)`。
- 提供 PowerShell 只读查询命令和独立指南，可按 `request_id/topic_id/error_id` 查看链路；Checkpoint Debug API 留待后续工程化课程。

## 十、第7课：Checkpointer 持久化

### 10.1 当前问题

`MemorySaver` 只保存在当前 Python 进程内，服务重启后全部丢失，也不适合多进程部署。

### 10.2 分阶段方案

1. 开发和单机演示阶段：使用文件型持久化 Checkpointer，验证恢复流程。
2. 正式部署阶段：使用适合多进程访问的数据库型 Checkpointer。
3. 通过工厂函数创建 Checkpointer，避免业务图绑定具体存储实现。

### 10.3 验收标准

- 重启服务后，用相同 `conversation_id:topic_id` 可以恢复状态。
- Supervisor 图不直接写死 `MemorySaver()`。
- 存储连接配置放入配置文件或环境变量。

## 十二、第9课：记忆异常与幂等处理

### 12.1 本课目标

- 使用 `request_id` 防止同一请求重复执行 SQL。

## 十三、第10课：轻量业务知识与多库多表配置化

### 13.1 本课目标

- 新增库表时不修改 Planner、Advisor、Seeker 的业务代码。
- 元数据增强、索引构建和字段类型加载支持增量更新。
- 为数据库、表和字段增加统一的稳定标识。
- 记录索引版本，避免代码与旧索引结构不兼容。
- 建立轻量业务知识表，管理指标名称、同义词、计算公式、固定过滤条件、适用表和版本。
- 将当前代码中的少量 `SEMANTIC_ENTRIES` 逐步迁移为可维护数据，而不是继续堆积静态规则。
- 轻量业务知识只为 Planner 和 Advisor 提供约束，不直接替代用户确认后的 `confirmed_plan`。

### 13.2 验收标准

- 新增一批库表后，只需运行元数据和索引脚本。
- 新增指标别名或口径时不需要修改 Agent 核心代码。
- Planner 能先定位库和表，再检索字段。
- Seeker 根据完整的 `confirmed_plan` 精确加载库表字段，不再回到全量混合索引盲搜。

## 十四、第11课：独立问题改写与可行性评估

### 14.1 本课目标

- 使用 `original_question`、`current_user_input`、`topic_summary` 和最近消息生成可独立理解的 `standalone_query`。
- 解决“那上个月呢”“换成订单量”“按地区看”等多轮省略表达。
- 用户已经确认方案后，普通确认词不重新改写业务含义，优先保留 `confirmed_plan`。
- 增加可行性评估，判断当前数据和元数据是否足以回答用户问题。
- 将评估结果划分为 `answerable`、`needs_clarification` 和 `unsupported`，避免无法回答时仍生成 SQL。

### 14.2 路由规则

- `answerable`：继续进入方案确认或执行阶段。
- `needs_clarification`：路由 Advisor 补充时间、指标、维度或过滤条件。
- `unsupported`：明确说明当前数据无法回答，并记录缺失的数据能力。
- 记录问题改写前后内容和评估理由，但不把大段检索上下文写入 checkpoint。

## 十五、第12课：元数据规模化与表关系准备

### 15.1 本课目标

- 建立数据库 → 表 → 字段的分层候选链路。
- Planner 和 Advisor 使用分层向量检索完成业务语义消歧。
- 扩展更多库表时继续保证每次只锁定一个能够完整覆盖当前需求的目标表。
- 建立物理外键、逻辑外键、表粒度、关系基数和常用 Join 条件的关系元数据，但本课不开放多表执行。
- 对跨库同名表、同名字段进行消歧，为未来表覆盖分析和 Join Path Planner 提供稳定标识。
- 将单表确认结果写入当前查询计划，不把未确认候选传给 Seeker。
- 降低库表数量扩大后的向量检索噪声。
- 当单表无法覆盖用户需求时，当前阶段返回 `unsupported` 或说明能力边界，不允许 LLM 自由生成 Join。

### 15.2 重点指标

- 正确库、表、字段的 Top-K 命中率。
- 单表问题的完整字段覆盖率和最终选表准确率。
- 无关候选数量和平均澄清轮数。
- 新增库表后的索引构建时间和检索耗时。
- 表关系元数据的完整率、重复关系数量和非法关系数量。

### 16.1 本课目标

## 十八、扩展课A：语义层编译与企业级多表 Join

> 本扩展课只在单表问数链路达到上线标准后开始，不影响当前课程优先级。

### 18.1 开课前置条件

- Seeker 已完全由最终确认方案驱动精确 Schema 加载，不存在向量检索兜底。
- 单表 SQL 生成、方案一致性校验、权限控制、分区限制和执行异常处理已经稳定。
- Checkpointer 持久化、历史恢复、幂等处理、全链路日志和健康检查已经完成。
- 新增单表只需要更新元数据和配置，不需要修改 Planner、Advisor、Seeker 核心代码。
- 已通过实际场景验证单表选表准确率、SQL 首次成功率和请求耗时满足上线要求。

### 18.2 用户与系统职责

- 业务人员只确认指标、维度、时间范围、过滤条件和业务口径。
- 业务人员不需要选择物理表、字段、Join 类型或关联条件，也不需要阅读 SQL。
- LLM 负责理解业务问题、识别业务概念和判断是否存在业务歧义。
- 表覆盖分析器负责判断一张表是否能够完整覆盖需求。
- 语义层编译器负责将业务计划映射为物理表、字段、聚合和过滤方案。
- Join Path Planner 只允许使用已配置的表关系、字段关系和基数信息，禁止模型自由猜测 Join。

### 18.3 目标架构

```text
BusinessQueryPlan
    ↓
业务概念识别
    ↓
TableCoverageAnalyzer
    ├─ 单表完整覆盖 → 单表 PhysicalExecutionPlan
    └─ 单表无法覆盖 → SemanticPlanCompiler
                              ↓
                        JoinPathPlanner
                              ↓
                    多表 PhysicalExecutionPlan
                              ↓
                     Seeker 精确加载与执行
```

### 18.4 核心建设内容

- 建立业务指标、维度、实体、默认过滤条件和业务口径的语义元数据。
- 建立表粒度、字段归属、主外键、逻辑关联、Join 类型和关系基数元数据。
- 实现表覆盖分析，优先选择能够完整覆盖需求的单表，避免不必要的 Join。
- 实现确定性 Join 路径搜索，并处理多条路径对应不同业务含义的情况。
- 对业务歧义进行业务化追问，例如询问“下单城市还是注册城市”，不向用户询问物理关联字段。
- 检查一对多、多对多和事实表直接关联产生的度量膨胀风险。
- 支持按公共粒度预聚合后再关联，避免事实表 Join 导致重复计算。
- 让 Seeker 按 `PhysicalExecutionPlan` 精确加载多表 Schema，不重新进行语义选表。
- 扩展 SQL 一致性校验，检查表集合、字段归属、Join 条件、聚合粒度和过滤条件。

### 18.5 验收标准

- 单表能够覆盖时不会生成不必要的 Join。
- 多表执行方案中的每条关系都可以追溯到已配置的关系元数据。
- 模型无法绕过 Join Planner 使用未配置关联条件。
- 存在多个业务含义不同的关联路径时，系统向用户追问业务口径而不是数据库细节。
- 无安全关联路径或存在无法消除的多对多膨胀风险时，系统明确拒绝执行。
- 可以通过日志还原业务计划、表覆盖判断、Join 路径选择、物理执行计划和最终 SQL。
