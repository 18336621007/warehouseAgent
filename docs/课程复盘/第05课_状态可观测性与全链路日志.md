# 第05课：状态可观测性与全链路日志复盘

> 日期：2026-07-31  
> 课程状态：已完成  
> 复盘用途：面试中说明请求链路追踪、结构化日志、并发上下文隔离和异常定位  
> [返回文档索引](../文档索引.md)

## 一、本课目标

让一次请求从 Web 或 CLI 入口进入 LangGraph 后，可以使用统一身份定位完整执行链路：

```text
conversation_id + topic_id + request_id + graph_thread_id
```

日志需要覆盖请求开始、节点执行、路由决策、关键状态变化、请求结束和异常，并能够回答以下问题：

1. 某次请求依次执行了哪些节点？
2. Planner 和 SQL Router 为什么选择当前分支？
3. Topic 状态在哪个节点发生了变化？
4. 请求失败在哪个节点，完整异常堆栈和错误编号是什么？
5. 同一 Topic 的多轮请求是否能够被正确串联？

## 二、当前发现的困难

### 困难一：现有日志无法定位到具体请求

当前日志已经记录节点、路由、耗时和部分业务摘要，但没有自动携带 `conversation_id/topic_id/request_id`。单用户串行调试时可以依靠日志顺序阅读，并发请求进入后会发生交错，无法可靠判断每行日志属于哪次请求。

### 困难二：直接向每个日志调用传递身份字段会造成重复代码

如果每个节点都手动编写：

```python
log_node_start(
    "planner",
    conversation_id=state.get("conversation_id"),
    topic_id=state.get("topic_id"),
    request_id=state.get("request_id"),
)
```

所有节点都会出现相同代码，新增节点时也容易漏传，不适合作为企业级统一日志方案。

### 困难三：现有日志文件不适合线上长期运行

`graph_logger.py` 目前直接向单个文件追加文本，`build_graph_runtime()` 启动时还会清空旧日志。它缺少日志级别、滚动保留、结构化字段和完整异常堆栈，无法满足线上问题追溯。

### 困难四：部分节点和路由没有日志

`capture_user_message`、`build_schema_context`、`enrich_schema_context` 尚未接入统一节点日志；`planner_router` 只返回路由结果，没有记录路由原因和当前状态。

### 困难五：异常只返回 str(error)

Web 当前捕获 Graph 异常后直接把 `str(error)` 返回前端，既可能暴露内部信息，又没有生成可供后端检索的 `error_id`，日志中也没有完整堆栈。

## 三、考虑过的方案

### 方案一：每个日志调用显式传入身份字段

优点是实现直接；缺点是重复代码多、容易漏传，并会让业务节点承担日志上下文管理职责，因此不采用。

### 方案二：使用 ContextVar 保存请求日志上下文

在 Web 或 CLI 请求入口绑定四个身份字段，`graph_logger` 在写日志时自动读取。`ContextVar` 能隔离不同线程和异步任务的上下文，节点不需要重复传递身份字段。

这是当前阶段采用的方案。

### 方案三：直接接入 LangSmith、OpenTelemetry 或外部日志平台

该方案能力更完整，但会增加部署依赖和学习成本。当前优先完成本地结构化日志和错误定位能力，后续再将相同字段接入外部可观测平台。

## 四、最终架构取舍

```text
Web/CLI 请求入口
  └─ bind_log_context(identity)
       └─ LangGraph 节点与路由
            └─ graph_logger 自动附加身份字段
                 └─ JSON Lines + 按日期滚动文件
                      └─ request_id / topic_id 查询工具
```

- Graph State 继续保存业务状态，日志上下文不重复写入新的 State 字段。
- State 中的身份字段是业务执行和 checkpoint 的事实来源，`ContextVar` 只负责当前执行上下文的日志传播。
- 日志使用稳定的 `event` 名称，不再依赖图标判断日志类型。
- 前端只返回安全错误提示和 `error_id`，完整堆栈仅写入服务端日志。
- 当前不引入 Prometheus、Grafana 和分布式追踪服务，避免单体上线阶段过度设计。

## 五、本课实施阶段

### 阶段一：统一请求日志上下文

- 在 `graph_logger.py` 增加 `bind_log_context()`、`reset_log_context()` 和上下文读取方法。
- Web 和 CLI 每轮请求开始时绑定身份字段，并在 `finally` 中释放上下文。
- 增加 `request.started`、`request.completed` 和 `request.failed` 事件。

### 阶段二：结构化日志与滚动保留

- 使用标准库 `logging` 和 `TimedRotatingFileHandler`。
- 每行输出一个 JSON 对象，保留时间、级别、事件、身份、节点、状态和耗时。
- 删除 Runtime 启动时清空日志的行为。

### 阶段三：补齐节点、路由和状态变化日志

- 补齐当前没有日志的节点。
- Planner Router 和 SQL Router 统一记录决策。
- 在日志中记录 `topic_status` 的前后变化，但不打印完整 Graph State。

### 阶段四：统一异常边界

- 捕获请求级未处理异常，生成唯一 `error_id`。
- 日志保存异常类型和完整堆栈。
- 前端只收到安全提示和 `error_id`。
- 区分核心查询失败与 Evaluator 等非核心后处理失败。

### 阶段五：只读排查工具

- 支持按 `request_id` 查看完整请求链路。
- 支持按 `conversation_id + topic_id` 查看多轮状态变化。
- 支持读取 checkpoint 的关键字段，不直接暴露完整 State。

- Planner Router 只记录最终路由、当前状态和方案状态，不重复输出 Planner 已记录的完整推理原因。

### 阶段三实现结果

- `graph_logger.py` 已新增 `request.started/request.completed/request.failed/state.changed` 四类事件接口。
- Web 在请求开始时记录输入长度、是否为 Topic 首轮和原状态，在查询结束时记录最终状态、路由、节点数量和总耗时。
- Web 直接消费 LangGraph 的节点增量更新，集中识别 `topic_status` 的真实变化，相同状态不会重复记录。
- Planner Router 已记录最终决策、元数据完整度、Topic 状态和 QueryPlan 状态，不重复打印 Planner 的完整原因。
- Runtime 中遗留的 `clear_log_file` 导入已经清理。
- 四个修改文件已通过 `py_compile`、`git diff --check` 和日志 Handler 配置检查。
- 当前尚未启动完整 Web 服务执行端到端查询，JSON 事件内容需要在下一次手动运行时确认。

### 阶段四异常边界设计

- 核心查询节点异常继续向上抛出，由 Web 请求边界统一生成 `error_id`、记录完整堆栈并返回安全提示。
- 节点日志只负责指出失败位置，请求日志负责保存最终错误编号和完整异常链，避免每层重复打印堆栈。
- Web 捕获未处理异常后，将 checkpoint 更新为 `failed`，State 只保存错误编号，不保存内部异常文本。
- SQL 校验失败仍属于正常业务分支，不转换为 Python 异常。
- Intent Classifier 和 Evaluator 属于可降级能力，失败时记录 `node.degraded`，不影响核心查询结果。
- Evaluator 位于 FinalAnswer 之后，因此其 LLM、MySQL 或 FAISS 异常不能把已经完成的查询重新标记为失败。
- 前端只展示统一安全文案和 `error_id`，完整异常类型、消息和堆栈仅保存在服务端 JSON 日志中。

### 阶段四实现结果

- `graph_logger.py` 已支持 `error_id/error_code/error_type/error_message/stack_trace`，完整堆栈不再经过普通文本截断。
- 新增 `node.degraded` 事件，用于区分可恢复的附加能力异常和核心查询失败。
- Evaluator 的 LLM、自评入库和 FAISS 异常均改为非阻断降级，不再重新抛出影响最终答案。
- Intent Classifier 异常改为结构化降级日志，并继续使用 query 路由兜底。
- Web 已建立统一请求异常边界，异常时生成 `error_id`、写入 `failed` checkpoint，并把下一轮切换到新 Topic。
- State 的 `error_message` 只保存错误代码和编号，不保存数据库地址、Python 路径等内部异常文本。
- 前端只展示安全提示和错误编号，不再直接展示 `str(error)`。
- Python、JavaScript、差异格式和内存异常日志 payload 检查均已通过；完整 Web 运行仍需重启后手动验证。

## 七、日志定位案例：用户确认后仍被重复追问

### 现象

用户先选择 Advisor 给出的候选口径，Advisor 回复“当前方案已完整明确”；用户随后回复“好的”，系统却再次要求选择口径。第二次形成真实 locked 方案后，再次回复“好的”才进入 Seeker。

### 日志还原

- Planner 已把用户选择还原为唯一字段，但高相似字段数量超过阈值，程序硬规则把 `full` 重新降为 `partial`。
- Advisor 本轮没有调用 `submit_query_plan`，日志明确显示 `locked=False`，但 LLM 文本仍声称方案已经完整。
- 用户回复“好的”后，Planner 尝试确认方案，领域服务返回“当前不存在可确认的查询方案”。
- Planner 本轮输出的完整度已经是 `full`，但进入 Advisor 子图后日志变成 `completeness=none`。
- 根因是 `AdvisorState` 没有声明 `planner_entities/planner_reason`，父图字段进入子图时被 State Schema 过滤。

### 设计结论

1. Planner 和 Advisor 之间需要独立的 Handoff State 契约，不能依赖父图 `AgentState` 自动透传未声明字段。
2. 删除候选数量对路由和 `completeness` 的硬控制，保留高相似候选统计作为日志、调优和告警指标。该代码改造尚待实施。
3. Advisor 只有在程序获得 `locked_plan` 后才能展示完整确认方案；Plan 模式未调用 `submit_query_plan` 应视为协议未完成并内部重试，不能直接展示 LLM 原文。
4. 新增独立 `PlannerHandoffState`，显式传递 `planner_reason/planner_entities`；该代码改造尚待实施。

## 九、当前边界

- 日志、异常边界和前端安全错误提示已经完成；Planner Handoff 与候选硬门禁移除尚未修改业务代码。

## 十、面试表达

### 30 秒版本

项目原有日志能看到节点耗时和路由结果，但没有请求身份，并发后无法串联。我没有在每个节点重复传递 ID，而是在 Web 和 CLI 入口使用 `ContextVar` 绑定 `conversation_id/topic_id/request_id/graph_thread_id`，由统一日志组件自动注入。随后把日志改为 JSON Lines 和按日期滚动，并增加请求、节点、路由、状态变化和异常事件。这样可以通过一个 `request_id` 还原完整链路，同时避免完整 State、查询结果和内部异常泄露到前端。

### 为什么不直接使用外部可观测平台？

当前系统处于单体上线阶段，先建立稳定的日志字段和事件语义。未来接入 OpenTelemetry 或日志平台时，可以直接复用这些字段，不需要重新改造业务节点。
