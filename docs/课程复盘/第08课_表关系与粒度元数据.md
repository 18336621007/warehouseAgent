# 第08课：表关系与粒度元数据复盘

> 日期：2026-08-03  
> 课程状态：已完成  
> 复盘用途：面试中说明 Join 安全设计、关系元数据模型和单文件可复用架构  
> [返回文档索引](../文档索引.md)

## 一、本课目标

建立可维护的表关系元数据目录，为 JoinPlanner 提供已审核的安全关联路径，禁止 LLM 现场猜测 Join 键。

## 二、困难一：关系存储放哪里

### 讨论过程

最初考虑 MySQL 存关系，但关系元数据是配置而非运行时数据——改一次关系不需要 SQL 写入，也不会有并发修改。最终采用 `semantic_metadata.json` 单文件方案。

### 设计取舍

- `tables` 和 `relations` 共用一个 JSON，单文件、单 Provider、单一真相来源
- `columns` 字段预留为空数组，未来语义层扩展时直接填入业务指标映射，Provider 接口不变
- `enabled` 字段控制 Runtime 可见性：`false` 表示审核未通过或已废弃，JoinPlanner 不读取

## 三、困难二：联合主键的处理

原始设计 `primary_key: str`，但实际业务中 `rent_detail_no + pt_platform` 这样的联合主键是常态。改为 `primary_key: list[str]`，单主键写 `["id"]`，联合主键写 `["key1", "key2"]`。Provider 的 `get_table_primary_key` 返回类型同步改为 `list[str]`。

## 四、困难三：后续语义层如何复用

`columns` 字段当前为空。语义层需要以下信息时直接填入：

- 业务别名（"channel_name" 的业务名叫"渠道名称"）
- 默认聚合方式（`new_order_amount` 默认 `SUM`）
- 固定过滤条件（`status = 1`）

这些信息不需要新建表或新 Provider，同一个 JSON + 同一个 `SemanticMetadataProvider` 读不同 section 即可。

## 五、关键修改文件

## 六、面试表达

### 30 秒版本

多表 Join 最大的风险是 LLM 自由猜测关联键和基数字段。我建立了一套关系元数据模型，用 JSON 配置文件描述"表 A 通过 channel_id 以 many_to_one 关联表 B"。所有关系必须人工审核并标记 enabled=true 后才对 Runtime 可见，`many_to_many` 默认拒绝。JoinPlanner 只从这份配置中读取安全路径，不会让 LLM 自己判断能不能 Join。
