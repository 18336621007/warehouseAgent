# 第13课：连续问答与延迟澄清恢复复盘

> 日期：2026-08-10
> 课程状态：已完成
> 复盘用途：面试中说明多轮对话的确定性收敛——判断归模型、校验归程序、编号冻结、元数据可信分层与优秀案例存储去重
> [返回文档索引](../文档索引.md)

## 一、本课目标

在不新增独立 Agent、不依赖硬编码业务规则的前提下，让同一 Topic 支持连续问答与延迟澄清恢复：

1. **结果追问**：引用上一轮查询结果继续查询（如“第一名的业务经理是谁”）。
2. **方案追问**：沿用上一轮 QueryPlan 只修改时间、过滤、维度或指标（如“换成近 7 天”）。
3. **延迟选择**：Advisor 给出候选后，用户隔数轮再回复“第二个”仍能定位原候选。
4. **冲突保护**：多 pending 时不猜测；经评估，当前系统一次只澄清一个问题，该能力关闭。

## 二、问题与根因

### 现象

1. 用户回复“3”，最终方案却是别的字段；用户选“2”，方案却给了 `order_last_renting_com`，编号解析反复出错。
2. `MetricClarificationService` 用 `_CHINESE_NUMBERS` / `_match_by_index` 写死“第几个=第几个候选”，无法泛化且易受候选重排影响。
3. 一个“新增订单”概念召回十多个口径，一次全部展示，用户负担大。
4. 澄清描述用 LLM 增强别名（“当日租赁中订单数”），与报表组原始备注（“日租租赁中订单数”）不一致，误导用户。
5. 优秀案例保存的是改写后问题，用户原文与去重口径不一致，同义问题可能重复入库。

### 根因

1. 候选编号在每次重排后变化，跨轮解析无稳定锚点；用“最近一条 AI 消息”反推候选不可审计。
2. 选择判断本应依赖模型对对话历史的语义理解，却被写死规则替代。
3. 检索候选无上限、无模型精选，程序把“全部真实候选”直接当“展示候选”。
4. 展示层混用 DDL 原始备注与 LLM 增强元数据，增强内容被当成可信来源。
5. 案例存储语义不清：改写与原文混存，去重键不稳定。

## 三、方案取舍

| 候选方案 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| 保留硬编码序号解析 | 实现简单 | 无法泛化、重排即漂移、模型能力闲置 | 不采用 |
| 让 LLM 直接输出任意字段名 | 灵活 | 可能输出候选外字段，不可审计 | 不采用 |
| 程序召回全部候选一次展示 | 信息完整 | 候选过多、用户负担大 | 不采用 |
| 程序召回真实候选 + 模型受限精选 + 编号冻结 + 程序白名单校验 | 展示可信、编号稳定、输出合法 | 需要新增状态与服务 | **采用** |
| 新增 `follow_up_context` / `active_clarification_id` 等结构化状态 | 引用精确 | 状态复杂、当前单澄清 + 历史推断已覆盖 | 评估后不采用 |

**最终方案**：判断归模型、校验归程序。程序只负责召回真实元数据（字段 + 原始备注 + 来源表）、冻结编号和白名单校验；模型负责判断用户意图（选择/询问区别/闲聊/追问）并挑选最相关的 ≤N 个候选；跨轮靠 `pending_clarifications` 固定 `clarification_id` 与 options，不依赖消息文本反推。
## 四、实现内容

### 新增文件

- `langgraph_app/services/candidate_reranker.py`：模型受限精选，程序召回真实候选交模型挑选 ≤`MAX_AMBIGUITY_CANDIDATES` 个，输出必须命中候选集合，不足 `RERANK_MIN_CANDIDATES` 由程序补足。
- `langgraph_app/services/metric_clarification_service.py`（升级）：`pending_clarifications` 注册表、`validate_user_selection` 白名单校验、`freeze_reranked_options` 编号冻结（`frozen_options_by_mention`）、澄清文本与口径区别说明。
- `langgraph_app/services/metric_ambiguity_validator.py`（升级）：候选收集改为表作用域逐表 + 全局兜底，与检索路径一致。

### 修改文件

- `state/analysis_spec.py`：`pending_metric_clarification` 升级为 `pending_clarifications` 列表（`PendingClarification`：clarification_id/mention/question/options/status/created_request_id/last_active_request_id/resolved_value）。
- `state/base_state.py`：新增 `effective_query`（Planner 每轮改写后的有效需求，`original_question` 保留话题原文不覆盖）、`last_query_result`（查询结果快照：引用 + 预览 + 实体键）。
- `state/planner_state.py`：`PlannerOutput` 新增 `user_selection`（selected/clarification_id/field/reasoning）与 `follow_up_mode`（new_query / plan_refinement / result_follow_up / clarification_explanation）。
- `nodes/planner_node.py`：两段式召回（先表级 `TABLE_SEARCH_K`，再表作用域逐表字段 `PER_TABLE_COLUMN_QUOTA`，最后全局字段兜底）；消费 `user_selection`；Planner 聚焦判断（选定单一口径后 `effective_query`/`metric_mentions` 只保留该口径含义）。
- `nodes/build_final_answer_node.py`：查询成功/空结果后写入 `last_query_result` 结果快照；回答基准使用 `effective_query`（回退 `original_question`），已确认口径覆盖收敛到 `confirmed_plan.measures`，修复多轮追问后按首轮问题误判“数据不足以回答”。
- `prompts/planner_prompt.py`：模板改为【当前需求基线（滚动）+ 对话历史 + 本轮输入 + 待澄清候选 + 已确认口径】；澄清与方案确认模板收敛，避免长篇大论。
- `config/advisor.py`：新增 `MAX_AMBIGUITY_CANDIDATES`、`PER_TABLE_COLUMN_QUOTA`、`RERANK_MIN_CANDIDATES`；检索 K 复用 `config/planner.py` 的 `TABLE_SEARCH_K/COLUMN_SEARCH_K`。
- `metadata/mysql_store.py`：`enriched_columns` 新增 `meta_source`（`ddl_comment`/`llm_enhanced`），澄清选项、口径区别说明、方案确认优先展示原始备注。
- `langchain_app/vectorstores/example_vector_store.py`：优秀案例两级去重（精确 hash + 语义 ≥`EXAMPLE_DEDUP_SIMILARITY=0.9` 且表/字段一致，高分优先合并）；FAISS 用原文召回、`effective_query` 注入 Few-shot；`sync_by_score` 透传 `effective_query`。
- `nodes/evaluator_node.py` 与 `config/evaluator.py`：`example_hash` 统一为 `example_hash_id(question)`，MySQL 与 FAISS hash 口径一致；`init_evaluator_table` 自动补 `effective_query` 列。
- `runtime/graph_logger.py`：日志补充记录 `request.input` 用户输入原文，便于链路排查。

## 五、关键设计

1. **判断归模型、校验归程序**：Planner LLM 只基于 State 中真实保存的 pending options 判断 `user_selection`；程序 `validate_user_selection` 做白名单校验（field 逐字命中 options 且 clarification_id 对齐），候选外字段或 id 不匹配一律拒绝，宁可不选也不猜测。
2. **编号冻结**：`freeze_reranked_options` 在精选后由程序统一分配编号，预校验与提交门禁共用同一份 `frozen_options_by_mention`；跨轮由 pending 复用保证编号稳定，修复“用户回 3 方案却是别的字段”。
3. **展示完整、解释受限**：“请选择”由程序模板完整列出冻结候选；仅“询问区别/闲聊”允许 LLM 自由文本，且过 `validate_field_references` 字段白名单。
4. **元数据可信分层**：展示优先字段原始备注，无备注才回退“系统推断别名”；增强元数据只参与召回不参与面向用户的解释。
5. **优秀案例原文召回**：`question` 存用户原文用于召回与去重，`resolved_question` 存改写 + 确认方案，`effective_query` 注入 Few-shot；三层分离避免改写污染去重口径。
6. **延迟澄清恢复**：用户未选择同一概念时复用原 open pending；只有明确解决、用户取消或 Topic 结束时才关闭；新 Topic 不读取旧 Topic 的 pending 与结果快照。

## 六、验证场景

1. 用户先问“新增订单”产生多候选，连续询问两轮口径解释后回复“第二个”，仍命中最初 option 2。
2. 候选在后台重新召回并改变排序后，延迟回复编号仍按原 options 解析。
3. 查询完成后问“A类经销商呢”，能基于上一轮结果与历史对话继续查询，无需新澄清。
4. 用户回复“指标字段为 new_order”，程序白名单命中后同轮锁定，不增加重复确认。
5. 同一问题重复提交只保存一份优秀案例；语义相似且表/字段一致的案例高分优先合并，低分不降级。
6. 多 pending、结果追问路由、`follow_up_context`、pending 过期策略经评估关闭：当前系统一次只澄清一个问题，追问由对话历史推断已覆盖。

## 七、当前边界

- 单澄清模型：一次只存在一个 open pending，多 pending 冲突消解未实现（当前场景不需要）。
- 结果追问依赖对话历史 + `last_query_result` 快照，无结构化 `follow_up_context`。
- pending 无过期策略，依赖 Topic 生命周期关闭。
- 枚举值漏采需手动运行 `refresh_enum_samples.py` 补采；向量索引更新为全量重建，精准单字段更新脚本未实现。
- 优秀案例去重阈值 `EXAMPLE_DEDUP_SIMILARITY=0.9` 与候选数量上限等均为配置项，可按业务调整。

## 八、面试表达

- 用一句话说明“为什么不用硬规则解析编号”：候选重排会让编号失去稳定锚点，硬规则把模型能力闲置，且无法跨轮恢复；改为模型判断 + 程序白名单校验，选择判断可解释、可审计。
- 强调“程序兜底”：元数据召回、编号冻结、白名单校验和字段收敛是程序行为，LLM 只负责语义判断，因此模型输出再不稳定，最终方案也是确定的。
- 强调“展示可信分层”：DDL 原始备注优先、增强别名仅兜底，避免把 LLM 增强内容当权威口径。
- 用验证场景 1/2 说明延迟澄清恢复的价值：用户隔数轮回复编号仍命中最初候选，且不依赖最近一条 AI 消息。
