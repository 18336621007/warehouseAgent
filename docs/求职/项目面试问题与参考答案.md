## 一、面试回答原则

1. 先说业务问题，再说技术方案，不要从框架名称开始背。
2. 强调为什么不能让 LLM 直接生成并执行 SQL。
3. 每个困难至少说明现象、日志证据、根因、候选方案、最终取舍和结果。
4. 不夸大规模，明确当前表数量、测试范围和未完成能力。
5. 对生产化问题给出下一步设计，不要只说“以后优化”。

## 二、项目基础问题

### 1. 请介绍一下这个项目

这是一个面向企业 Hive 数仓的多智能体智能问数系统。用户输入自然语言后，Planner 负责还原有效需求和路由；Advisor 通过元数据工具消除指标、维度、表和时间歧义，生成 locked QueryPlan；用户最终确认后，Seeker 完成字段覆盖、Join 规划、Schema 加载、SQL 生成、安全校验和执行；Evaluator 对对话质量和结果进行评估。系统使用 FAISS 做库表字段检索，MySQL 保存增强元数据，JSONL 日志记录全链路状态。

### 2. 为什么使用多 Agent，而不是一个大 Prompt？

一个 Prompt 同时承担需求理解、元数据映射、SQL 生成、执行和回答，职责冲突且难以设置确定性边界。多 Agent 的价值不是角色名称，而是把不同风险等级的任务拆开：Advisor 可以讨论业务语义，但不能执行；Seeker 可以执行，但只能接受 confirmed QueryPlan；Planner 只路由和确认，不直接修改方案。这样每个阶段都能独立校验和记录日志。

### 3. 为什么选择 LangGraph？

项目需要显式 State、条件路由、子图、循环重试和 Checkpointer。普通 Chain 更适合线性调用，而 LangGraph 可以表达 Planner 到 Advisor/Seeker 的分支、SQL 校验修复循环、执行失败重试以及 Topic 级状态恢复。它也便于把节点输入输出作为可观测契约。

### 4. QueryPlan 解决了什么问题？

QueryPlan 是用户业务意图和物理 SQL 之间的稳定契约。它保存表、指标、维度、时间范围、过滤、排序、限制、字段来源和逐表计划。没有 QueryPlan 时，用户确认的是自然语言，而模型执行时可能换表、换字段或遗漏条件；有 QueryPlan 后，SQL 必须通过程序校验与方案一致。

### 5. locked 和 confirmed 为什么要区分？

locked 表示系统已经形成完整方案，等待用户授权；confirmed 表示用户接受整份方案，可以执行。区分后 Advisor 只能生成方案，Planner 才能根据用户本轮输入完成最终授权，避免 Agent 自己确认自己生成的 SQL。

## 三、核心困难与答案

### 6. 项目中最难的问题是什么？

最难的不是调用模型，而是把非确定性模型输出放进数据系统的确定性安全边界。具体包括多轮需求是否已经明确、字段究竟来自哪张表、Join 是否会放大数据、每张表是否做分区裁剪、模型生成失败如何恢复，以及如何通过日志证明问题发生在哪个阶段。

### 7. 为什么用户会反复确认？你怎么解决？

日志显示 Advisor 在 `locked=false` 时输出“已确认查询方案”，用户确认后 Planner 发现没有可确认方案，只能再次进入 Advisor；Advisor 真正锁定后用户还要再确认一次。根因是 Planner completeness 被当作固定结论，Clarify 模式不能提交方案，却允许输出看起来像最终方案的文本。

我将 Advisor 改为 Adaptive 模式：存在真实业务歧义时继续提问；用户本轮解决最后一个歧义并完成字段核验后，同轮调用 `submit_query_plan`。同时未锁定回复统一增加“仅用于继续核对”，只有真实 locked QueryPlan 才显示最终确认。目标流程变为“澄清—锁定—确认一次—执行”。

### 8. 为什么不能直接根据用户说“确认”就执行？

“确认”必须有明确对象。如果 State 中没有 locked QueryPlan，用户可能只是确认某个指标选项，而不是授权整份查询。Planner 必须同时检查当前方案状态、Advisor 上轮是否展示完整方案、用户是否无修改地接受整份方案，程序还要重新执行 QueryPlan 校验。

### 9. 多表字段来源怎么确定？

Advisor 提交 `field_sources`，例如 `sales_manager → dim_trip.dim_company_snapshot_day`。锁定服务将字符串形式标准化为字典。Coverage Analyzer 在执行前只在指定表中精确校验字段存在性；如果不存在就报 uncovered，禁止重新搜索后静默换到另一张表。未指定来源的兼容场景才使用向量检索定位。

### 10. 为什么不完全依赖向量检索选表？

向量检索适合召回，不适合最终裁决。同名字段、相似业务词和元数据注释不足都会产生错误候选。最终执行应该使用用户已确认的字段来源、关系元数据和程序校验。向量分数保留用于排序、日志和离线调优。

### 11. JoinPlanner 是怎么实现的？

JoinPlanner 从 semantic metadata 读取 enabled 关系，将参与表构造成无向邻接图，通过 BFS 连接目标表并生成 Join 边。每条边包含左右表、左右键、Join 类型和基数。当前支持单字段和复合字段列表，并检查左右键数量一致。

### 12. 为什么 Join 键要支持复合字段？

真实数仓中 `company_id` 可能只在某个平台内唯一。如果只按 `company_id` 关联，不同平台相同 ID 会交叉匹配。当前运营日报和经销商维表使用 `pt_platform + company_id`，避免跨平台重复和指标膨胀。

### 13. 允许 LLM 推测 Join 安全吗？

不是绝对安全，因此做成开关。人工关系路径存在时优先使用配置；缺失路径且开关开启时，LLM 可以根据 Schema 推测，但仍受表白名单、只读、逐表过滤和最终 SQL 校验约束。生产环境可以关闭开关，或者把推测结果送人工审核后写回关系元数据。

### 14. 这次维表数据膨胀的根因是什么？

最新日志中的 SQL 已经使用正确复合 Join 键，但只在 WHERE 中过滤事实表 `pt_dt`，快照维表没有日期条件，历史分区全部参与 Join。由于同一经销商在多个日期存在多行，事实指标被重复聚合。原校验只检查 SQL 任意位置存在 `pt_dt`，事实表条件掩盖了维表缺失。

### 15. 如何解决维表缺少 pt_dt？

我在 Hive Guardrails 增加全局配置 `REQUIRED_FILTER_FIELDS_FOR_ALL_TABLES=["pt_dt"]`。SQL 校验器解析每张物理表和别名，只在 ON/WHERE 中判断真实过滤；每张表必须分别出现 `alias.pt_dt` 常量或函数条件。简单查询缺失时根据 confirmed QueryPlan 自动重建 SQL，事实表条件放 WHERE，LEFT JOIN 维表条件放 ON；复杂查询继续走 LLM 修复，执行前保留硬门禁。

### 16. 为什么 `a.pt_dt = b.pt_dt` 不算过滤？

它只说明两个字段相等，没有限制具体日期，Hive 仍可能扫描并连接全部历史分区。真正过滤必须是 `a.pt_dt = '20260803'`、`date_sub`、`IN`、`BETWEEN` 等常量或函数表达式。校验器会区分字段引用和真实过滤值。

### 17. 为什么维表时间条件放在 ON，而不是 WHERE？

对于 LEFT JOIN，如果把 `b.pt_dt = ...` 放在 WHERE，主表中没有对应维度记录的行会被过滤，语义退化为 INNER JOIN。放在 ON 中既能裁剪维表分区，又保留左表记录。

### 18. 业务过滤为什么不能复制到每张表？

时间分区字段可以通过全局 Guardrails 要求每张表都有，但业务过滤通常属于特定表。例如主表的 `platform_type='换电'` 不一定是维表字段。系统只为所有表补齐时间计划，全局 `filters` 只兼容主表，其他表必须使用自己的 `table_plan.filters`，可以为空或不同。

### 19. SQL 自动修复是怎么做的？

生成 SQL 后先执行程序化逐表过滤校验。普通聚合查询如果缺少必选字段，并且时间范围属于确定性构造器支持的场景，系统直接根据 QueryPlan、field_sources、joins 和 table_plans 重建 SQL。修复后再次校验；无法构造或复杂查询则把错误原因交给 LLM 重试，最终仍可降级或拒绝。

### 20. 为什么还需要 LLM SQL Audit？

程序校验适合检查表名、字段、聚合、Join 键、过滤和 LIMIT 等明确规则，但一些语义一致性难以通过正则或轻量 AST 完整覆盖，例如用户说“新增回流订单”是否使用正确指标。程序规则先过滤确定性错误，LLM Audit 再做语义检查，两者不是替代关系。

## 四、State、记忆与并发问题

### 21. State 中为什么同时有 messages 和结构化字段？

messages 保存用户与 Agent 的自然语言上下文，QueryPlan、route、topic_status 等字段保存程序控制状态。只使用 messages 会导致每轮都让模型重新推断事实；只使用结构化字段又无法处理自然语言修改。两者结合才能同时支持对话和确定性路由。

### 22. 为什么使用 conversation_id、topic_id、request_id 和 graph_thread_id？

conversation 是用户看到的会话容器；topic 表示一个独立分析目标；request 表示一次 HTTP/CLI 调用；graph_thread_id 是 Checkpointer 的执行线程键。分层后可以在同一对话中建立多个 Topic，也能从日志定位某次请求具体经过哪些节点。

### 23. 当前 MemorySaver 有什么问题？

它只在当前进程内保存 State。服务重启、多进程部署和水平扩容时无法共享或恢复 Topic。生产化需要 PostgreSQL/Redis 等持久化 Checkpointer，并处理 State Schema 版本、过期清理和敏感信息。

### 24. 如何处理重复请求？

当前消息 ID 使用 `request_id:user` 和 `request_id:advisor` 等格式，LangGraph `add_messages` 可避免相同 ID 重复追加。但数据库查询和外部副作用还需要独立幂等键；未来会在执行层记录 request_id、SQL 指纹和执行状态，避免网络重试造成重复查询。

### 25. 同一 Topic 并发修改怎么办？

当前尚未完成生产级并发控制。设计上应为 Topic 增加版本号或乐观锁，Planner 基于版本读取 locked plan，确认或修改时进行 compare-and-set；同一 Topic 同时只能有一个执行中的 confirmed plan。

## 五、日志、评估与测试问题

### 26. 日志设计有什么特点？

使用 ContextVar 绑定 conversation、topic、request 和 graph thread 身份，节点不需要重复传参。日志采用 JSON Lines 和按天滚动文件，事件包括 request started/completed/failed、node started/completed/degraded、route decided、state changed 等。异常只在请求边界记录完整堆栈和错误 ID。

### 27. 如何通过日志判断一次查询是否正确？

不能只看最终回答或 Evaluator 分数。应依次检查：Planner 有效需求、Advisor locked plan、table_plans、Coverage 字段来源、Join 路径、最终 SQL、逐表必选过滤、执行行数和最终答案。Evaluator 可能只根据自然语言和 SQL 表面结构评分，无法发现所有数据质量问题。

### 28. Evaluator 有什么作用和风险？

作用是对完整性、体验、耗时、轮次和自评进行统一评分，并把高质量样本写入示例库。风险是模型评估不等于真实业务正确性，所以它不能决定 Topic 是否完成，也不能替代 SQL Guardrails 和人工验收。

### 29. 你怎么测试这个系统？

目前包含 SQL 只读安全样例、Hive Guardrails 测试以及多表确认协议回归测试。新增测试覆盖单次确认、复合 Join、AI Join 开关、LEFT JOIN 过滤语义、逐表全局必选字段、字段对字段不算过滤、自动修复和业务过滤独立性。下一步需要建立标准 NL2SQL 评测集，分层统计意图、Schema Linking、SQL 等价性和执行结果准确率。

### 30. 如何评估 Text2SQL 正确率？

至少分四层：QueryPlan 准确率、Schema Linking 准确率、SQL Execution Accuracy 和最终 Answer Accuracy。字符串完全匹配意义有限，因为不同 SQL 可能语义等价。企业场景还要加入分区扫描量、执行成本、安全拒绝正确率和澄清轮次。

## 六、性能和工程化问题

### 31. 当前性能瓶颈在哪里？

真实日志中 Hive 执行占请求耗时的主要部分，其次是 Planner/Advisor/SQL 生成的多次 LLM 调用。优化顺序应是先减少无效轮次和 SQL 重试，再做元数据缓存、并行检索、查询超时、结果缓存和 Hive SQL 成本优化。

### 32. 为什么不用异步并行所有 Agent？

Planner、Advisor 和 Seeker 存在强依赖，盲目并行会产生浪费。例如未确认 QueryPlan 前不能生成 SQL。可并行的部分是表/字段检索、示例检索、独立 Schema 加载和某些评估任务。应根据依赖图并行，而不是为了并发而并发。

### 33. 如果表数量从 4 张扩到 1000 张怎么办？

需要分层检索和元数据治理：先路由数据库/主题域，再召回表，最后在候选表内召回字段；增加关键词+向量混合检索和 Cross-Encoder/LLM 重排；关系图按主题域分片并缓存；QueryPlan 保存元数据版本；离线统计召回率和误选率。

### 34. 如何避免 Prompt 过长？

Planner 只接收 top-k 候选摘要，Advisor 通过工具按需取字段，Seeker 只加载 confirmed tables 的 Schema。后续会对历史消息做摘要，仅保留原始问题、QueryPlan、最近轮次和关键错误，不长期保存完整 Schema 与结果集。

### 35. 为什么使用 FAISS？

当前项目规模较小，FAISS 本地部署简单、检索延迟低，适合快速验证三级索引。生产环境可以迁移到 Milvus、Elasticsearch/OpenSearch 或数据库向量能力，并补充版本、权限、增量更新和多实例共享。

## 七、安全追问

### 36. 如何防止执行 DELETE、DROP 或多语句？

SQL 在执行前通过只读校验和 AST Guardrails，只允许 SELECT/WITH，禁止 DELETE、UPDATE、DROP 和多语句拼接。表还必须在白名单中，并满足 LIMIT 和分区字段规则。

### 37. Prompt Injection 怎么办？

用户文本不能直接改变工具权限和 Guardrails。元数据工具只返回受控内容，Seeker 只能执行 confirmed QueryPlan，SQL 执行前有独立代码校验。进一步可对元数据文本做来源标记、对系统 Prompt 和工具结果分隔、增加敏感表权限和审计。

### 38. 如何做数据权限？

当前尚未实现完整权限层。生产设计应在 QueryPlan 到 ExecutionPlan 编译阶段注入用户身份、行列权限和脱敏规则，权限条件不能由 LLM 删除；SQL 校验器需要确认这些强制谓词存在。

### 39. AI Join 推测失败怎么办？

如果开关关闭直接拒绝；开启时也不能无条件执行。可以要求模型返回候选键、置信度和依据，使用 Schema 类型、字段名、主键唯一性和小样本探测校验，低置信度进入人工审批，并将确认关系版本化写回元数据。

## 八、架构取舍追问

### 40. 为什么 QueryPlan 里还有 joins 等物理字段？

这是从单表向多表演进时的渐进式设计，避免一次重构所有节点。缺点是业务方案与物理计划耦合，执行阶段会补充 QueryPlan。下一阶段计划拆分 ExecutionPlan：QueryPlan 保存用户确认语义，ExecutionPlan 保存 Join、别名、物理字段、分区谓词和元数据版本。

### 41. 为什么使用 BFS，而不是 Dijkstra？

当前关系图规模小，主要目标是找到能连接目标表的最少边路径，边成本尚未建模，所以 BFS 足够。未来如果加入关系优先级、表大小、基数、扫描成本和桥表风险，就应使用加权最短路或基于成本的 Join Optimizer。

### 42. target_grain 有什么用？

当前主要用于记录参与表粒度，尚未形成完整硬校验。未来会用它判断一对多 Join 上的聚合膨胀：如果目标指标粒度低于 Join 后粒度，需要先预聚合或拒绝执行。

### 43. 为什么不用完整 SQL Parser？

当前轻量校验结合现有 AST Guardrails 和正则，开发成本低，能覆盖主要风险。但多层 CTE、嵌套子查询、复杂别名和方言语法会超过正则能力。功能进入复杂分析阶段后，应统一使用支持 Hive 方言的 Parser/AST，并在 AST 上完成表、字段、谓词和 Join 校验。

### 44. 为什么自动修复选择重建 SQL，而不是字符串追加？

直接字符串追加容易把条件插到错误子查询、破坏 LEFT JOIN 或处理不了别名。普通聚合场景下，confirmed QueryPlan 已包含字段来源、Join 和 table_plans，重建一条标准 SQL 更可控。复杂 SQL 不强行重建，而是进入 LLM 修复和最终安全门禁。

## 九、反问与压力问题

### 45. 这个项目和普通 ChatBI 有什么区别？

区别不在页面，而在执行契约。系统要求业务语义先形成 QueryPlan，再规划多表和过滤，最后执行；每个环节有状态、日志和校验。普通 Demo 常把 Schema 全塞给模型直接生成 SQL，难以解释为什么选表、如何确认口径以及错误时如何恢复。

### 46. 你这个项目真实规模不大，为什么有价值？

规模确实有限，所以不能宣称已经解决超大规模问题。但项目验证了可扩展的核心抽象：分层元数据检索、QueryPlan、关系图、逐表过滤、Guardrails、日志和评测。下一步扩大规模时主要替换存储、检索和调度实现，而不是推翻协议。

### 47. 如果不用大模型能不能做？

固定报表和严格模板查询可以用规则实现，但开放自然语言中的同义词、局部修改、业务歧义和组合分析规则成本很高。合理方案是模型负责语言理解和候选推理，代码负责元数据事实、权限、安全和执行。

### 48. 这个项目最失败的一次设计是什么？

曾经把 Planner completeness 当成硬门禁，并让 Clarify Agent 无法提交方案。它看起来安全，但日志证明当用户已经解决最后一个歧义时，系统仍要额外一轮才能锁定；更糟的是 LLM 文本会伪装成已确认。这个问题让我认识到安全不能只靠“禁止工具”，而要区分业务歧义、工具核验和用户授权三个状态。

### 49. 如果重新设计，你最先改什么？

我会从一开始拆分 QueryPlan 和 ExecutionPlan，并定义 PendingAmbiguities 结构，避免每轮从消息历史重新推断已解决槽位。同时先建立离线评测集和可观测指标，再迭代 Prompt 和阈值。

### 50. 下一步最重要的工作是什么？

短期是 AnalysisSpec 和分析查询 IR，支持 TopN、趋势、同比、环比和占比；中期是持久化 Checkpointer、Topic 并发和执行幂等；长期是大规模元数据检索、权限语义层、成本优化和标准化评测平台。

## 十、白板讲解提纲

面试白板可以画：

```text
User
 ↓
Supervisor Graph
 ├─ Planner ── partial/none ─→ Advisor + Metadata Tools
 │                    └─ locked QueryPlan ─→ User Confirm
 └─ confirmed ─→ Seeker
                  ├─ Coverage Analyzer
                  ├─ JoinPlanner
                  ├─ Schema Resolver
                  ├─ SQL Generator
                  ├─ Per-table Filter Repair
                  ├─ Guardrails / Hive
                  └─ Final Answer → Evaluator
```

旁边补充三条红线：

1. 未 confirmed 不执行。
2. 未通过 Join/过滤/只读校验不执行。
3. LLM 失败必须可重试、可降级、可审计。
