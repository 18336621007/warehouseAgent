# M3 主协调者演进方案：路由收敛 + 校验层独立 + 并行查询

> 目标：把当前「多智能体（Planner/Advisor/Seeker）」演进为「单决策主 Agent + 工具/执行层」的通用 data agent 形态（对齐 Codex）。
> 原则：业务意图交给 LLM，安全永远在程序层；增量迭代、分阶段上生产。

## 一、背景与目标

当前系统是 supervisor（Planner）→ Advisor / Seeker 子图的多智能体架构，存在三个核心问题：

1. **决策分裂**：Planner 和 Advisor 是两个独立 LLM，各自持有上下文，方案/口径在状态传递中丢失语义（历史上反复出现"方案不一致、降级、Advisor 不知道 Planner 决定、反复追问"）。
2. **路由写死业务意图**：`route ∈ {seeker, advisor, answer}` 是程序业务枚举，把 LLM 的连续行为压扁成三个状态，表达不了"澄清+查询混合、先答再问"等真实场景。
3. **skill 需多节点注入**：多决策者导致业务策略（口径追问/反问模板/拒绝场景）要注入多处，成本高且难保持一致。

本次演进的目标形态：**一个会决策的 LLM（Planner）+ 一堆确定性工具/执行链**，skill 只注入 Planner 一次，业务判断全部交给 LLM，程序只保留「协议转移 + 安全校验」。

## 二、多智能体的取舍分析

| 类型 | 例子 | M3 后 | 结论 |
|---|---|---|---|
| 决策型（自己拿主意） | Planner / Advisor | 合并成**一个**连贯决策者 | Advisor 无独立必要 |
| 任务型（吃结构化输入、机械产出） | generate_sql / final_answer | 保留为执行链组件 | 有意义，但**不是智能体、不需要 skill** |
| 确定性程序 | validate / execute | 保留为工具 | 有意义 |

- **Advisor 并入 Planner**：澄清是 Planner 决策的自然延伸（Planner 判断口径不明 → 自己提问 → 等用户回复 → 同一上下文继续）。独立 Advisor 的代价（状态传递、token 重复、策略不一致）远大于收益。
- **Seeker 本就不是智能体**：seeker 子图是 retrieve_schema → generate_sql → validate → execute → final_answer 的节点流水线，M3 后重组为「执行链」，作为 Planner 的工具流程，不做业务决策、不注入 skill。

## 三、Codex 设计参考（隐式路由）

Codex 是单 agent ReAct，**没有业务路由枚举**，程序只响应 LLM 的行为：

| LLM 输出 | 程序做什么 | 谁判断 |
|---|---|---|
| 调工具（tool_call） | 执行工具 → 回传结果 → LLM 继续 | LLM 决定要查 |
| 输出文本 + 不再调工具 | 透传给用户，等用户回复 | LLM 决定"澄清/回答" |
| 最终回答 | 展示，结束 | LLM 决定完成了 |

关键：**LLM 的行为即路由**。程序不建 route 枚举，只做两件事——执行工具、透传消息。安全靠工具内校验（沙箱/白名单/权限），不靠路由。

## 四、本次范围

| 阶段 | 内容 | 上生产条件 |
|---|---|---|
| **A1** | 路由收敛两值（execute/respond）+ 校验层独立挂载 + 结果落盘强制 | ✅ 可上（校验不丢、业务意图交 LLM） |
| **A2** | 并行查询（plans 多方案 + 线程池执行） | 观察 A1 准确性后开 |
| **A3** | 纯 ReAct（删 route，execute_sql 成工具） | 充分验证后作为长期目标 |

本方案文档覆盖 A1~A3 的完整设计；实施按阶段推进。

## 五、目标架构

```
GraphInput
  → capture_user_message
  → planner（主协调者 = 唯一决策 LLM，skill 单点注入）
     ├─ route=execute → 执行链（校验层）
     │     plans[0..n]：generate_sql(LLM) → validate_sql(程序必过) → execute_sql(程序落盘)
     │     结果 → plan_results → 回 planner（LLM 决定 respond 或再 execute）
     ├─ route=respond → 输出文本给用户（澄清或回答由 LLM 自定）→ END 等用户
     └─ 用户回复 → capture_user_message → planner（同一上下文继续）
```

## 六、路由语义

| route | 含义 | 谁判断 |
|---|---|---|
| `execute` | 进入执行链（方案校验→SQL 校验→执行→落盘→结果回填） | LLM 决定要查 |
| `respond` | 输出文本给用户（澄清或最终回答由 LLM 自己定内容），图结束等用户 | LLM 决定要给用户说话 |

删除：`clarify`（并入 respond）、`seeker`（并入 execute）、`answer`（并入 respond）。
协议路由与业务路由分离：业务判断（查不查、问不问、答没答完）交给 LLM；图只需知道「执行 / 输出」两个转移。

## 七、状态设计

### 新增
| 字段 | 类型 | 说明 |
|---|---|---|
| `plans` | `list[QueryPlan]` | Planner 输出的方案列表（单方案=长度1；多方案=并行入口） |
| `plan_results` | `list[dict]` | 每个方案执行结果 `{plan_index, sql, result_id, result_preview, row_count, error, status}` |
| `execution_rounds` | `int` | 本轮 Planner 发起 execute 的次数，防死循环上限（如 ≤3） |
| `last_planner_text` | `str` | respond 时透传给用户的文本，供日志/前端展示 |

### 修改
- `route: Literal["execute", "respond"]`
- PlannerOutput：加 `plans`（可选）；`final_answer` 保留（respond 时填）
- `confirmed_plan`：保留为 `plans[0]` 的同步快照（兼容现有消费方）

### 删除（A1 清理）
- `advisor_state`：`advisor_thinking` / `advisor_next_step` / `advisor_draft_updated`
- `base_state`：`advisor_auto_rounds` / `plan_repair_rounds`（执行链内自愈替代回 planner repair）
- `planner_handoff_state`：Planner→Advisor 交接字段（`planner_entities/planner_reason` 改 Planner 内部用）

## 八、状态流转

```
用户输入
  → capture_user_message（写入 messages）
  → planner（单决策 LLM，skill 注入）
       │
       ├─ route=execute → 执行链（校验层）
       │     for each plan in plans:
       │       generate_sql(LLM) → validate_sql(程序，必须过) → execute_sql(程序，落盘)
       │     结果写入 plan_results
       │     → 回 planner（LLM 看结果：够就 respond，不够/有歧义可再 execute，上限 execution_rounds）
       │
       └─ route=respond → 文本透传给用户 → END（等用户回复）
                              │
              用户回复 ────────┘ → capture_user_message → planner（同一上下文继续）
```

要点：
- Planner 是唯一收口点：execute 执行完必回 planner；respond 必 END，不自循环。
- respond 不判断"是澄清还是回答"：LLM 输出什么文本就透传什么；是否答完由下一轮用户是否继续提问自然决定（Codex 模式）。
- 澄清循环天然成立：respond（澄清）→ END → 用户回复 → planner 同一上下文，记得自己刚才要澄清什么。

## 九、校验层（安全/准确底线，独立于路由）

挂载在 execute 链内，无论路由怎么变都存在：

| 校验 | 节点 | 强制内容 |
|---|---|---|
| 方案完整性 | `validate_query_plan` | plans 结构合法、有时间/过滤 |
| SQL 合法性 | `validate_sql_node` | 字段真实（`is_field_in_table`）、join 契约、必带 LIMIT、必带时间过滤 |
| 执行安全 | `execute_sql_node` | 白名单表、超时、权限 |
| 结果落盘 | `result_store` | 每个子结果落盘，供 respond 引用与后续追问 |

准确性防幻觉（从路由迁移过来）：
- execute 后结果必须落盘、`plan_results` 有 `result_id`，respond 若引用结果才有依据；
- 程序不判断回答内容对错（准确性靠 LLM + 校验层，程序不枚举场景）。

## 十、防循环 / 防幻觉

| 风险 | 机制 |
|---|---|
| Planner 反复 execute 不 respond | `execution_rounds` 上限（如 3），超限强制 respond 或给兜底 |
| Planner 反复 respond 不收敛 | respond 后必 END；同一话题澄清轮次由 `advisor_turns`/话题轮次上限兜底 |
| LLM 跳过查询直接编答案 | execute 链强制校验 + 结果落盘；respond 引用需有 `result_id` |

## 十一、节点改动清单（A1）

| 节点 | 动作 | 说明 |
|---|---|---|
| `planner_node` | 改 | route 两值；输出 `plans`；skill 注入保持；respond 文本直接输出 |
| `supervisor_graph` | 改 | capture→planner→(execute/respond)；execute 链作为子流程，结束回 planner；respond→END |
| 执行链 | 重组 | 复用 generate_sql/validate/execute 节点函数，串成工具链子流程，含校验层 |
| `build_final_answer_node` | 改/删 | respond 由 planner 直接输出；可退化为"多结果格式化"可选 |
| `advisor_graph.py` / `seeker_graph.py` | 删 | 图结构删除，节点函数保留为执行链组件 |
| routers | 改 | 只剩 execute/respond 二分 + execute 完回 planner |

## 十二、并行查询（A2）

`plans: list[QueryPlan]` 是并行入口：
- Planner 把用户需求拆成多方案；**同表同过滤的多指标优先合并成一条多列聚合 SQL**（减少连接数）；
- 执行链内 `ThreadPoolExecutor(max_workers=min(len(plans), 4))` 并行执行；
- 子查询隔离：失败只写 `plan_results[i].error`，不阻塞其他；
- `plan_results` 回填 → Planner 统一 respond，按用户提问顺序组织回答；
- 每个子结果照常走 result_store 落盘，供后续追问。

## 十三、风险

1. 准确性依赖模型：respond 不判断内容，LLM 漏查/编答风险靠「结果落盘 + 引用校验」兜底，需线上观察漏查率；
2. execute 回环 token：执行完回 planner 再看结果，比"一次到底"多一轮 LLM 调用（换取自主决策，可接受）；
3. 并行 SQL 压力：Hive/连接池并发限制，max_workers 上限 + 每查询超时；
4. 回归面大：A1 阶段跑全量 unittest + 覆盖案例（澄清、多口径、直接答、0 行、SQL 失败）。

## 十四、skill 与多节点注入

- skill 只注入 planner（单决策者），无需多节点注入；
- Advisor 并入后，口径追问模板/反问模板/拒绝场景由 skill 注入 Planner，Planner 直接产出规范澄清文案；
- 与 skill 机制（`agentTest/skills/` + `SkillManager`）保持解耦：skill 是策略层，M3 只影响注入点数量，不影响 skill 机制本身。
## 十五、A1 落地记录（2026-09-11）

A1 已实施完成，全量 unittest（130 项）+ Hive 集成测试通过。以下为落地结果，供后续 A2/A3 参照。

### 15.1 落地要点
- **路由收敛**：`PlannerOutput.route ∈ {execute, respond}`（删除 seeker/advisor/answer/clarify）。Planner 是唯一决策者；`execute` 进执行链、`respond` 输出文本后 END 等用户（Codex 模式）。
- **Advisor 并入 Planner**：删除 `advisor_graph.py` / `advisor_state.py` / `build_final_answer_node.py`；澄清不再降级 Advisor，由 Planner respond 直接产出，同一上下文继续。
- **执行链重组（原 Seeker）**：`retrieve_schema → generate_sql → validate_sql → execute_sql → persist_result`；执行成功落盘后回 Planner 撰写最终回答。
- **结果强制落盘**：新增 `persist_result_node`，有数据 → `execution_review=True` 回 Planner 评审；0 行 → `seeker_empty_result=True` 回 Planner 用 probe_values 自愈或确认无数据后告知。
- **失败确定性兜底**：新增 `query_error_fallback_node`，SQL 校验失败/执行失败重试耗尽后直接输出用户可见错误文本并结束，不再消耗额外 LLM 轮次。
- **Evaluator 上移到父图**：仅"执行回看后的 respond（evaluator_pending=True）"触发评估；澄清/直接回答跳过。
- **防死循环**：`execution_rounds` 上限 `MAX_EXECUTION_ROUNDS=3`（config/planner.py），超限强制 respond；`capture_user_message_node` 每轮用户输入重置执行/评审/评估标记。

### 15.2 实际节点与路由（与本文 §五/§六/§十一 对齐）

```
capture_user_message → planner
  planner route=execute  → seeker（执行链）→ {review|repair|empty_self_heal → planner；fallback → plan_error_fallback；end → END}
  planner route=respond  → END（若 evaluator_pending → evaluator → END）
plan_error_fallback → END
```

- 改动：`planner_node.py`（route 两值 + respond 直接输出 + 上次执行结果注入）、`supervisor_graph.py`（去 advisor 子图、evaluator 上移）、`seeker_graph.py`（执行链重组）、`routers/*`（二分 + 回 planner）
