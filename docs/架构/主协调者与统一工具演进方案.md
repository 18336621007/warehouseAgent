# 主协调者与统一工具演进方案

> 目标：把当前多智能体 Text2SQL 系统演进为「主协调者 + 统一工具」的通用智能体形态（参考 Codex 的主 agent + 子 agent + 统一工具集）。
> 原则：增量迭代、逐步确认；安全永远在程序层；工具与节点解耦；不引入不必要的抽象。

## 一、目标架构（终点形态）

```
主 Agent（原 Planner，ReAct，自主编排）
  ├─ 统一工具注册表（registry）
  │    ├─ sql_query / search_* / update_draft_plan / query_stored_result / …
  │    └─ 每个工具带安全元数据（只读/白名单/行数上限）
  ├─ Advisor（子 agent，按需委派：澄清/核验/读落盘结果）
  ├─ Seeker（子 agent，按需委派：独立/并行查询执行）
  └─ 程序安全层（白名单/只读/LIMIT/字段归属，始终生效，不交给 LLM）
```

核心不变式：**Planner 决定「做什么、找谁做」；轻量操作主 agent 自己做；重活才委派子 agent；安全永远在程序层。**

## 二、当前职责边界

| Agent | 角色 | 做什么 | 不做什么 |
|---|---|---|---|
| Planner | 路由/决策 | 还原需求（query 改写）、检索元数据、判定 seeker/advisor、数据探查（probe_values 实时确认过滤值） | 不执行最终 SQL、不做口径澄清 |
| Advisor | 澄清/核验 | 对话补口径、核验表/字段、更新共享方案、读落盘结果回答追问 | 不探查实际业务数据、不锁定方案、不决定是否执行 |
| Seeker | 执行 | 加载 schema、生成 SQL、校验、执行、总结回答 | 不澄清、不改方案 |
| 程序安全层 | 安全底线 | SQL 校验、白名单、只读、LIMIT、字段归属、审计 | — |

边界一句话：Planner 决定「做什么、找谁做」并负责数据探查（事实问题查库可解）；Advisor 负责「把口径问题问清楚」；Seeker 负责「把方案变成 SQL 和答案」；程序层负责「安全底线」。

## 三、分阶段路线图

### M0｜打通「落盘结果可用」（当前阶段）
目标：让 LLM 用上落盘中间结果，职责并入 Advisor（不单独建节点）。

- `query_stored_result` 进 Advisor 工具（conversation_id 用 contextvar 注入，run_advisor 入口 set / finally reset）
- 删除 result_review 节点（supervisor / planner_router 删节点和边；nodes/result_review_node.py 删除）
- Planner 路由调整：route 去掉 result_review；result_follow_up → advisor + result_ref + 聚合意图（第14课：`follow_up_mode` / `result_ref` 一并移除，连续问答类型由 Planner LLM 结合对话历史自行判断，Advisor 按需调用 query_stored_result）
- prompt 同步：planner / advisor prompt 说明可用工具读落盘结果

验收：端到端「统计各个原因多少条」→ Advisor 调工具返回计数；不重查 Hive、不塞全量；全量测试通过。

### M1｜统一工具注册表（地基）
目标：工具成为一等公民，与节点解耦，为 Planner 工具化铺路。

- 新建 registry（tools/registry.py）：收拢 sql_query、search_*、update_draft_plan、query_stored_result
- 工具带元数据：name / 描述 / 安全级别（read_only、字段白名单、行数上限）
- 节点从 registry 取子集：Advisor 取 [search_*, update_draft_plan, query_stored_result]；Seeker 取 [sql_query, schema 工具]

验收：行为不变，但任何节点拿工具都走 registry；新增工具只注册一次。

### M2｜Planner 工具化 → 主协调者雏形
目标：Planner 从「单次结构化输出」升级为「可调工具的 ReAct」，但保留路由骨架。

- Planner 升级 ReAct：可调 registry 工具，先检索元数据 / 读落盘结果预览，再输出 route + 方案
- 工具子集先给「只读安全」的（元数据检索 + query_stored_result 预览），先不给 sql_query
- 保留结构化输出：route + confirmed_plan 仍程序校验，只是判定过程可多步

验收：Planner 能自主判断「这个统计用落盘结果还是查库」；路由结果与 M0 一致；token 增幅可控。

### M2b｜0 行自愈与数据探查职责（已完成）
目标：查询 0 行时由 Planner 自主探查实际值，不把事实问题抛给用户（参考 Codex「查不到数据返回用 LIKE 确认」）。

- `probe_values` 工具：受控只读 LIKE 探查（`SELECT DISTINCT col FROM table WHERE col LIKE '%kw%' LIMIT n`），
  白名单校验、字段真实性、LIKE 转义、上限 50，只注册进 planner 工具组
- 0 行自愈链路：execute_sql 返回 0 行 → 回 Planner 注入【上次执行 0 行反馈】→
  Planner 优先调 probe_values 探查实际值、修正 filters 后 route=seeker 重跑；确认无数据则 route=answer 直接告知
- route=answer：Planner 直接回答能力（无需再查，final_answer 写入历史，消息 id 以 :answer 结尾）
- 事实问题 vs 口径问题：过滤值与实际存储值不匹配属「事实问题」，查库可解，禁止 route=advisor 问用户；
  只有需要用户在多个候选之间选择的口径歧义才允许 route=advisor（prompt 约束，非程序兜底）
- dimension_mentions 软失败：未命中语义层实体的维度词跳过不阻断（写入 unresolved_dimensions 供审计），
  不再因槽位分类错误导致方案构建失败

### M3｜主 agent + 按需委派子 agent（Codex 形态）
目标：Advisor / Seeker 从「固定管线节点」降级为「按需拉起的子 agent」。

- 主 agent 自主编排：轻量操作自己做（查库/读历史/改方案）；重活（长查询、需隔离探索）才委派
- 子 agent 按需创建：Advisor（澄清）/ Seeker（执行）由主 agent 决定拉起时机，工具从 registry 取
- 程序安全层不变：SQL 校验 / 白名单 / 审计始终在程序层

验收：同一问题主 agent 能走「读历史→回答」或「查库→回答」两条路；委派逻辑可审计。

### M4（可选）｜增强
- 并行子 agent（多个独立查询同时跑）
- 受控 python / 文件工具（沙箱或白名单参数）
- 跨会话结果读取（显式放开时）

## 四、贯穿原则

1. 增量迭代：M0 先做，每阶段独立验收、可回滚，不做一次性大改
2. 安全在程序层：白名单 / 只读 / LIMIT / 字段归属 / 审计永远不交给 LLM
3. 工具与节点解耦：任何新工具进 registry，未来主 agent 自动获得
4. 不加死规则：是否读落盘结果、分组维度，由 LLM 决定，程序只保证工具安全
5. token 可控：注入摘要 / 路径，不塞全量；工具返回行数设上限
