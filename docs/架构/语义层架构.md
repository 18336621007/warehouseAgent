> 更新日期：2026-09-03

> [返回文档索引](../文档索引.md)

## 一、定位与职责

语义层是**人工维护的确定性业务口径层**，回答"用户说的业务词是什么指标、怎么算、查哪张表"。

与双路召回（向量 + BM25）的分工：

| 层 | 回答的问题 | 性质 |
|---|---|---|
| **语义层** | 业务词 → 指标（来源表/表达式/别名/单位/支持维度） | 权威、确定性、可审计 |
| **双路召回（向量/BM25）** | 物理上有哪些表/字段可能相关 | 发现、相似度排序、有噪声 |

**原则：语义层优先，双路召回兜底**——语义层命中用权威口径；未命中或歧义时，才用向量/BM25 去物理元数据里发现。

## 三、核心组件职责

### 3.1 `semantic_layer_provider.py` —— 数据层 + 匹配引擎

- **加载**（`load()`）：把 YAML 读进内存：
  - `_metrics`：`{指标id: 完整定义}`
  - `_metric_aliases`：`{别名小写: 指标id}`（反向索引，匹配核心）
  - `_entities`（含 `id` 语义名 + `key` 物理键 + `display_fields`）
  - `_physical_tables`（含 `partition`、`field_formats`）/ `_semantic_models`（维度 key 为**语义名**）/ `_relationships` / `_join_contracts`
- **词法匹配**（`match_metrics_from_query(query)`）：分词 → 别名命中 → 打分 → 排序 → 返回**带 score 的指标字典**
- **全文 grep**（`grep_metrics(keywords, limit)`）：按业务关键词对 id/name/aliases/definition/notes/dimensions 全文匹配，
  区分强命中（名称/别名）与弱命中（定义/备注/维度），返回带 `hit_type/strong_hits/weak_hits/grep_score/confidence` 的指标字典
- **指针导航**（`resolve_metric_chain(metric_id)`）：按 metric.source_model → semantic_model → physical 逐层打开，只返回小组信息
- **分区格式**（`get_partition_field_format(table, field="pt_dt")`）：从 physical 字段级 `format` 读取（默认 `yyyyMMdd`）
- **单例**（`get_semantic_layer_provider()`）

### 3.2 `metric_matcher.py` —— 前台封装 + 实体维度解析 + 格式化

- `match_metrics_from_query(question, limit=5)`：词法匹配，调 Provider 取前 5
- `grep_metrics_from_keywords(keywords, limit)`：全文 grep 包装（第1层，含 notes/definition 命中）
- `resolve_metric_chain(metric_id)`：指针导航包装（第2层）
- `resolve_entity_dimension_fields(entity, models, scope_model_ids, provider)`：**relationship 驱动**的实体→维度解析（见第五章）
- `format_metric_context(metrics)`：把指标格式化成【语义层指标候选】文本，`支持维度` 渲染语义 key 并补实体中文名（如 `dealer(经销商)`）

## 四、匹配算法

```python
分词：re.split(r"[\s,，。、;；:：]+") + 追加整句（用于精确子串）
打分：
  token == alias                    → +10（精确命中）
  token in alias 或 alias in token  → +3（包含命中）
排序：score 降序，再按 id
取前 limit=5
```

示例「昨天新增订单数是多少」：

- 分词 → ["昨天新增订单数是多少", "昨天新增订单数是多少"]（整句追加后共两个 token）
- 遍历 `_metric_aliases`：
  - "新增订单数" in "昨天新增订单数是多少" → +3（×2 token）
  - "新增订单" in 句 → +3（×2 token）
  - 累计 `addition_order_num` score=12
- 返回 `[addition_order_num(score=12, source_model="dws_trip.dm_exchange_order_addition_info_hour")]`

### 4.1 全文 grep（第1层，对齐 skill 关键词 grep）

词法匹配只查 name/aliases，**备注（notes）/定义（definition）里的业务词会漏召**
（如"调出"只出现在 `device_transfer_detail` 的 notes 中）。为对齐 skill 的文件系统 grep 思路，
新增 `grep_metrics(keywords)`：对 id/name/aliases/definition/notes/dimensions 全文匹配。

```text
打分：
  keyword in name / alias          → 强命中 +6
  keyword in definition            → 弱命中 +3
  keyword in notes                 → 弱命中 +2
  keyword in dimensions            → 弱命中 +1
hit_type：有强命中=strong，否则=weak
confidence（grep 提示，最终以 LLM 判定为准）：strong=0.9，weak=0.7
排序：grep_score 降序，再按 id；取前 SEMANTIC_GREP_TOP_K=5
```

命中后按 `source_model → semantic_model → physical` 指针导航（`resolve_metric_chain`），
只打开命中指标的小组文件，把分区/物理字段带出（如无分区明细表需用日期字段过滤）。

## 五、语义模型规范（全量改造后）

### 5.1 维度 key 用语义名，field 指向物理字段

```yaml
dimensions:
  dealer:            # 语义 key（业务概念，与 entities.yaml 实体 id 对齐）
    field: company_id
    role: local
    display_field: company_name   # 同表展示字段（名称）
  battery_group:
    field: group_id
    role: local
    display_field: battery_group
  battery_type:
    field: extra_battery_type_id   # 订单表无 battery_type_id，经 relationship 映射
    role: reference
```

- **`role: local`**：字段直接在当前物理表；
- **`role: reference`**：字段不在当前表，需经 relationship 从实体获得（如订单表的 `extra_battery_type_id` 即"电池类型"）；
- **`display_field`**：同表内的展示字段（分组用 key 的 field，展示带出名称）；
- 非实体字段（city/region/status 等）保留物理名作为语义名（physical 里 semantic 即物理名）。

### 5.2 relationship 驱动实体解析（`resolve_entity_dimension_fields`）

用户说"经销商"时，Advisor 的维度实体解析不再靠全模型硬匹配，而是：

```text
dimension mention "经销商"
  → get_entity_by_keyword("经销商") → 实体 dealer（id=dealer, key=company_id）
  → 范围收敛：指标 source_model + join 契约可达模型
  → 对每个候选模型：get_relationships_for_model(model)
      找 to_entity == dealer 的 relationship → keys.from 即分组物理字段
  → 语义维度 key == dealer 的模型维度带出 display_field（company_name）
```

产出候选 `{field: company_id, table, display_field: company_name}`，供 Advisor 短路维度澄清。

### 5.3 指标 `dimensions` 声明

指标必须声明"支持哪些维度分组"，且这些维度必须在 `source_model` 中声明过（全量已补齐，0 个空维度）：

```yaml
dimensions: [battery_type, dealer, extra_battery_type_group, goods_type, order_goods_type]
```

### 5.4 维度度量（`dimensional_measures`）

口径族指标用 `{field}` 占位 + `dimensional_measures` 展开（如丢失电池数 = 热失控/盘点丢失/逾期丢失/用户上报）：

```yaml
expression: sum({field})
dimensional_measures:
  - dimension: 热失控电池
    field: lost_control_in_hot_battery_num
  - dimension: 盘点丢失电池
    field: check_lost_battery_num
```

## 六、完整链路（用户提问 → 语义层映射）

```text
用户：昨天从山东瀛能公司调出的调出明细是多少
  ↓ 第0层  Planner LLM 拆业务检索词（PLANNER_KEYWORD_*）：["调出", "明细"]
  ↓ 第1层  grep_metrics(keywords) 全文检索（含 notes/definition）
  ↓        命中 device_transfer_detail（"明细"强命中 + "调出"弱命中 notes）
  ↓ 第2层  resolve_metric_chain → metric → semantic_model → physical（小组信息，含分区/字段）
  ↓        format_metric_context → 【语义层指标候选】文本（带命中类型/关键词）
  ↓ 第3层  Planner LLM 输出 semantic_metrics: [{id, confidence, mention}]
  ↓ 第4层  分档路由：
  ↓        >=0.9 唯一 → 短路（跳过双路召回，直接用 source_model + expression + 物理字段）
  ↓        0.55~0.9 → 候选反问（候选注入 Advisor，复用现有澄清）
  ↓        <0.55   → 走 RAG 双路召回
```

**Planner 侧**（`planner_node.py`，两阶段 LLM 调用）：

```python
# 阶段A：独立小调用拆检索词
keyword_output = keyword_structured_llm.invoke(...)      # semantic_keywords=["调出","明细"]
semantic_matches = grep_metrics_from_keywords(...)       # 第1层全文 grep（含 notes 命中）
_grep_strong = any(hit_type == "strong")                 # 强命中 → 短路跳过 FAISS
if _grep_strong:                                         # 第2层指针导航构造元数据
    metadata_lines.append(物理字段/分区信息)
# 阶段B：完整结构化输出（含 semantic_metrics 置信度）
planner_output = structured_llm.invoke(...)
_semantic_unique = 唯一 && top>=0.9（LLM 置信度）         # 第4层分档
semantic_metrics / semantic_candidates → new_entities     # 传给 Advisor
log_metric_event("semantic.grep"/"semantic.match", ...)   # 日志（hit_count/tier）
```

**Advisor 侧**（`advisor_graph.py`）：

```python
# 优先复用 Planner 的 grep 候选（含 notes 命中，避免词法漏召"调出"）
semantic_matches = planner_entities["semantic_candidates"] or match_metrics_from_query(...)
# 短路：Planner LLM 判定 >=0.9 的指标（_planner_high_conf_ids）→ 注入 previous_resolutions
# _semantic_override：唯一命中时信任判定，跳过 validator 候选澄清预校验与提交门禁，
#   不再逐概念反问（如"返厂明细/徐州大区/同意返厂"各自召回候选）
# 维度实体解析 → resolve_entity_dimension_fields(relationship 驱动) → 短路维度澄清
# 字段/表挂错仍由提交时 validate_field_table_bindings 确定性兜底（validator 之外）
```

## 七、语义层与双路召回的关系

### 7.1 分层判定（程序化，不只靠 prompt）

```text
① Planner LLM 拆业务检索词 → grep_metrics 全文检索（含 notes/definition）
   ├─ 强命中（名称/别名，hit_type=strong）→ 短路跳过 FAISS，语义层主导
   ├─ 弱命中（定义/备注）→ 保留 FAISS 补充物理字段（RAG 兜底）
   └─ 无命中 → 直接走双路召回
② Planner LLM 对候选输出 semantic_metrics 置信度，分档路由：
   ├─ >=0.9 且唯一（top1-top2 gap≥0.15）→ 以语义层为准：表/字段/表达式用 source_model + expression，
   │      跳过【分层元数据检索结果】段落（Planner）；Advisor 设 _semantic_override 跳过 validator
   │      候选澄清门禁，不再逐概念反问（字段归属仍由提交校验兜底）
   ├─ 0.55~0.9 → 候选反问：语义层候选注入 prompt + Advisor 澄清（复用现有候选口径链路）
   └─ <0.55 → 双路召回兜底：向量 + BM25 检索物理表/字段
```


### 7.2 各自承担什么

- **语义层**：权威口径（来源表/表达式/别名/支持维度）——减少 LLM 猜表猜字段、减少口径漂移、可审计；
- **双路召回**：物理发现（有哪些表/字段、相似度、备注）——覆盖语义层未定义的大量表/字段；
- **程序硬校验**（元数据/白名单/字段归属/分区格式）是最终防线，语义层和召回都不替代它。

### 7.3 谁说了算

- **口径层面**：语义层说了算（双路召回是参考/核验）；
- **执行层面**：程序硬校验说了算（`is_allowed_table` / `validate_field_table_bindings` / `lock_query_plan`）；
- LLM 只在"语义层口径 + 物理候选 + 程序白名单"的交集里组装，不能越权改口径或猜来源。

## 八、当前边界

- 语义层指标覆盖订单/资产/天数池/哈尔滨周月报/双月套餐/三平台天数池；**未定义的业务词走双路召回兜底**；
- 匹配分两层：**词法匹配**（name/aliases，`match_metrics_from_query`）与**全文 grep**（含 definition/notes，`grep_metrics`）；
  口语化改写若不在别名/备注里仍会漏（grep 覆盖面比纯别名宽，但仍是关键词规则不是语义向量）；
- 语义层命中不再靠词法 score 硬判定，而是 **Planner LLM 输出置信度（semantic_metrics）分档路由**：
  unique(>=0.9)/candidate(0.55~0.9)/rag(<0.55)；LLM 未输出但 grep 唯一强命中时回退短路；
- 三平台天数池（美团/淘宝/光宇）表在 **Doris（`data_project` 库）**，`DorisDataSource` 待接入；接入后需用 `DESC` 校准 physical 字段结构；
- 语义层 YAML 变更后需 `reload()` 或重启服务生效；`metrics/**` 中 notes 含 `query_type: detail` 的条目会被 YAML 解析成嵌套 dict，代码已兼容（建议后续规范为引号包裹）。
