# 架构文档：语义层（权威口径层）

> 更新日期：2026-08-27
> 定位：业务词 → 指标 → 来源表/表达式的权威映射，供 Planner/Advisor 优先采信
> [返回文档索引](../文档索引.md)

---

## 一、定位与职责

语义层是**人工维护的确定性业务口径层**，回答"用户说的业务词是什么指标、怎么算、查哪张表"。

与双路召回（向量 + BM25）的分工：

| 层 | 回答的问题 | 性质 |
|---|---|---|
| **语义层** | 业务词 → 指标（来源表/表达式/别名/单位/支持维度） | 权威、确定性、可审计 |
| **双路召回（向量/BM25）** | 物理上有哪些表/字段可能相关 | 发现、相似度排序、有噪声 |

**原则：语义层优先，双路召回兜底**——语义层命中用权威口径；未命中或歧义时，才用向量/BM25 去物理元数据里发现。

## 三、核心组件职责

### 3.1 `semantic_layer_provider.py` —— 数据层 + 匹配引擎

- **加载**（`load()`）：把 YAML 读进内存：
  - `_metrics`：`{指标id: 完整定义}`
  - `_metric_aliases`：`{别名小写: 指标id}`（反向索引，匹配核心）
  - `_entities`（含 `id` 语义名 + `key` 物理键 + `display_fields`）
  - `_physical_tables`（含 `partition`、`field_formats`）/ `_semantic_models`（维度 key 为**语义名**）/ `_relationships` / `_join_contracts`
- **匹配**（`match_metrics_from_query(query)`）：分词 → 别名命中 → 打分 → 排序 → 返回**带 score 的指标字典**
- **分区格式**（`get_partition_field_format(table, field="pt_dt")`）：从 physical 字段级 `format` 读取（默认 `yyyyMMdd`）
- **单例**（`get_semantic_layer_provider()`）

### 3.2 `metric_matcher.py` —— 前台封装 + 实体维度解析 + 格式化

- `match_metrics_from_query(question, limit=5)`：调 Provider，取前 5
- `resolve_entity_dimension_fields(entity, models, scope_model_ids, provider)`：**relationship 驱动**的实体→维度解析（见第五章）
- `format_metric_context(metrics)`：把指标格式化成【语义层指标候选】文本，`支持维度` 渲染语义 key 并补实体中文名（如 `dealer(经销商)`）

## 四、匹配算法

```python
分词：re.split(r"[\s,，。、;；:：]+") + 追加整句（用于精确子串）
打分：
  token == alias                    → +10（精确命中）
  token in alias 或 alias in token  → +3（包含命中）
排序：score 降序，再按 id
取前 limit=5
```

示例「昨天新增订单数是多少」：

- 分词 → ["昨天新增订单数是多少", "昨天新增订单数是多少"]（整句追加后共两个 token）
- 遍历 `_metric_aliases`：
  - "新增订单数" in "昨天新增订单数是多少" → +3（×2 token）
  - "新增订单" in 句 → +3（×2 token）
  - 累计 `addition_order_num` score=12
- 返回 `[addition_order_num(score=12, source_model="dws_trip.dm_exchange_order_addition_info_hour")]`

## 五、语义模型规范（全量改造后）

### 5.1 维度 key 用语义名，field 指向物理字段

```yaml
dimensions:
  dealer:            # 语义 key（业务概念，与 entities.yaml 实体 id 对齐）
    field: company_id
    role: local
    display_field: company_name   # 同表展示字段（名称）
  battery_group:
    field: group_id
    role: local
    display_field: battery_group
  battery_type:
    field: extra_battery_type_id   # 订单表无 battery_type_id，经 relationship 映射
    role: reference
```

- **`role: local`**：字段直接在当前物理表；
- **`role: reference`**：字段不在当前表，需经 relationship 从实体获得（如订单表的 `extra_battery_type_id` 即"电池类型"）；
- **`display_field`**：同表内的展示字段（分组用 key 的 field，展示带出名称）；
- 非实体字段（city/region/status 等）保留物理名作为语义名（physical 里 semantic 即物理名）。

### 5.2 relationship 驱动实体解析（`resolve_entity_dimension_fields`）

用户说"经销商"时，Advisor 的维度实体解析不再靠全模型硬匹配，而是：

```text
dimension mention "经销商"
  → get_entity_by_keyword("经销商") → 实体 dealer（id=dealer, key=company_id）
  → 范围收敛：指标 source_model + join 契约可达模型
  → 对每个候选模型：get_relationships_for_model(model)
      找 to_entity == dealer 的 relationship → keys.from 即分组物理字段
  → 语义维度 key == dealer 的模型维度带出 display_field（company_name）
```

产出候选 `{field: company_id, table, display_field: company_name}`，供 Advisor 短路维度澄清。

### 5.3 指标 `dimensions` 声明

指标必须声明"支持哪些维度分组"，且这些维度必须在 `source_model` 中声明过（全量已补齐，0 个空维度）：

```yaml
dimensions: [battery_type, dealer, extra_battery_type_group, goods_type, order_goods_type]
```

### 5.4 维度度量（`dimensional_measures`）

口径族指标用 `{field}` 占位 + `dimensional_measures` 展开（如丢失电池数 = 热失控/盘点丢失/逾期丢失/用户上报）：

```yaml
expression: sum({field})
dimensional_measures:
  - dimension: 热失控电池
    field: lost_control_in_hot_battery_num
  - dimension: 盘点丢失电池
    field: check_lost_battery_num
```

## 六、完整链路（用户提问 → 语义层映射）

```text
用户：昨天新增订单数是多少
  ↓ ① Planner/Advisor 调 metric_matcher.match_metrics_from_query(当前需求文本)
  ↓ ② SemanticLayerProvider.match_metrics_from_query
  ↓    分词 → 遍历 _metric_aliases → 打分 → 排序
  ↓ ③ 返回带 score 的指标（如 addition_order_num, score=12）
  ↓ ④ format_metric_context → 【语义层指标候选】文本（支持维度带实体中文名）
  ↓ ⑤ 注入 prompt 最前面（"优先参考它们的来源表与口径"）
  ↓ ⑥ _semantic_unique 判断
  ↓    命中 1 个（或 top1-top2 gap≥阈值）→ 跳过双路召回，直接用 source_model + expression
  ↓    多候选歧义（gap 小）→ 保留双路召回，走澄清
```

**Planner 侧**（`planner_node.py`）：

```python
metric_search_text = current_user_input                 # 匹配源
semantic_matches = match_metrics_from_query(...)        # 命中指标（带 score）
metric_context_text = format_metric_context(...)        # 格式化注入
_semantic_unique = 命中1个 或 gap≥阈值                  # 唯一判断
# 唯一 → 跳过【分层元数据检索结果】，用 source_model 直接构造候选
log_metric_event("semantic.match", ...)                 # 日志（hit_count/metric_ids）
```

**Advisor 侧**（`advisor_graph.py`）：

```python
metric_search_text = effective_query or current_user_input
semantic_matches = match_metrics_from_query(...)        # 同样匹配
# 唯一命中短路 → 注入 previous_resolutions → validator 直接保留，不澄清
# 维度实体解析 → resolve_entity_dimension_fields(relationship 驱动) → 短路维度澄清
```

## 七、语义层与双路召回的关系

### 7.1 分层判定（程序化，不只靠 prompt）

```text
① 语义层匹配指标（match_metrics_from_query）
   ├─ 命中且唯一（1 个 或 top1-top2 gap≥0.15）
   │    → 以语义层为准：表/字段/表达式用 source_model + expression
   │      跳过【分层元数据检索结果】段落（Planner）、跳过候选澄清（Advisor）
   ├─ 命中但歧义（多个候选、gap 小）
   │    → 语义层候选注入 prompt（权威口径参考），同时保留双路召回结果做核验/发现，Advisor 澄清
   └─ 未命中
        → 双路召回兜底：向量 + BM25 检索物理表/字段，Planner/Advisor 基于检索结果工作
```

### 7.2 各自承担什么

- **语义层**：权威口径（来源表/表达式/别名/支持维度）——减少 LLM 猜表猜字段、减少口径漂移、可审计；
- **双路召回**：物理发现（有哪些表/字段、相似度、备注）——覆盖语义层未定义的大量表/字段；
- **程序硬校验**（元数据/白名单/字段归属/分区格式）是最终防线，语义层和召回都不替代它。

### 7.3 谁说了算

- **口径层面**：语义层说了算（双路召回是参考/核验）；
- **执行层面**：程序硬校验说了算（`is_allowed_table` / `validate_field_table_bindings` / `lock_query_plan`）；
- LLM 只在"语义层口径 + 物理候选 + 程序白名单"的交集里组装，不能越权改口径或猜来源。

## 八、当前边界

- 语义层 115 个指标覆盖订单/资产/天数池/哈尔滨周月报/双月套餐/三平台天数池；**未定义的业务词走双路召回兜底**；
- 匹配是**关键词/别名规则**（不是语义向量）：口语化改写若不在别名里会漏；
- 三平台天数池（美团/淘宝/光宇）表在 **Doris（`data_project` 库）**，`DorisDataSource` 待接入；接入后需用 `DESC` 校准 physical 字段结构；
- 语义层 YAML 变更后需 `reload()` 或重启服务生效；
- 唯一命中短路依赖 score：`match_metrics_from_query` 返回带 score 的指标字典，`_semantic_unique` 支持"命中 1 个"与"top1-top2 gap≥0.15"。
