# 架构演进说明：从多智能体到单 Agent

> 最后更新：2026-10-08
> [返回文档索引](../文档索引.md)

本文记录系统为什么采用当前的**单 Agent + 工具**结构，以及演进过程中放弃的方案。当前实现细节见 [Text2SQL 系统架构文档](./Text2SQL系统架构文档.md)。

## 一、当前结构

```text
capture_user_message → planner（唯一 Agent，ReAct 工具循环）→ END
                          └─ 工具：语义层检索 / read_skill / probe_values
                                  / query_stored_result / execute_query / make_chart
```

- **Planner** 是唯一的决策者：判断意图、定位口径、决定是否澄清、生成 SQL、撰写回答。
- **execute_query** 是工具，不是智能体：只做引擎路由、安全校验、执行与落盘，不做任何业务判断。
- **没有 Advisor**：口径追问由 Planner 直接输出澄清文案，不再有独立的"澄清智能体"。
- **没有 Seeker**：执行流程已内联进工具，不再作为独立子图或独立智能体存在。

## 二、为什么不做多智能体

早期实现参考学术方案，采用 `Planner → Advisor → Seeker → Evaluator` 的多智能体分工。实际运行暴露出三类问题：

1. **信息在交接中损耗**：Planner 的判断要序列化成 State 字段传给 Advisor，Advisor 再传给 Seeker。字段契约一旦不完整，下游只能靠猜或直接失败，排查成本高。
2. **追问被程序门禁拦死**：为了"安全"引入的模糊度硬门禁，会把模型已经确认的口径重新判为"待确认"，出现重复追问同一件事。
3. **轮次与延迟翻倍**：一次查询要经过多次 LLM 决策与多轮图调度，同样的语义层与数据，端到端耗时明显高于单 Agent 循环。

结论：**多智能体的收益主要在"职责隔离"，而本系统的复杂度集中在"口径定位 + SQL 正确性"，这两件事恰恰需要完整上下文，拆开反而更差。**

## 三、收敛后的设计取舍

| 取舍点 | 选择 | 理由 |
|---|---|---|
| 澄清归属 | Planner 直接输出澄清文案 | 澄清需要的上下文就是对话本身，不需要跨 Agent 传递 |
| 执行归属 | 收敛为 `execute_query` 工具 | 执行是确定性流程，交给程序比交给"智能体"更稳 |
| 安全边界 | 程序做确定性校验，不做业务判断 | 只读 / 白名单 / 分区 / AST 校验属于程序职责 |
| 失败处理 | 错误原样回填给 Planner | 让模型看到真实错误再决定改 SQL、探查取值还是如实说明 |
| 检索顺序 | 语义层优先，RAG 兜底 | 语义层是权威口径，RAG 只补"语义层没覆盖"的情况 |
| 技能注入 | 只注入 Planner | 只有一个 Agent，天然不需要按角色分发技能 |

## 四、保留的可观测与治理能力

架构收敛不代表放弃治理，以下能力被保留并加强：

- **结构化日志**：按 `request_id` 还原完整链路，见 [日志使用与问题排查指南](../指南/日志使用与问题排查指南.md)。
- **语义层权威**：口径不写在提示词里，统一维护在 `semantic_layer/`。
- **确定性安全校验**：SQL 生成由模型负责，能否执行由程序说了算。
- **用户评分闭环**：成功率与用户评分落 `evaluated_dialogues`，RAG 开启时高分案例回流为 Few-shot 示例。

## 五、当前边界

- 多指标长查询仍是主要耗时来源，需要继续做并行与缓存。
- 语义层覆盖不到的口径只能澄清或拒答，不做猜测式补全。
- Checkpoint 已持久化到 SQLite，但尚未做多实例共享。
